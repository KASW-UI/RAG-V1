## 1. 项目背景

识海社区是一套面向中文技术社区的 UGC 内容平台，后端承载**内容生产、互动关系、成长任务、账号体系**四类能力。本仓库（RAG-V1）是其后端服务端的第二版：把第一版 Go 服务（RAG 仓，下称 B 侧）按 Spring Boot 惯用形态重做——**行为等价，代码按 Java 生态重排**。

要解决两个问题：一是 B 侧「一域两进程 + 手写装配清单 + Go 风格全局配置」难以承载 Java 团队的工程规范；二是跨语言重做最易在 proto 字段号、错误码、事务边界上悄悄分叉，且无机器可验的对照手段。

因此本仓把 B 侧定为**唯一行为基准**：按映射表逐类抄写，再把「不一致 / 有意不同 / 为什么踩坑」分落三档台账，用 17 条机器断言与双侧对拍钉死差异。

使用者是社区用户（注册、发文、评论、点赞、收藏、关注、领任务）与社区运营（审核、封禁、公告）。**项目处于开发中阶段**：10 个业务域功能全部落地并通过全仓回归，但尚未提供镜像 / compose 等部署产物，属工程化复刻与教学示范。

## 2. 业务模块

项目采用「一域一进程」形态：**10 个业务域 + 1 个共享层 + 1 个契约模块**，对应 16 个 Maven 模块。各域职责：

**article（文章域）** 建稿、更新、软删除、查询与列表分页、图片上传（MinIO）。文章不直接上线，先入审核态。

**comment（评论域）** 发表评论、删除、点赞、列表查询、审核与举报，并维护评论主体的可见状态。

**like（点赞域）** 点赞与取消、点赞数、点赞状态、点赞者列表、用户点赞列表与用户总点赞。

**favorite（收藏域）** 收藏夹与收藏项的建删改查，支持按目录分页浏览。

**follow（关注域）** 关注、取关、拉黑、解除拉黑，关注/粉丝/黑名单列表与共同关注推荐。

**hot（热度域）** 只算热门文章榜：消费 Kafka 事件，用带衰减的 HeavyKeeper sketch 维护 Top-K 并落 Redis 快照，不持业务数据。

**task（任务中心）** 定义文章任务与点赞任务的目标及进度，Kafka 计数流灌入进度供查。

**message（消息域）** 站内信与通知：会话列表/消息/已读/发送，通知列表/已读/未读汇总，另含管理端下发通道。

**users（账号域）** user 侧注册、登录、注销、资料增删改查、头像上传与历史；admin 侧管理员登录与创建、用户查询列表、封禁与解封、删号、重置密码、邀请码。

**common（共享层）** 不含业务，只给跨域复用的机制：统一响应与异常映射、JWT 鉴权与 Redis 黑名单、日志门面、雪花 ID、Redis 封装、gRPC 拦截链与超时预算、OpenTelemetry 埋点、MyBatis-Plus 类型处理器，以及 comment/favorite/like 三域共用的社区事实事件层。

**proto（契约模块）** 集中 10 份 `.proto`，生成 gRPC 与 DTO 类型，是跨进程字段号的唯一来源。

模块之间是**单向依赖**：`users` 提供身份，`article` 提供内容，comment/like/favorite 围绕内容产生互动，`follow` 提供关系链，`hot` 只读事件做排行，`task` 只读计数，`message` 汇总对用户的告知。跨域写操作一律经 Kafka 事件或 gRPC 调用，域内不直接改别人的表。

## 3. 核心业务流程

**流程一：注册登录 → 发文 → 审核上线 → 进入热度榜**

用户调 `POST /user/v1/register` 落库（`SchemaInitializer` 幂等建表），`POST /user/v1/login` 校验密码哈希与用户状态（封禁用户在此被拒），签发含 `userId` 与过期时间的 JWT，注销时把 token 写入 Redis 黑名单（`user:jwt_blacklist:*`）。作者调 `POST /v1/article` 建稿，文章**先落在 REVIEWING 态**并写同步 outbox；`ArticleSyncOutboxRelay` 定时投递到 `article-creation-topic`，同步结果经 `article-sync-results` 回到 `ArticleSyncResultConsumer`，校验幂等键与版本后才推进为 PUBLISHED 并写 revision 与发布指针，失败则退回 REVIEWING 而非误判发布。发布事件再经 Kafka 流向 hot 域刷新 Redis 快照，客户端 `GET /hot/v1/articles` 取榜单。

**流程二：评论 → 通知 → 事实事件（最终一致）**

用户调 `POST /comment/v1/comment/create` 发评论，事务内同时写评论内容、索引与一条**不可变事实信封**（入 `comment_domain_fact_outbox`）；评论**立即可见**，跨域走异步。通知侧：comment 域经 gRPC 调 message 域发通知，由其生成站内信。事实侧：调度器以 `FOR UPDATE SKIP LOCKED` 取件、校验信封、投递给对端并校验回执；投递失败只记重试次数或标 blocked，**不回滚已提交的评论**——评论先落地，通知与跨域事实最终一致；对端要事实源数据时，经共享层 authority 端点回查。

**流程三：点赞 → 计数 → 热度 → 任务进度**

`POST /like/v1/likeaction` 写点赞记录与 fact outbox；点赞消息在 `like_promotion_topic`（配置键 `like-topic`）驱动计数更新（已点赞去重、取消回退）；计数变化经 `LikeHotEventOutboxRelay` 转发到 `article-hot-events`，hot 域消费后刷新榜单；`LikeTaskProgressPublisher` 同时把增量推给任务中心，任务域按「文章任务 target=3 / 点赞任务 target=5」累加进度落 `task_progress` 表，客户端 `POST /taskcenter/v1/task/get` 查完成度。

**流程四：管理端封禁 → 登录被拒、跨域写入被拦**

管理员调 `POST /admin/v1/banuser`：只改库中 `user.status`（0→1），**不写 Redis 黑名单**（那是注销机制）。封禁后该用户**再次登录**被直接拒（登录三态：status=1 ⇒ 封禁）；其他域解析调用者身份时查库取 status，`status != 0` 即拒 ⇒ 跨域写入立即失效。但 user 域自身只校验签名与黑名单，**已签发 token 要等自然过期才失效**。`unbanuser` 把 status 改回 0，用户即可再登录。

## 4. 技术架构

**后端**：Java 21 + Spring Boot **3.5.11** + Spring MVC + MyBatis-Plus + jjwt + Spring Data Redis(Lettuce) + gRPC(net.devh) + Nacos Discovery + OpenTelemetry + Flyway 11.14.1 + Jackson **2.19.4**（D14：只用 Jackson 2，不引入 Jackson 3）+ Lombok（允许使用，但强制在注解上方写出被简化的完整代码）+ MinIO SDK。

**前端**：本仓**不含前端**，是纯后端仓库；前端与推荐系统不在本仓范围内。

**数据库与缓存**：PostgreSQL 为唯一持久层，33 个 Flyway 迁移脚本（users 域另用 4 个幂等建表脚本）建出 33 张表，按域分表：`article`/`article_revision`/`comment_*`/`like_*`/`favorite_*`/`follow_relation`/`message_*`/`task_progress`/`users_user` 等；Redis 承载计数、热点缓存、JWT 黑名单与热度快照。

**消息队列**：Kafka 承担跨域异步，主题包括 `article-creation-topic`、`article-sync-events`、`article-sync-results`、`article-hot-events`、`like_promotion_topic`、`comment-audit-topic` 与 task 系列日志主题；跨域可靠投递统一走「本地 outbox 表 + `@Scheduled` 定时 relay」，不裸发消息。

**微服务与通信**：10 个域各自是可独立启动的 Spring Boot app，同进程同时暴露 HTTP（Tomcat 10.1）与 gRPC 两套接口；跨域 gRPC 经 Nacos 服务发现寻址，HTTP 路径按域隔离（`/v1`、`/like/v1`、`/comment/v1`…）。

**AI 的使用方式**：**运行态不引入任何 AI/ML 依赖**（推荐系统与内容安全域不在范围内；内容审核端口因缺对端而设计为 fail-loud 抛错、由 Kafka 重投）。AI 用在**研发侧**：主代码由 AI agent 依映射表逐类抄写 B 侧实现，测试与守门脚本同样由 AI 生成，再用变异测试证明判据「能红」，用双侧活体对拍证明「不是假绿」。

**已测试**：全仓串行 `mvn -o clean verify` 回归 **16/16 模块 BUILD SUCCESS · 1611 例 · Failures 0 / Errors 0 / Skipped 0**（2026-11-09 记录；2026-11-10 于隔离工作树 `8d41b8c` 复跑结论一致）；三道守门脚本 `check-mapping-coverage.py`（C 645/645 · B 752/752）、`check-arch-invariants.py`（A1–A17：PASS 15 · FAIL 0 / N/A 2 / PENDING 0）、`check-docs-vs-tree.py` 均 EXIT=0。

**仍在开发/未收口**：并非所有条目都达到「双侧活体对拍」级证据强度，部分域仍有 NOT_VERIFIED 残留（comment 4、favorite 5、like 1、follow 1 项）；`proto` 域台账尚未建立；决策记录 P1–P7 仍待拍板（P4-④ 的 6 处 `GoStyle*` 命名债未清）。

**已知问题**：users 域的 Nacos namespace/group 与 B 侧不一致（已登记签字偏离，属部署面而非行为面）；hot 域的 OTLP 导出缺失、actuator 暴露面偏大等 D-01~D-04 尚未收口；共享层「批 3」与真 Tomcat 守门未开工。

**AI 占比**：645 个主代码类基本由 AI agent 依 Mapping_Table 从 B 侧抄写，注释强制标注「B 出处 + 语义是否一致」三段式；276 个测试类与全部守门脚本同样由 AI 生成——因此本仓的验证重心不在「有没有测试」，而在「测试会不会假绿」，这也是双侧对拍与变异测试占比高的原因。
