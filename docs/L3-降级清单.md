# L3 降级清单

> **本文档记录"完全 Spring 化"过程中，被有意放弃的 L3（影响可观察行为的技术语义）。**
> **这些是决策，不是缺陷** —— 不得反向"修回"旧行为；若认为某条必须保真，走 [`决策记录.md`](决策记录.md) 的 P1–P5 重新拍板。

---

## 〇、什么是 L3

| 层 | 内容 | 本仓库的处理 |
|---|---|---|
| **L1** 外部契约 | HTTP 路由 / 方法 / 出入参、gRPC 方法与 proto、错误码取值、状态码 | **全部保留**，一个字节都不改 |
| **L2** 业务语义 | 业务规则、状态转换、鉴权结果、读写含义、副作用与触发条件 | **全部保留** |
| **L3** 技术语义 | 事务边界、错误传播、超时重试降级、幂等、并发控制、序列化、资源生命周期、消息投递 | **保 6 降 4** |
| **L4** 实现机制 | 依赖注入、配置绑定、拦截器、注册与生命周期、文件划分、样板代码 | **全面重选** |

> **降级的判定标准**：降级项**全部落在框架内部行为**上，**没有一项落在业务语义上**。
> 业务语义降级 = 业务行为变了 = 必须重新拍板，不能由"框架更地道"顺带发生。

## 一、降级项（8 项）

### D-01 · 请求体必填校验的错误文案

| 项 | 内容 |
|---|---|
| **B 侧现状** | B 侧 `GoStyleRequiredFields` / `GoStyleRequired` / `GoStyleRequest`（`service/users/users-common/.../http/`）—— **手写**必填校验器：按字段 tag 上的 `,optional` 判定必填（仅标量字段计必填），缺失时返回 `400  field "username" is not set`（含字段名）。 |
| **完全 Spring 化后** | Bean Validation（`@NotNull` / `@NotBlank`）⇒ 错误文案由 Hibernate Validator 决定，**与 B 侧那套手写文案不同**。 |
| **为什么降级** | 逐字复刻需自定义 `ConstraintValidator` + 维护 B 侧那套 tag 驱动的必填判定规则，**成本高于收益**。 |
| **影响面** | ① 错误**文案**（B 侧那套手写校验器的 `field "x" is not set` / `mustn't be nil` → Bean Validation 文案）；② **map 字段的必填判定**（B 的 `GoStyleRequired.explicitNull` 三态：缺席不报 / 显式 null 报 ⇒ `@NotNull` 会把「缺席」也拒掉 ⇒ **比 B 多拒一类合法输入**）；③ **标量字段的空串合法性**（B 的 `GoStyleRequired.field` 只判 null ⇒ 空串合法 ⇒ 改用 `@NotBlank` 会**多拒空串**）。<br>⚠️ **②③ 的适用范围 = users 域**：B 的 `field()` 在 users 域**只作用于标量**、`explicitNull()` **只作用于 map `extra_info`** ⇒ 标量上 `@NotNull` 与 B **等价**（B 本来就拒「缺席」与「显式 null」）⇒ **多拒只发生在 map 字段（②）与空串（③）两处**。<br>状态码（400）、错误**结构**（text/plain vs JSON）由 `RouterErrorResponses` 独立保证，**不受影响**。⇒ 详见下方 dated note。 |
| **关联决策** | [P1](决策记录.md#p1--错误文案保真度) |
| **验收方式** | 双侧对拍时**忽略 error body 的文本**，只断言 status code + content-type + 错误结构。⇒ **对拍脚本必须显式排除此项，否则会全红。** |
| ⚠️ **2026-11-02 · users 域审核追加：本条的「影响面」原登记偏窄** | 迁移审核（RAG → RAG-V1，users-common 组件）实测：D5 删掉的 `GoStyleRequired*` 里，**除错误文案外还承载了两条 Bean Validation 无等价物的可观察行为** ——<br>① **「缺席 vs 显式 null」的区分（限 map 字段）**：B 的 `GoStyleRequired.explicitNull` 是**三态**语义（字段**缺席** ⇒ 不报；字段**显式为 null** ⇒ 报 `mustn't be nil`；**空串** ⇒ 合法）；而 Bean Validation 的 `@NotNull` 会把「**缺席**的字段」也一并拒掉 ⇒ **比 B 多拒一类合法输入**。<br>**⚠️ 适用范围 = map 字段**：B 的 `explicitNull()` 在 users 域**只**用于 `extra_info`（`RegisterReq.java:61` · `CreateAdminReq.java:57` · `UpdateUserReq.java:64` · `UpdateSelfReq.java:62`）。<br>② **「空串合法」（限标量字段）**：B 的 `GoStyleRequired.field` **只判 null**（`:32-36`）⇒ **空串合法**（**B 侧只判 null ⇒ `email=""` 被接受**）⇒ 若 C 侧改用 `@NotBlank` ⇒ **比 B 多拒一类合法输入**；用 `@NotNull` 则与 B 等价。<br>**⚠️ 适用范围 = 标量字段**：B 的 `field()` 在 users 域只作用于 `username` / `password` / `email` / `uid` / `invite_code` / `keyword` / `avatar_url` / `history_id`（**全部标量**）⇒ 标量上 `@NotNull` 与 B **等价**（B 本来就拒「缺席」与「显式 null」）⇒ **多拒只发生在 map 字段（①）与空串（②）两处**。<br>⇒ 因此**本条的影响面应为「错误文案 ＋ map 字段的必填判定 ＋ 标量字段的空串合法性」**，而非仅文案。<br>⚠️ **处置口径**：本条**维持「接受降级」不变**（D5 已拍板「逐字复刻成本高于收益」）⇒ 只需把**登记范围写准**，避免后续对拍脚本按「仅文案」的口径漏判这两类差异。<br>📌 证据：B `service/users/users-common/src/main/java/com/rag/users/common/http/GoStyleRequired.java:67-71`（`explicitNull` 三态）· `:32-36`（`field` 只判 null、空串合法）· `GoStyleRequiredFields.java:42-44`（为什么不用反射）· `:13`（**B 侧**判据「Map / Slice / Array 永不计必填」）· 审核记录 `docs/DRIFT/users/verification-users-common-2026-11-02.md` 的 **AUD-01**。 |
| ⚠️ **2026-11-02 · 同日订正（上行 note 自身的表述收窄）** | 上行 note 的两处表述在复审中被判**过宽**，现按 B 源码逐条收窄：<br>① 原写「`@NotNull` 会把**缺席**的字段也一并拒掉 ⇒ 比 B 多拒一类合法输入」—— **该结论只对 map 字段成立**：users 域的标量字段走 `field()`，而 Jackson 对**缺席**的字段不调 setter ⇒ 值留 null ⇒ `field()` 照抛 ⇒ B 本来就拒「缺席」⇒ 标量上 `@NotNull` **不比 B 多拒**；<br>② 原写「**B 侧 map/集合从不参与必填判定**」—— **作为全局断言不成立**：B 的 `like` 域 `GetLikeStateReq.java:46` 对**集合** `target_ids` 调了 `GoStyleRequired.field(...)` ⇒ 「Map / Slice / Array 永不计必填」是 **上游 `core/mapping` 的判据**（B 侧 `GoStyleRequiredFields.java:13` 照抄了它），**不是** B 全域的 Java 侧行为（那是 B 自身的域间不一致，非本条降级项）⇒ 上行 note 已改为**限定 users 域 + 区分标量/map**。 |

### D-02 · 熔断（circuit breaker）的内部策略

| 项 | 内容 |
|---|---|
| **B 侧现状** | B 侧 `common/protection/GoStyleBreaker` = **手写** googlebreaker 移植：滚动窗口 ＋ **概率** dropRatio ＋ force-pass ＋ **无三态**；隔离 key = `method + "://" + path`（`path` 以 `/` 开头 ⇒ **三个斜杠**）；路由模板解析是**三态**（`TEMPLATE` / `NOT_MATCHED` / `UNKNOWN`，见 `GoStyleRouteResolution`）。 |
| **完全 Spring 化后** | resilience4j `CircuitBreaker`。**默认参数与 B 侧不等价**（滑动窗口大小、最小请求数、wait duration、异常类型判定都不同），且**拒绝机制的类型就不同**（B 侧 = 概率性拒绝；resilience4j = 计数窗口 + 三态状态机）。 |
| **为什么降级** | resilience4j 无 B 侧那种「概率 drop + force-pass + 无三态」的语义等价配置；逐项对拍需构造大量故障注入场景。 |
| **影响面** | ⚠️ **这是 4 项里影响面最宽的** —— 熔断行为直接影响"什么请求会被拒"。属**可用性语义**，仍属 L3 而非 L2（不改变业务规则，只改变故障时的拒绝策略）。<br>⚠️ **2026-11-02 批 3 追加（隔离 key 的「路由模板记法」差异）**：B 侧的隔离 key 是 `strings.Join([]string{method, path}, "://")`，`path` 取自**注册期路由模板** ⇒ **B 侧本身也是 Spring ⇒ B 侧的模板记法就是 `{id}` 形态**（`GoStyleBreakerRouteTemplateAutoConfiguration` 从 `RequestMappingHandlerMapping` 取模板）⇒ ⇒ **相对 B 侧，本仓的 `{id}` 记法不构成差异**（`PUT:///article/{id}` 与 B 侧同形）；⚠️ **只有相对「更早基线」的比对**（基线是 `:id` 形态）才看得到记法差异 ⇒ 本条**不再是「相对 B 侧」的降级点**。<br>⚠️ **分隔符是三个斜杠**：B 侧的 `path` 本身以 `/` 开头 ⇒ `method + "://" + "/article/{id}"` = `PUT:///article/{id}` ⇒ **不是笔误**，本仓逐字对齐。 |
| **关联决策** | [P2](决策记录.md#p2--熔断语义) |
| **验收方式** | 必须做**故障注入对拍**（人为制造下游失败 ⇒ 比对"第 N 次请求后开始拒绝"）。⇒ **未做对拍前，不得把 P2 判为 ③ 完成。** |
| ⚠️ **2026-11-02 批次 B 追加（gRPC 侧的机制类型差异 · V09）** | RAG 侧的 gRPC 熔断用的是**手写** googlebreaker 移植（`GoStyleBreaker`：滚动窗口 ＋ **概率** dropRatio ＋ force-pass ＋ **无三态**）；本仓的 gRPC 熔断（`RpcCircuitGateInterceptor` / `ClientCircuitGateInterceptor`）统一用 **resilience4j**（计数窗口 ＋ 打开/半开/关闭三态）⇒ ⇒ **拒绝机制的类型都不同**（概率性拒绝 vs 状态机拒绝）⇒ ⇒ 比本条原登记的「阈值参数不等价」**更重**。<br>⇒ ⇒ 但 **L2 侧的行为契约逐条对齐**：隔离 key（服务端 = gRPC 全方法名；客户端 = `path.Join(target, method)` 的最小折叠）、失败判据（**6 码白名单**，业务错误不参与）、拒绝形状（服务端 `UNAVAILABLE` ＋ `"circuit breaker is open"`；客户端抛**普通异常** ⇒ 调用方映射成 1015 / `service busy`）。<br>⇒ ⇒ **不得反向"修回"**（那会与 D-04/D-02 的生态优先前提冲突）。 |
| ⚠️ **2026-11-02 批次 H 追加（HTTP 侧的机制类型差异 · V09 收口）** | RAG 侧的 **HTTP** 熔断（`GoStyleBreakerFilter`）用的**同样是**手写 googlebreaker 移植（概率 drop ＋ force-pass ＋ 无三态）；本仓的 HTTP 熔断（`ProtectionAutoConfiguration` 内嵌 `RouteIsolationFilter`）用 **resilience4j**（`CircuitBreakerRegistry`，由 resilience4j 的 `CircuitBreakerAutoConfiguration` **自动装配**）⇒ ⇒ **机制类型同样不等价**。<br>⇒ ⇒ **HTTP 侧的有效参数（2026-11-02 实测 · resilience4j 2.2.0）**：滑动窗口 **COUNT_BASED / 100** · 最小请求数 **100** · 失败率阈值 **50%** · open 状态等待 **60s** · 半开放放行 **10** · open→半开自动转换 **关** · 慢调用率阈值 **100%**（时长阈值 1 分钟）⇒ ⇒ **已由 `HttpCircuitBreakerConfigPinTest` 钉桩**（框架默认值一旦变形 ⇒ 测试立刻红 ⇒ 逼着回来重登记本条）。<br>⇒ ⇒ **L2 侧行为契约逐条对齐**：隔离 key（`METHOD://<路由模板>`，**三个斜杠**）· 成败判据（`<500` 成功；**下游 200+业务码不触发**）· 回落语义（`UNKNOWN` ⇒ 回落 raw URI 分桶且**熔断仍生效**；`NOT_MATCHED` ⇒ 本层完全不参与）⇒ ⇒ **漂移只在「拒绝机制类型」这一层**。<br>⇒ ⇒ **刻意不把参数写进本仓自己的配置**：那会**覆盖** resilience4j 的自动配置（域 yml 若有 `resilience4j.circuitbreaker.*` 也会被顶掉）⇒ ⇒ 等于**制造一次未经批准的行为漂移** ⇒ ⇒ 保持「**继承生态默认值 + 钉桩**」才是最小漂移的做法。 |

### D-03 · 链路追踪（span）的名称与属性

| 项 | 内容 |

| **验收方式** | 指标名 / label 的逐条比对（`tools/difftest/` 扩展）；trace 属性可接受差异但需在文档登记。 |

### D-05 · gRPC 边界上「业务码」的承载方式

| 项 | 内容 |
|---|---|
| **B 侧现状** | B 侧 `common` 域各自的 `<域>GrpcError`（如 `service/like/like-common/.../errmsg/LikeGrpcError.java` · `service/comment/comment-common/.../errmsg/CommentGrpcError.java`）：<br>① **gRPC status code 只能是标准码** —— `mapToGrpcCode(bizCode)` 把业务码映射成 `INVALID_ARGUMENT`（仅参数错一类）或 `UNKNOWN`（其余）；<br>② **业务码另找载体** —— 用 **trailer 元数据**承载（**按域各一个名字**：`rag-like-biz-code` / `rag-comment-biz-code` …）；<br>③ **反读** —— `bizCodeFromError(err)` 按「trailer → 进程内 `CodeError` → 标准码反查」三级顺序还原业务码；<br>④ ⚠️ 错误必须交给 `observer.onError(...)` ⇒ 直接 `throw` 会让 grpc-java 把 description 覆盖成 `Application error processing RPC`（**文案当场全丢**）。 |
| **完全 Spring 化后** | grpc-java **承载不了任意数值 status code**：javap 实测 `io.grpc.Status#fromCodeValue(int)` 对未知码**回落 `UNKNOWN`**（数值 2）⇒ ⇒ 业务码**必须另找载体** ⇒ 本仓用 **trailer 元数据** `sea-biz-code`（十进制业务码）承载；客户端拦截器在 `Listener#onClose(status, trailers)` 里把它还原成 `BusinessException`（挂在 status 的 cause 上）。 |
| **为什么降级** | 生态缺口，**不是选择** —— grpc-java 的 `Status` 只认 17 个标准码。 |
| **影响面** | ① **status code 数值**：**B 侧同样是标准码**（`INVALID_ARGUMENT` / `UNKNOWN`(2)）⇒ **相对 B 侧不是差异**；② **trailer 的 key 名不同** —— B 侧**按域各一个**（`rag-<域>-biz-code`），本仓**统一一个** `sea-biz-code` ⇒ ⇒ **相对 B 侧这是可观察差异**（trailer 集合会在 wire 层出现）⇒ 需登记并裁决（见下）。<br>✅ **description 与 B 侧逐字一致**（都只是业务文案，无包装）⇒ 那一半**不是**降级。 |
| **验收方式** | 双侧对拍时：断 **status code 数值**与 **trailer 集合**；**description 逐字比对**。⇒ 对拍脚本须显式排除本项。 |
| **关联决策** | D2 / D5 的「统一错误模型」；与 [P1](决策记录.md#p1--错误文案保真度) 同族（错误表达形态）。 |

### D-06 · Prometheus 指标的**桶布局**与写入面形态

| 项 | 内容 |
|---|---|
| **B 侧现状** | B 侧 gRPC 侧用 **prometheus client 原生 Histogram** 的等价物：`rpc_server_requests_duration_ms`，**显式 12 个桶**（1, 2, 5, 10, 25, 50, 100, 250, 500, 1000, 2000, 5000 ms），label = `method`；外加 Counter `rpc_server_requests_code_total`，label = `method` + `code`。B 侧额外套了一层「**接缝接口 + 静态 holder**」（`GoStylePrometheusSink` / `GoStylePrometheusMetrics` / `GoStylePrometheusMeterRegistryBridge`），因为拦截器链是**静态构造**的 ⇒ 拿不到 Spring 容器 ⇒ 只能靠静态 holder 传递。 |
| **完全 Spring 化后** | Micrometer `DistributionSummary`（`rpc_server_requests_duration_ms`，tag `method`）＋ `Counter`（Meter 名 `rpc_server_requests_code`，tag `method` + `code`）。⚠️ **写入面形态不同**：本仓的拦截器是 `@Bean` ⇒ **构造器注入 `MeterRegistry`** ⇒ **零静态状态、零接缝接口、不需要 destroy 钩子** ⇒ B 侧那套「静态 holder ＋ 每次请求取」的复杂度被生态消化掉。 |
| **为什么降级** | ① **桶布局不等价**：Micrometer 的 `DistributionSummary` 默认是 **summary（分位数）**，没有 B 侧那 12 个显式桶 ⇒ 桶边界须按生态配置（`publishPercentileHistogram`）才能近似；② **指标名**：Micrometer 的 Prometheus 命名约定会给 Counter 自动加 `_total` 后缀 ⇒ Meter 名**不能**叫 `rpc_server_requests_code_total`（会变成 `..._total_total`）⇒ 本仓取 `rpc_server_requests_code` ⇒ 导出后正好是 B 侧的 `rpc_server_requests_code_total`。 |
| **影响面** | **指标名与桶边界**（会出现在 Prometheus 的 exposition 里 ⇒ 仪表盘 / 告警规则要按新名与新桶写）。⚠️ **请求计数 / 状态码计数的语义逐条等价**（成功/失败的判定、panic 不记、被降载/熔断拒绝的请求照样记 —— 三条都逐条对齐 B 侧）。 |
| **关联决策** | D4（生态优先）· 与 [D-03](决策记录.md#d-03--链路追踪span的名称与属性) 同族的「手写采集面 ⇒ 生态承接」。 |
| **验收方式** | 对拍：同一批请求在两侧各跑一次 ⇒ 比对「耗时样本的条数」「状态码计数的 (method, code) 分布」⇒ **桶边界**按已知差异豁免。 |

### D-08 · HTTP 侧降载的**可观察面**（每分钟统计行 + 丢弃时的错误行）缺席
