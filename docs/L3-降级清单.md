# L3 降级清单

> **本文档记录"完全 Spring 化"过程中，被有意放弃的 L3（影响可观察行为的技术语义）。**
> **这些是决策，不是缺陷** —— 不得反向"修回"旧行为；若认为某条必须保真，走 [`决策记录.md`](决策记录.md) 的 P1–P5 重新拍板。

---

## 〇、什么是 L3

| 层 | 内容 | 本仓库的处理 |
|---|---|---|
| **L1** 外部契约 | HTTP 路由 / 方法 / 出入参、gRPC 方法与 proto、错误码取值、状态码 | **全部保留**，一个字节都不改 |
| **L2** 业务语义 | 业务规则、状态转换、鉴权结果、读写含义、副作用与触发条件 | **全部保留** |
| **L3** 技术语义 | 事务边界、错误传播、超时重试降级、幂等、并发控制、序列化、资源生命周期、消息投递 | **保 6 降 4** |
| **L4** 实现机制 | 依赖注入、配置绑定、拦截器、注册与生命周期、文件划分、样板代码 | **全面重选** |

> **降级的判定标准**：降级项**全部落在框架内部行为**上，**没有一项落在业务语义上**。
> 业务语义降级 = 业务行为变了 = 必须重新拍板，不能由"框架更地道"顺带发生。

## 一、降级项（6 项）

### D-01 · 请求体必填校验的错误文案

| 项 | 内容 |
|---|---|
| **Go / RAG 现状** | go-zero `httpx.Parse` 走 `core/mapping`，必填缺失时返回 `400  field "username" is not set`（含字段名）。 |
| **完全 Spring 化后** | Bean Validation（`@NotNull` / `@NotBlank`）⇒ 错误文案由 Hibernate Validator 决定，与 go-zero 不同。 |
| **为什么降级** | 逐字复刻需自定义 `ConstraintValidator` + 维护 go-zero 的文案规则，**成本高于收益**。 |
| **影响面** | 仅错误**文案**。状态码（400）、错误**结构**（text/plain vs JSON）由 `RouterErrorResponses` 独立保证，**不受影响**。 |
| **关联决策** | [P1](决策记录.md#p1--错误文案保真度) |
| **验收方式** | 双侧对拍时**忽略 error body 的文本**，只断言 status code + content-type + 错误结构。⇒ **对拍脚本必须显式排除此项，否则会全红。** |

### D-02 · 熔断（circuit breaker）的内部策略

| 项 | 内容 |
|---|---|
| **Go / RAG 现状** | go-zero `rest` 内置 `Middlewares.Breaker`（`rest/config.go:15`），默认开启。失败判定窗口、half-open 探测策略、错误率阈值由 go-zero 定义。 |
| **完全 Spring 化后** | resilience4j `CircuitBreaker`。**默认参数与 go-zero 不等价**（滑动窗口大小、最小请求数、wait duration、异常类型判定都不同）。 |
| **为什么降级** | resilience4j 无 go-zero 语义等价配置；逐项对拍需构造大量故障注入场景。 |
| **影响面** | ⚠️ **这是 4 项里影响面最宽的** —— 熔断行为直接影响"什么请求会被拒"。属**可用性语义**，仍属 L3 而非 L2（不改变业务规则，只改变故障时的拒绝策略）。<br>⚠️ **2026-11-02 批 3 追加（隔离 key 的「路由模板记法」差异）**：Go 的隔离 key 是 `strings.Join([]string{method, path}, "://")`（`rest/handler/breakerhandler.go:18-19`），而 `path` 取自 `rest/engine.go:149` 的 `route.Path` ⇒ Go 侧是 goctl 生成的 **`/article/:id`**（path-to-regexp 风格）；Spring 侧的路由模板是 **`/article/{id}`** ⇒ ⇒ **隔离 key 的字符串形态两侧不同**（如 `PUT:///article/:id` vs `PUT:///article/{id}`）⇒ ⇒ 该 key 会出现在熔断器名 / 指标标签上 ⇒ 属可观察差异。<br>⚠️ **分隔符是三个斜杠**：Go 的 `path` 本身以 `/` 开头 ⇒ `method + "://" + "/article/:id"` = `PUT:///article/:id` ⇒ **不是笔误**，本仓逐字对齐。 |
| **关联决策** | [P2](决策记录.md#p2--熔断语义) |
| **验收方式** | 必须做**故障注入对拍**（人为制造下游失败 ⇒ 比对"第 N 次请求后开始拒绝"）。⇒ **未做对拍前，不得把 P2 判为 ③ 完成。** |
| ⚠️ **2026-11-02 批次 B 追加（gRPC 侧的机制类型差异 · V09）** | RAG 侧的 gRPC 熔断用的是**手写** googlebreaker 移植（`GoStyleBreaker`：滚动窗口 ＋ **概率** dropRatio ＋ force-pass ＋ **无三态**）；本仓的 gRPC 熔断（`RpcCircuitGateInterceptor` / `ClientCircuitGateInterceptor`）统一用 **resilience4j**（计数窗口 ＋ 打开/半开/关闭三态）⇒ ⇒ **拒绝机制的类型都不同**（概率性拒绝 vs 状态机拒绝）⇒ ⇒ 比本条原登记的「阈值参数不等价」**更重**。<br>⇒ ⇒ 但 **L2 侧的行为契约逐条对齐**：隔离 key（服务端 = gRPC 全方法名；客户端 = `path.Join(target, method)` 的最小折叠）、失败判据（**6 码白名单**，业务错误不参与）、拒绝形状（服务端 `UNAVAILABLE` ＋ `"circuit breaker is open"`；客户端抛**普通异常** ⇒ 调用方映射成 1015 / `service busy`）。<br>⇒ ⇒ **不得反向"修回"**（那会与 D-04/D-02 的生态优先前提冲突）。 |

### D-03 · 链路追踪（span）的名称与属性

| 项 | 内容 |
|---|---|
| **Go / RAG 现状** | go-zero `zrpc` 提供的 Trace / Recover / Stat / Prometheus / Breaker / Shedding 中间件链，`observability` 包定义 span 名称与属性；`sea.slow` 等标记是业务约定。 |
| **完全 Spring 化后** | Micrometer Observation + OpenTelemetry bridge。span 名称、属性 key、慢调用标记的生成方式不同。 |
| **为什么降级** | Micrometer 的观察模型与 go-zero 的中间件链不是一对一映射。 |
| **影响面** | 观测数据（trace / metrics 的 label）—— **不影响业务响应**。但 `sea.slow` 这类**业务定义的标记**必须保留（见下）。<br>⚠️ **2026-11-02 批 3 追加（Micrometer 侧的属性类型退化）**：Micrometer 的 `io.micrometer.common.KeyValue` **只有 String 值的工厂**（javap 实测：`KeyValue.of(String, String)` 是唯一的 String 键工厂，**没有** `of(String, boolean)`）⇒ ⇒ `sea.error` / `sea.timeout` / `sea.slow`（Go 侧是 boolean）在 Observation 侧**退化为字符串 `"true"`**；`sea.biz_code`（Go long）/ `sea.duration_ms`（Go double）同样退化为字符串 ⇒ ⇒ **属性类型变了（值不变）** ⇒ ⇒ 告警 / 看板的查询表达式要跟着改。<br>⇒ ⇒ **缓解**：共享层同时写 **OTel span（带类型）** ＋ **Micrometer Observation**（双载体）⇒ ⇒ OTel 侧的属性类型**逐字保住** ⇒ ⇒ 退化只发生在 Micrometer 侧。<br>⚠️ **待办**：`micrometer-tracing-bridge-otel` 1.5.9（Boot 3.5.11 管理版）**当前离线仓不可得** ⇒ OTel 侧现在**没有真正的 span**（`Span.current()` 是 no-op ⇒ 写入被丢弃）⇒ ⇒ 恢复联网后应补 bridge，并**撤掉**共享层的 OTel 直写（否则 bridge 会把同名属性覆盖成字符串）。 |
| **保留项（不降级）** | ① 指标名与标签（如 `message_api_request_total{route,result}`）是**业务定义**，逐字保留；② 慢调用阈值与标记语义保留。 |
| **验收方式** | 指标名 / label 的逐条比对（`tools/difftest/` 扩展）；trace 属性可接受差异但需在文档登记。 |

### D-04 · CPU 降载（adaptive shedding）的实现路径

| 项 | 内容 |
|---|---|
| **Go / RAG 现状** | go-zero `rest` 内置 `CpuThreshold`（`rest/config.go:56`，默认 900‰ = 90% CPU），读整机 CPU（Linux `/proc/stat`）。 |
| **完全 Spring 化后** | resilience4j **无等价能力** ⇒ 保留 1 个自研 `CpuThresholdHealthIndicator`（读 CPU + 暴露健康状态），由 Spring Boot Actuator 的健康检查与一个 Filter 消费。 |
| **为什么降级** | 生态缺口，**不是选择** —— 不自研就没有这个能力。 |
| **影响面** | 超阈值时的**拒绝响应形状**（裸状态码 + 空 body + 无 Content-Type）必须保留。<br>⚠️ **2026-11-02 批 3 追加（本仓只实现了「CPU 一半」判据）**：Go 的 adaptive shedder 是「**CPU 过载** + **在途请求数超动态上限**」**两个条件同时成立**才丢请求（`core/load/adaptiveshedder.go`）⇒ 生态**无**「在途超动态上限」的等价物 ⇒ ⇒ 本仓的 `CpuThresholdHealthIndicator` + 降载 Filter **只有 CPU 这一个条件** ⇒ ⇒ **比 Go 更激进**（可能在 Go 不会丢请求的时刻丢）⇒ ⇒ 属 L3，**不得反向"修回"**（那会把「已知缺口」变成「静默行为漂移」）。 |
| **关联决策** | 与 [P2](决策记录.md#p2--熔断语义) 同批落地。 |
| ⚠️ **2026-11-02 批次 B 订正（gRPC 侧已闭合，REST 侧仍缺）** | 上面的「只实现 CPU 一半」是 **REST（HTTP）侧**的情况 ⇒ 至今仍缺；⇒ **gRPC 侧**在批次 B 里**整段抄了 RAG 的 `GoStyleAdaptiveShedder`**（`common/protection/AdaptiveShedder.java`）⇒ ⇒ **双条件判据（CPU 过载 **且** 在途超动态上限）在 gRPC 侧已完整落地** ⇒ ⇒ 本条的缺口**收窄为「仅 HTTP 侧」**。<br>⇒ ⇒ 守门：`RpcProtectionLayerTest#sheddingRequiresBothCpuAndInFlight`（断言「只有 CPU 过载、**没有在途** ⇒ **不**降载」）|
| **验收方式** | 人为压高 CPU ⇒ 比对拒绝行为与响应形状。 |

### D-05 · gRPC 边界上「业务码」的承载方式

| 项 | 内容 |
|---|---|
| **Go 现状** | `service/<域>/common/errmsg/errmsg.go:33-35`：`func NewGrpcErr(code int, msg string) error { return status.Error(codes.Code(code), msg) }` ⇒ **gRPC status code 就是 SEA 业务码**（如 1001 / 5001），**description 就是业务文案**。调用侧 `service/<域>/api/internal/logic/*.go` 用 `errmsg.NewErrCodeMsg(int(st.Code()), st.Message())` **反读**回去。 |
| **完全 Spring 化后** | grpc-java **承载不了任意数值 status code**：javap 实测 `io.grpc.Status#fromCodeValue(int)` 对未知码**回落 `UNKNOWN`**（数值 2）⇒ ⇒ 业务码**必须另找载体** ⇒ 本仓用 **trailer 元数据** `sea-biz-code`（十进制业务码）承载；客户端拦截器在 `Listener#onClose(status, trailers)` 里把它还原成 `BusinessException`（挂在 status 的 cause 上）。 |
| **为什么降级** | 生态缺口，**不是选择** —— grpc-java 的 `Status` 只认 17 个标准码。 |
| **影响面** | ① **status code 数值**：Go = 业务码（如 1001）· 本仓 = `UNKNOWN`(2)；② **多一个 trailer**（`sea-biz-code`）—— Go 侧没有。<br>✅ **description 与 Go 逐字一致**（都只是业务文案，无包装）⇒ 那一半**不是**降级。 |
| **关联决策** | D2 / D5 的「统一错误模型」；与 [P1](决策记录.md#p1--错误文案保真度) 同族（错误表达形态）。 |
| **验收方式** | 双侧对拍时：断 **status code 数值**与 **trailer 集合**；**description 逐字比对**。⇒ 对拍脚本须显式排除本项。 |

### D-06 · Prometheus 指标的**桶布局**与写入面形态

| 项 | 内容 |
|---|---|
| **Go / RAG 现状** | Go 的 `zrpc/internal/serverinterceptors/prometheusinterceptor.go` 用 **prometheus client 原生 Histogram**：`rpc_server_requests_duration_ms`，**显式 12 个桶**（1, 2, 5, 10, 25, 50, 100, 250, 500, 1000, 2000, 5000 ms），label = `method`；外加 Counter `rpc_server_requests_code_total`，label = `method` + `code`。RAG 侧额外套了一层「**接缝接口 + 静态 holder**」（`GoStylePrometheusSink` / `GoStylePrometheusMetrics` / `GoStylePrometheusMeterRegistryBridge`），因为拦截器链是**静态构造**的 ⇒ 拿不到 Spring 容器 ⇒ 只能靠静态 holder 传递。 |
| **完全 Spring 化后** | Micrometer `DistributionSummary`（`rpc_server_requests_duration_ms`，tag `method`）＋ `Counter`（Meter 名 `rpc_server_requests_code`，tag `method` + `code`）。⚠️ **写入面形态不同**：本仓的拦截器是 `@Bean` ⇒ **构造器注入 `MeterRegistry`** ⇒ **零静态状态、零接缝接口、不需要 destroy 钩子** ⇒ RAG 那套「静态 holder ＋ 每次请求取」的复杂度被生态消化掉。 |
| **为什么降级** | ① **桶布局不等价**：Micrometer 的 `DistributionSummary` 默认是 **summary（分位数）**，没有 Go 那 12 个显式桶 ⇒ 桶边界须按生态配置（`publishPercentileHistogram`）才能近似；② **指标名**：Micrometer 的 Prometheus 命名约定会给 Counter 自动加 `_total` 后缀 ⇒ Meter 名**不能**叫 `rpc_server_requests_code_total`（会变成 `..._total_total`）⇒ 本仓取 `rpc_server_requests_code` ⇒ 导出后正好是 Go 侧的 `rpc_server_requests_code_total`。 |
| **影响面** | **指标名与桶边界**（会出现在 Prometheus 的 exposition 里 ⇒ 仪表盘 / 告警规则要按新名与新桶写）。⚠️ **请求计数 / 状态码计数的语义逐条等价**（成功/失败的判定、panic 不记、被降载/熔断拒绝的请求照样记 —— 三条都逐条对齐 Go）。 |
| **关联决策** | D4（生态优先）· 与 [D-03](决策记录.md#d-03--链路追踪span的名称与属性) 同族的「手写采集面 ⇒ 生态承接」。 |
| **验收方式** | 对拍：同一批请求在两侧各跑一次 ⇒ 比对「耗时样本的条数」「状态码计数的 (method, code) 分布」⇒ **桶边界**按已知差异豁免。 |

## 二、保留项（6 项，明确不降级）

> 这些是 L3，但**有对应的 Spring/Jackson 机制或语义等价物**，必须逐条保住。

| # | L3 语义 | 承载方式 | 注意 |
|---|---|---|---|
| K-01 | 请求体类型强转判定（数字/布尔不进 String 字段、浮点不进整数字段） | **Jackson 原生 `CoercionConfig`**（`CoercionAction.Fail` / `ACCEPT_FLOAT_AS_INT` off） | RAG 早已在用（`GoStyleCoercion`），**这不是自研** —— 已归位到 `common/web/` |
| K-02 | "何时才读请求体"判据（`ContentLength > 0` 且 Content-Type **字面**含 `application/json`） | 自定义 `HttpMessageConverter.canRead` | ⚠️ **字面子串匹配**，不是媒体类型兼容判定 ⇒ `application/vnd.api+json` 在 Go 侧**不**匹配 ⇒ body 被丢弃。这条必须逐字复刻 |
| K-03 | 超时取消在途 IO（`context.WithTimeout` 的 ctx-aware 取消） | `DeadlineState` + `setQueryTimeout`（pgjdbc CancelRequest） | ⚠️ Java 的 `Future.cancel(true)` 对阻塞 IO **无效** ⇒ 必须走服务端取消语义。RAG 已实测坐实 |
| K-04 | 日志输出格式（含 `call_chain` 字段等） | **实现 SLF4J `Logger` 的适配器** | 格式是行为契约；接入 SLF4J 生态不改变输出 |
| K-05 | 事务边界 / 行级悲观锁 / 幂等键 / 游标编码 | 逐条保留 | 这些是业务语义，不是框架机制 |
| K-06 | `ApiResponse` 信封形状（`{code,msg,data}`） | `common/contract/ApiResponse` | ⚠️ **不可用 `ProblemDetail` 替换** —— 客户端按此解析，属 L1。`ProblemDetail` 只能用于内部异常表达 |

## 三、变更登记规则

| 规则 | 说明 |
|---|---|
| **降级项不得反向修回** | 一旦拍板降级，后续实现**不得**"顺手"恢复旧文案 / 旧策略。要恢复 ⇒ 走 P1–P5 重新拍板并更新本文档。 |
| **降级项不得静默扩大** | 新增降级必须写进本文档，**不能只写进代码注释**。 |
| **对拍脚本必须显式排除降级项** | 否则双侧对拍会因文案差异全红 ⇒ 红了会被误判为"回归" ⇒ 触发"修回旧行为" ⇒ **降级被静默撤销**。⚠️ 这是最容易出问题的一环。 |
| **降级项与有意偏离分开记** | 降级 = 主动放弃 L3；有意偏离 = 两侧确实不同且已签字。本文档属前者，`docs/Intentional_Deviations/` 属后者。 |
