### 1.3 `Event` 与 `TechnicalReceipt` 的字段（L1，逐字 · **B 侧形态**）

```java
// B 侧 service/common/src/main/java/com/rag/common/communityfact/Wire.java
public static final class Event {
    @JsonProperty("event_id")          public String eventId;
    @JsonProperty("event_type")        public String eventType;
    @JsonProperty("schema_version")    public int    schemaVersion;
    @JsonProperty("producer")          public String producer;
    @JsonProperty("aggregate_id")      public String aggregateId;
    @JsonProperty("aggregate_version") public long   aggregateVersion;
    @JsonProperty("operation_id")      public String operationId;
    @JsonProperty("occurred_at")       public String occurredAt;
    @JsonProperty("payload")           public Object payload;   // ⚠️ 延迟反序列化

public static final class TechnicalReceipt {
    @JsonProperty("event_id")         public String eventId;
    @JsonProperty("producer")          public String producer;
    @JsonProperty("technical_status")  public String technicalStatus;
```

⚠️ **`payload` 是 `Object`** ⇒ 延迟反序列化 ⇒ 生产者域拥有 payload 语义，协议层只搬运。
⚠️ **`SchemaVersion` + `AggregateVersion` + `OperationID`** ⇒ 这是一套**事件溯源 + 幂等**协议，不是普通消息队列。

### 1.4 ⚠️ 最危险的一处：canonical JSON 哈希

```java
// B 侧 service/common/.../communityfact/Wire.java
public static String canonicalHash(byte[] raw)   // 用 org.everit.json.schema? 否 ——
// B 侧实际依赖：com.github.erosb:java-json-canonicalization（RFC 8785 JCS），版本 1.1（根 pom 的
// java-json-canonicalization.version 管）
```

⇒ **Spring 自带生态没有等价物**（Jackson 的 `MapperFeature.SORT_PROPERTIES_ALPHABETICALLY` **不等价** ——
JCS 还规定了数字规范化（`1.0` vs `1`）、字符串转义（`/` 不转义）、UTF-16 码元顺序等），
⇒ **但 B 侧已经把它解决了**：B 侧引了 **`java-json-canonicalization` 1.1** 这条 RFC 8785 实现，
并配了 `JcsDifferentialTest` 做差分守门。

⇒ **落地**：本仓**直接引 B 侧同款坐标**（`java-json-canonicalization` 1.1）+ 新增
`common/communityfact/CanonicalHash.java`（B 侧的形态是把该逻辑放在 `Wire.java` 内 ⇒ 本仓**拆成独立类**，
与其余 12 个 wire 类对齐）。
⇒ ⚠️ **G-2 的「生态无等价物」结论因此需要修订**：不是"生态无等价物"，而是"**生态外的专用库**" ⇒ **B 侧已给出答案，照抄即可**。

### 2.3 ⚠️ 缺陷 1：`like-rpc_action_total` 用了连字符

更早基线源码：
```go
LikeActionCount = prometheus.NewCounterVec(prometheus.CounterOpts{
    Namespace: "",
    Subsystem: "like-rpc",          // ← 全仓唯一用连字符的
    Name:      "action_total",
}, []string{"target_type", "action", "result"})
```

⚠️ **Prometheus 指标名正则 `[a-zA-Z_:][a-zA-Z0-9_:]*` 不允许连字符** ⇒ 该指标**不会出现在 `/metrics` 里**。

⚠️ **B 侧的实际渲染形态（2026-11-02 实测）**：B 侧 `LikeRpcMetrics` 用 Micrometer 落名
**`like_rpc_action_total`**（下划线）⇒ **B 侧在 Java 侧已把连字符形态消化掉了**
（Micrometer 的 `Counter.builder("like_rpc_action_total")`）。

⇒ **决策（按 B 侧为基准修订）**：本仓**照抄 B 侧** ⇒ 落名 **`like_rpc_action_total`**（下划线），
**不再**复刻「连字符 ⇒ 指标不出现」的那个形态。
⇒ ⚠️ **连带影响**：B 侧与更早基线在这一项上**存在可观察差异**（B 侧多出一个能出现的指标）⇒
该差异是**B 侧既有事实**，本仓照抄 ⇒ 若要「修回」只能走签字偏离流程，**不得顺手改**。

### 2.4 ⚠️ 缺陷 2：`high_risk_action_logal` 拼写错误

更早基线源码：`Name: "high_risk_action_logal"`（应为 `log` / `audit`）。

⚠️ **B 侧的实际渲染形态（2026-11-02 实测）**：B 侧 `AdminRpcPrometheusCarrierGateTest` 记录了
**`admin_rpc_high_risk_action_logal_total`** —— **拼写错误照抄保留**，
但 Micrometer 给 Counter **强制追加 `_total`** ⇒ 与更早基线的 `admin_rpc_high_risk_action_logal` 差一个后缀。

⇒ **决策：照抄 B 侧，不修正。** 指标名是**监控看板的依赖项** ⇒ 改 spelling 会让既有看板断裂。
⇒ 登记为已知缺陷。

## 五、T-5 · 翻案：task 域**有** `UserLikeCount`

> **盘点要按导出符号，不能按目录。**

## 七、本轮的第二个教训：**"生态无等价物"清单要单列**

第一轮深挖发现 1 处（CPU 降载），本轮发现第 2 处（canonical JSON / RFC 8785 JCS）。

⇒ 两处都是**必须自研且必须逐字对拍**的点，且都**不是业务语义**（一个在熔断、一个在幂等指纹）。
⇒ 建议在 `docs/L3-降级清单.md` 旁边新增一档：**「生态无等价物清单」**（待办）。

| # | 能力 | 生态现状 | 替代方案 | 风险 |
