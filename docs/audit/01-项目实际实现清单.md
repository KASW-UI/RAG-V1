## 0. 一句话结论

RAG-V1 不是「八股展示柜」，而是一个**行为等价迁移项目**：它把 Go 版识海社区后端（10 个业务域）逐类抄写成 Spring Boot 3.5 形态。
真实落地了 **PostgreSQL + MyBatis-Plus + Kafka + Redis + gRPC + Nacos + MinIO + Resilience4j + OpenTelemetry** 九条真实技术线；
**没有引入任何与业务无关的技术**（无 ES、无 Milvus、无 Neo4j、无 Dubbo、无 RocketMQ/RabbitMQ、无 Netty 业务层、无 Elasticsearch）。
真正的问题不在「技术太少」，而在 **① 三处「只写不投」的机制、② 一处假成功、③ 三处默认不可用/不可达、④ 一批生产死代码与死配置**。

## 3. 核心业务能力清单（按域）

> 口径：**真实实现** = 有完整业务链路且有对应测试；**占位** = 代码存在但语义不成立。

### 3.1 article（内容域）

- HTTP 7 端点（`/v1/article` CRUD、`/v1/me/article/{id}`、`/v1/articles`、`/v1/upload`）+ gRPC 6 方法 + Kafka 生产 2 / 消费 2。
- 存储：5 张表（`article`、`article_sync_outbox`、`article_revision`、`article_publication`、`article_domain_outbox`），含 **DB 层不可变触发器** `article_revision_immutable`（`V10__create_article_sync_outbox.sql` 对应的 `V10__create_article_community_revision.sql:60-70`）。
- 机制：悲观锁 `SELECT ... FOR UPDATE`（`ArticleMapper.java:237`）、`revision` 版本号 + `pointer_version` 发布指针、outbox 中继（`ArticleSyncOutboxRelay.java:178`）。
- ⚠️ **占位/失效**：
  1. `ContentAuditPort` 唯一实现是 `client/UnavailableContentAuditClient.java:71-113`（必抛）⇒ **默认部署下文章永远卡在 REVIEWING**。
  2. `article_domain_outbox` **只写不投**（`ArticleAtomicService.java:615-622` 写入；`ArticleDomainOutboxMapper.selectPending` 全仓无调用方）⇒ 行只增不减。
  3. `CommunityArticleEvent` **无 topic、无 relay、无消费者** ⇒ 域事件出口是死路。
  4. 消费者日志写 "will retry"（`ArticleReviewConsumer.java:277,421`；`ArticleSyncResultConsumer.java:265`），而 error handler 是 `FixedBackOff(0L,0L)`（`ArticleServiceApplication.java:185`）⇒ **零重试、失败即丢弃** ⇒ 日志与行为相反。
  5. `POST /v1/upload` 不在 `ArticleJwtAuthFilter.PROTECTED_ROUTES`（`:170-174`）⇒ **匿名可上传**。
  6. gRPC `ListArticles` 未 clamp `page_size`（`ArticleDomainService.java:811-812`）⇒ HTTP 面之外的深分页暴露面。

### 3.2 comment（评论域）

- HTTP + gRPC 覆盖评论 CRUD、点赞评论、举报、管理（软删/恢复/禁言）、主题信息（`UpdateSubjectState`）。
- Kafka：`comment-audit-topic` 生产（`CommentAuditPublisher.java:104`）+ 消费（`CommentAuditListener.java:133`），**失败不提交位点 ⇒ 重投**（刻意不同于 like 域，见 `service/comment/.../CommentServiceApplication.java:129-144`）。
- 事实投递：`comment_domain_fact_outbox` + `comment_fact_stream`，`FOR UPDATE SKIP LOCKED` 抢占（`CommentDomainFactOutboxMapper.java:119`）+ 部分索引 + `NOT VALID` CHECK 三件套齐全（`V6__create_comment_domain_fact_outbox.sql`）。
- Redis：`CommentCacheService` —— ★ **全仓唯一有完整缓存语义的域**：读缓存 → singleflight（并发 miss 只回源一次）→ 回源 DB → 回填；4 个差异化 TTL（5min/3min/10min/24h，`CommentCacheService.java:98-110`）；缓存故障时**分两档降级**（`:51-57`：有的继续回源 DB、有的直接报错不回源，防打爆 DB）。
- 敏感词过滤：`CommentSensitiveFilter`；权限：`CommentAuthorityLookupService` + `CommentAuthorityEndpointConfig`。

### 3.3 favorite（收藏域）

- 文件夹（增删改查）+ 收藏项（增删查）双层模型，7 张迁移脚本（V1..V7，含 3 次「对齐 B 侧」的 schema 修订）。
- 幂等：唯一索引 + `ON CONFLICT DO NOTHING`（`FavoriteFolderMapper.java:14-22` 等）。
- 事实投递：`favorite_fact_outbox` + `FavoriteFactDispatchService` + `FavoriteFactDispatchScheduler`；遗留事实预检 `FavoriteLegacyPreflightService` + `FavoriteLegacyFactMarker`。

### 3.4 like（点赞域）

- 状态机 + 计数 + 列表 + 作者维度查询；`like_record` 唯一索引 `uk_user_target(user_id,target_type,target_id)`。
- **Kafka 三面**：`LikeUpdateKafkaListener`（消费）+ `LikeTaskProgressPublisher` + `LikeHotEventOutboxRelay`（生产/中继）；topic `like_promotion_topic` 生产消费同 topic（yml `:355` 自述与 B 侧一致，非笔误）。
- 消费幂等：`like_consume_inbox` 表 + `msg_id` 主键冲突 + `ON CONFLICT DO NOTHING`（`LikeMessageIngestService.java:185`）。

### 3.5 follow（关注/拉黑域）

- 8 HTTP + 8 gRPC：关注/取关/拉黑/解黑/关注列表/粉丝列表/黑名单/推荐。
- 幂等靠**唯一索引 + `ON CONFLICT DO NOTHING`**（`FollowRelationMapper.java:14-22`），无锁、无版本列。
- 拉黑是唯一事务：`FollowBlockTransactionService.java:22-29`（插 block + 双向删 follow）。
- 推荐是**真算法**（多层 BFS + 权重打分，`FollowRecommendationService.java:47-131`），非占位。
- ⚠️ `follow` 前置黑名单检查与后续 INSERT 不在同一事务 ⇒ check-then-act 竞态（继承 B 侧）。
- 列表只返回 id 列表，不做 profile 富化。

### 3.6 hot（热榜域）

- **零 DB**（`db/migration/` 只有 `.gitkeep`，pom 无 MP/PG）⇒ 与 B 侧「hot 不碰 DB」一致。
- 核心存储 = Redis ZSET：`hot:articles`（查询唯一来源）、`hot:articles:p{n}`（分片）、`hot:articles:shadow`（影子键）。
- 算法：**HeavyKeeper**（`domain/model/HeavyKeeper.java`）+ `ReentrantLock`/`ReentrantReadWriteLock`。
- 一致性：写侧全部「影子键 + Lua `RENAME` 原子换名」⇒ 读者永不看到半份数据。
- 分布式锁：`SETNX` + TTL 10s + 看门狗 Lua 续期（`HotMergeScheduler.java:201-255`）。
- Kafka：只消费 `article-hot-events`（生产方在 like 域）+ `ConsumerRebalanceListener` 在重平衡时从 Redis 载入/flush。
- ⚠️ **4 个 gRPC 方法占位**：like/coin/share 抛 `UNIMPLEMENTED`（`InteractionStubService.java:60-72`），**comment 直接 `setSuccess(true)` 假成功**（`InteractionStubService.java:82-84`）—— 全仓最刺眼的一处。
- ⚠️ **消费者无幂等**（`HotEventConsumer.java:229` `hk.add` 无去重键，payload 只有 2 个字段无 event_id）⇒ 重复投递放大热度。
- ⚠️ **过度设计**：64 线程池 + 64 队列 + CallerRuns（`HotHydrationExecutorConfiguration.java:101-107`）之上再叠 `Semaphore(8)`（`HotApiService.java:124,307`）⇒ 池参数基本无效。

### 3.7 message（私信/通知域）

- 用户端 8 端点 + 管理端 5 端点 + gRPC 10 方法。
- 三表模型：`message_notification` / `message_conversation` / `message_conversation_message`；会话对唯一索引 `uk_conversation_pair`（V4 由唯一约束改唯一索引以对齐 GORM）。
- 已读 = 条件 UPDATE（`WHERE ... AND is_read=FALSE`）⇒ 天然幂等；未读数 = **每次实时 `COUNT(*)`**（非物化字段）。
- 事务边界集中在独立 Bean `MessageAtomicService`（避免 self-invocation 让 `@Transactional` 静默失效）。
- ⚠️ **无实时通道**：全量 grep `WebSocket|SseEmitter|stomp` 零命中 ⇒ 靠客户端轮询 `GET /message/v1/unread`。
- ⚠️ 无悲观锁/无乐观锁/无隔离级别 ⇒ 未读总数与逐会话未读之和是两次独立查询，非同一事务。

### 3.8 task（任务中心域）

- HTTP 仅 1 端点 + gRPC 仅 1 方法；真正能力在异步链路。
- Kafka **8 listener / 5 topic**（`TaskKafkaTopics.java:8-30`）：raw 日志 → 分流 → 计数 → 进度 sink → 奖励流。
- Redis：进度缓存（Hash）、初始化/完成幂等标记（SETNX + TTL 90d）、`INCR` 计数（**无 TTL**）、Redis Stream 奖励事件。
- PG 落库：`ON CONFLICT + GREATEST` 批量 upsert（`TaskProgressMapper.java:35-41`）⇒ 只增不减、done 不可回退、`done_at` 不可变。
- ⚠️ **无鉴权**：`service/task/.../config/WebMvcConfig.java:12-13` 拦截器为空，uid 取自请求体（yml `:458-467` 明写「按原样保留，补鉴权属新增行为」）。
- ⚠️ **无 DLQ / 无 `@RetryableTopic` / 无 `@DltHandler`**（全仓 grep 零命中）。

### 3.9 users/user + users/admin

- user 9 端点（注册/登录/注销/查/改/删 + 头像三件套），admin 13 端点（登录/创建/注销/自助三件套 + 管理用户六项 + 邀请码）。
- 认证：自研 Filter + Interceptor（**不用 Spring Security**；只用 `spring-security-crypto` 的 BCrypt）。
- claims 只有 `userId`，**没有 `status`**（封禁靠每次查库）。
- Redis 只做一件事：**JWT 黑名单**（`user:jwt_blacklist:<token>` / `admin:jwt_blacklist:<token>`，TTL=30d），且 **fail-open**。
- DDL 幂等重放（**不用 Flyway**，D17）：`service/users/common/src/main/resources/db/01..04_*.sql`。
- ⚠️ 默认管理员硬编码 `admin/admin`（`AdminDomainService.java:154,164` + `AdminSeederBootstrap.java:146`）。
- ⚠️ `users_user_avatar_history` **无 FK** ⇒ 删用户留孤儿行，而 `UserDomainService.java:535` 自述依赖 FK CASCADE。
