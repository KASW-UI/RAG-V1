## 1.4 ★ 鉴权改造方案：引入 Spring Security 角色体系

> **状态**：2026-11-27 用户拍板 —— 计划书内写明方案与改造路径。
> **背景问题**：当前是**自研 JWT 栈，且 9 个域各写一遍**（article 2 类 · user 4 · admin 3 · message 3 · comment 1 · favorite 1 · follow 2 · like 1），共享层只有 3 个类 / 322 行（`common/security/`：`BearerTokenExtractor` 105 + `JwtUtil` 111 + `PasswordUtil` 106），依赖面只有 `spring-security-crypto`（为了 BCrypt，`common/pom.xml:82-88`）。⇒ **重复才是真正的债**，「没用框架」不是。
> **同时它也是一个机会**：**目前没有角色/权限模型**（只有 `userId` claim，授权全靠服务层手写作者校验）⇒ 引入 Spring Security 时**顺手把角色体系补上**，这是本项目当前最大的能力缺口之一。

### 1.4.1 目标（三个都要同时满足）

| 目标 | 具体要求 |
|---|---|
| ① 用标准框架 | HTTP 侧的**认证与授权**由 Spring Security 承载（`SecurityFilterChain` + `AuthenticationProvider` + 方法级授权） |
| ② 补上角色体系 | 引入 **角色**（`ROLE_USER` / `ROLE_ADMIN`）与**基于角色的授权**，替换「只能手写作者校验」的现状 |
| ③ ★ wire 契约一字不变 | 401 空 body / 200+业务码 1006 / 413 压过 401 / 业务失败恒 200+信封 —— 全部逐字保持 |

### 1.4.2 角色模型（**最小可解释**，且不新增表）

| 角色 | 来源 | 典型授权点 |
|---|---|---|
| `ROLE_USER` | `users_user` 表存在该 uid | 点赞/收藏/关注/评论/发私信/改自己的文章 |
| `ROLE_ADMIN` | `admin_admin` 表存在该 uid | `/admin/v1/**` 管理端全部端点 |

> ⚠️ **不引入新角色表** —— 现状是「`users_user` 与 `admin_admin` **两张独立表 + 两个独立 JWT secret**」⇒ 角色由**表归属**推导，不是可配置的数据 ⇒ 新增角色表 = 新增 L1 变更 + 新增迁移，收益不抵成本。
> ⇒ 角色解析 = 一次「查两张表看命中哪张」 ⇒ 落成一个共享 bean（`AuthorityResolver`）。

### 1.4.3 ★ 令牌形态：**不变**（这是保住 L1 的关键）

| 项 | 决策 | 理由 |
|---|---|---|
| 签发 | 继续用 jjwt **HS256**，claims **仍只有 `userId`**（+ `iat`/`exp`） | claims 是 L1 wire；加 `role` claim ⇒ 令牌形态变更 ⇒ **另开决策，本轮不做** |
| 角色来源 | **不写进 token**；由 `AuthenticationProvider` 验签后**查库**解析 | ① 旧 token 继续可用 ② 各域验签逻辑与 B 侧一致 ③ 代价是每请求一次查询 —— 但项目现状本来就每请求查 `status` ⇒ **合并为同一次查询**，不加额外往返 |
| secret | 用户链用 `USER_JWT_SECRET`，管理链用 `ADMIN_JWT_SECRET`（**两个链，两个 secret**） | 保持现状不变 |

### 1.4.4 组件与接线（Spring Security 6.5.x）

**依赖**：`org.springframework.boot:spring-boot-starter-security`（`BCryptPasswordEncoder` 保持不变 —— crypto 由 starter 传递带入；★ **`common/pom.xml:87-89` 的 `spring-security-crypto` 显式声明保留不动**，实际生效版本本来就是 6.5.8，与 starter 传递带入的版本一致 ⇒ 无冲突、无需改 `common/pom.xml`）。
⚠️ **落位**：`starter-security` **不能加在 `common/`**（`common/` 属无域归属共享层，加了等于给 10 个 app 全量引入 servlet 安全栈 ⇒ 违反 AGENTS §2.3 R1）⇒ **加在 5 个新 boot 模块**（或各域模块内），`common/` 只保留 `spring-security-crypto` 现状不动。

### 1.4.5 ★ 授权：**不要直接用 `@PreAuthorize` 判权**（坑）

- Spring Security 的默认授权失败 = **403 + 空 body**；但本项目 wire 要求「**业务失败恒 200 + 信封**」⇒ 直接用 `@PreAuthorize("hasRole('ADMIN')")` 会**漏出裸 403** ⇒ **wire 漂移**。
- ⇒ **正确做法（两选一）**：
  - **方案甲（★ 建议，本轮采用）**：**只把「认证」交给 Spring Security**（产出带 authorities 的 `Authentication`），**授权仍在服务层做**（现状的手写作者校验）⇒ 但把判定**改成基于角色/权限**（读 `Authentication.getAuthorities()` 而不是手写 uid 比较）⇒ **wire 完全不变，改动面最小**。
  - **方案乙（可选增强）**：`@PreAuthorize("@bizAuth.canEditArticle(#id, authentication)")` —— **自定义 SpEL bean 抛业务异常**（`BusinessException`）⇒ 由既有 advice 产出业务码信封 ⇒ 仍不走 403。
- ⚠️ 若走方案乙 ⇒ **必须**自定义 `AccessDeniedHandler` 兜底（万一漏出 `AccessDeniedException`）⇒ 兜底形状与业务失败一致。

### 1.4.6 gRPC / Kafka 侧：**仍自研**，但身份模型统一

| 通道 | 现状 | 改造后 |
|---|---|---|
| HTTP | 自研 Filter + Interceptor（9 份） | ★ **Spring Security**（认证 + 角色） |
| gRPC | devh 拦截器 + trailer 业务码 `sea-biz-code`（`GrpcExceptionMapperAutoConfiguration.java:58`） | **不变**（Spring Security 不管 gRPC）⇒ **双栈是必然的**，要讲清边界 |
| Kafka | 消费者侧身份（若需要） | 复用同一 `JwtUtil` + 同一 `AuthorityResolver` |

⇒ ★ **统一的不是「机制」，是「身份模型」**：三侧都产出同一套 authorities（`ROLE_USER`/`ROLE_ADMIN`）⇒ 角色判定只有一份实现。

### D1 ★ Nacos 跨域寻址契约 —— ✅ 结论 A

**现状**：各域 yml 里写死了跨域 gRPC 目标地址，形式为 `discovery:///<注册名>`（如 `discovery:///message-rpc`、`discovery:///article-rpc`），注册名由各域手写 `NacosRegistration` 注册。

**合并后的矛盾**：5 个进程只注册 5 个名字，而调用方要寻址的是**域级**名字。

| 选项 | 做法 | 代价 | 状态 |
|---|---|---|---|
| A | **注册名保持域级**：一个进程可以注册**多个** Nacos 实例名（`article-rpc` + `comment-rpc` + …，端口各自独立）⇒ 调用方 yml **一字不改** | 需改 `NacosRegistration` 为「按域注册多实例」；Nacos 上实例数看起来没减少（但**进程数**减少了） | ⛔ **已被 P1 推翻**（见下方已定块）—— 保留仅作决策留痕 |
| **B（✅ 实际采用）** | 注册名改成进程级（`content-rpc` / `interaction-rpc` / …），调用方按映射表改 | 改动面大；**调用方与被调方必须同批发布**；跨域寻址变脆 | ✅ **P1 采用** |
| C | 同进程内的边全部改成 Spring Bean 直调 | ★ 跨进程 gRPC 实战面归零 ⇒ **面试上「微服务 / gRPC 跨服务调用」的说服力下降**（不推荐） | ⛔ 未采用 |

**✅ 已定（2026-11-27 用户拍板 · P1）：每进程 1 个 gRPC 端口，且注册名收敛为 5 个进程级名字（5 名 ↔ 5 端口）。**

**新的注册名映射**：

| 进程 | Nacos 注册名 | 含域 |
|---|---|---|
| `content-service` | **`content-rpc`**（新名） | article |
| `user-service` | **`user-rpc`**（沿用） | users/user + users/admin |
| `interaction-service` | **`interaction-rpc`**（新名） | like + comment + favorite + follow + **message** |
| `hot-service` | **`hot-rpc`**（沿用） | hot |
| `task-service` | **`task-rpc`**（沿用） | task |

**⇒ 10 个域级名字收敛为 5 个进程级名字**（`article-rpc` / `message-rpc` / `admin-rpc` 等**被寻址过的域级名全部消失**）。

**跨域寻址边全量重算（10 条边，实测自各域 yml 的 `grpc.client.*.address`）**：

| # | 调用方 | 现状地址 | 目标 | 变化类型 |
|---|---|---|---|---|
| 1 | article(content) | `discovery:///message-rpc` | `discovery:///interaction-rpc` | ★ 地址变更 |
| 2 | comment(interaction) | `discovery:///message-rpc` | **进程内直调** | ★ 进程内化 |
| 3 | like(interaction) | `discovery:///message-rpc` | **进程内直调** | ★ 进程内化 |
| 4 | comment(interaction) | `discovery:///article-rpc` | `discovery:///content-rpc` | ★ 地址变更 |
| 5 | favorite(interaction) | `discovery:///article-rpc` | `discovery:///content-rpc` | ★ 地址变更 |
| 6 | hot(hot) | `discovery:///article-rpc` | `discovery:///content-rpc` | ★ 地址变更 |
| 7 | favorite(interaction) | `discovery:///user-rpc` | `discovery:///user-rpc` | 不变（仍跨进程） |
| 8 | follow(interaction) | `discovery:///user-rpc` | `discovery:///user-rpc` | 不变（仍跨进程） |
| 9 | message(interaction) | `discovery:///user-rpc` | `discovery:///user-rpc` | 不变（仍跨进程） |
| 10 | message(interaction) | `discovery:///admin-rpc` | `discovery:///user-rpc` | ★ 地址变更（admin 与 user 同进程 ⇒ 统一到 `user-rpc`） |

⇒ **5 处地址变更 + 2 条边进程内化**；**跨进程边 10 → 8 条**（边 1、4、5、6、7、8、9、10 仍真实跨进程 ✔ gRPC 实战面保住）。

**执行要点**：
- ⚠️ **寻址地址是 L1 跨域契约** ⇒ 5 处地址变更**必须登记签字偏离**；且**调用方与被调方必须同批发布**（灰度期新旧名不兼容 ⇒ 一次全量切换，不能灰度）。
- ⚠️ **边 2、3 进程内化 ⇒ 要改代码，不只是改 yml**：
  - `service/comment/src/main/java/com/rag/comment/client/MessageRpcClient.java` ⇒ 改为同进程 bean 调用；
  - `service/like/src/main/java/com/rag/like/client/MessageRpcClient.java` ⇒ 同上；
  - 并删除两域 yml 的 `grpc.client.message-rpc` 配置段。
  ⇒ 这是本轮**唯一需要改调用代码**的地方，列入 S3-9。
- ⚠️ **边 10 也涉及代码**：`service/message/.../client/AdminRpcClient.java` 的注入通道名 `@GrpcClient("admin-rpc")` ⇒ 改成 `@GrpcClient("user-rpc")`（devh 的通道名 = `grpc.client.<X>` 的 `<X>`，**通道名与地址是绑定的**）⇒ 列入 S3-8。
- ⚠️ `register-enabled: false`（Nacos 自动注册）**必须仍然关着** —— 否则自动注册会注册 Web 容器端口，与手写的 gRPC 端口撞车（已登记 P-17）。
- ⚠️ 加断言：「**一个注册名只允许被一个进程注册**」+「**每个 `discovery:///X-rpc` 的 X 都在 5 个注册名白名单内**」⇒ 防止改漏后启动期才炸。


### D2 ★ Flyway 账本撞号（阻断）

**现状**：每个域的迁移都从 `V1` 起（like V1 / comment V1 / favorite V1 / follow V1 / message V1 / task V1 / article V8…），账本表名已按域独立（`flyway_schema_history_like` 等）。

**合并后的矛盾**：一个进程一本账 ⇒ `interaction-service` 同时含 like/comment/favorite/follow 四套迁移，**V1 号段直接撞**。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | **改用 users 域那套幂等 DDL 脚本**（`db/01..04_*.sql` + `SchemaInitializer`，不用 Flyway）—— 项目里已有现成范式（D17 决策） | ① 与 B 侧 Flyway 目录形态不一致（**登记为签字偏离**）；② `SchemaInitializer` 需扩展为「按清单建表」 |
| B | 迁移脚本重编号（like V1→V101…） | ⚠️ **违反 D16「迁移文件名与 B 侧逐字一致」** ⇒ 签字偏离；且 7 个域都要改 |
| C | 每进程多本账本（一个进程跑 N 个 Flyway 实例） | ★ Flyway 不支持「一个应用多本账本」的干净做法 ⇒ 要自研 ⇒ 不推荐 |
| D | 保留 Flyway，**每进程只保留一个域的迁移**，其余域的表由共享层或 DDL 脚本建 | 等价于 A 的变体，仍需幂等脚本 |

**✅ 已定：方案 A**。理由：① **零重编号**（不碰 B 侧文件名 ⇒ 不违反 D16 的「文件名逐字一致」硬要求）；② 复用项目内已验证的 D17 范式；③ 幂等重放天然支持「一个进程建多域的表」。
**执行要点**：
- 7 个域的 `db/migration/V*.sql` **文件内容与文件名一字不改**，但**不再由 Flyway 执行** ⇒ 需转成幂等 DDL 脚本（`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`），落位见待拍板 **P2**。
- `SchemaInitializer` 扩展为「**按清单建表**」：由每个 boot 模块传入本进程负责的脚本清单（而不是现在 users 域那种固定 4 个脚本）。
- ⚠️ **7 个域 pom 的 `flyway-core` / `flyway-database-postgresql` 依赖 + yml 的 `spring.flyway` 段是否移除** ⇒ 见待拍板 **P5**。
- ⚠️ 全部登记为**签字偏离**（与 B 侧的迁移机制不同：Flyway 账本 → 幂等 DDL）。

### D3 Kafka container factory 隔离

**现状**：`task` 域**自建**了 `ConcurrentKafkaListenerContainerFactory`（⇒ task yml 里 `spring.kafka.listener.*` 是死键，已登记 DRIFT-LIKE-016）；其余域用 Boot 默认 factory。

**合并后的矛盾**：同进程内 factory 是单例 bean ⇒ task 的自建 factory 会成为全进程的默认 factory，改变其他域的并发度/ack 语义。

| 选项 | 建议 |
|---|---|
| **A（建议）** | 保留 task 自建 factory，但**显式指定**：task 的 `@KafkaListener(containerFactory="taskKafkaListenerContainerFactory")`，其余 listener 显式指定各自 factory（各域一个，共 5 个） |
| B | 全进程统一一个 factory ⇒ ⚠️ 会改变 task 的 ack/并发语义（`AckMode.RECORD` 与自建配置）⇒ 行为变更 |

**✅ 已定：方案 A + 显式指定**（2026-11-27 用户拍板）。
**执行要点**：
- 保留 task 自建 factory；**每个 `@KafkaListener` 显式写 `containerFactory="<域>KafkaListenerContainerFactory"`**（5 个 factory 各自独立）。
- ⚠️ **所有域的 listener 都要显式指定**（不能只改 task）⇒ 否则 task 的自建 factory 成为全局默认，悄悄改掉其他域的 ack/并发语义。
- 补一条装配层断言：listener 落在**预期**的 factory 上（task 的 `AckMode.RECORD` 不被别域带走）。

### D4 测试 support 类同名

**现状**：`support/TestPostgres.java`、`support/TestRedis.java` 在 comment/favorite/follow/like/task/hot/users 等**多个域各有一份同名类**（不同包，合并后落进同包 ⇒ **类名冲突**）。

**✅ 已定：合并时统一改名 `TestPostgresXxx` / `TestRedisXxx`（按域后缀）**（2026-11-27 用户拍板）。
**执行要点**：
- 命名示例：`TestPostgresLike` / `TestRedisComment` / `TestPostgresTask` …（**Xxx = 域名**）。
- ⚠️ 同时要核对：合并后**多个域的 `@SpringBootTest` 启动类**是否冲突（10 个 `*ServiceApplication` + 各自的 `*ServiceApplicationTests`）⇒ 测试类的归属方案见待拍板 **P3**。
- 批量重命名 = **M3 关思考**的活（S2-1）。

### D5 HTTP 路径前缀与端口

**现状**：article 的基路径是 `/v1`（`ArticleController.java:99` 的 `@RequestMapping("/v1")`），其余域是 `/<域>/v1/...`；每域一对端口（HTTP + gRPC）。
**合并后的矛盾**：5 个进程各一对端口 ⇒ 10 个域的路径必须互不重叠；article 的 `/v1/**` 与其他域风格不一致。

**✅ 已定：article 基路径 `/v1` ⇒ `/article/v1`**（2026-11-27 用户拍板）—— 与其余域的 `/<域>/v1/...` 风格统一。

**受影响端点全量（7 个）**：

| 现状 | 目标 |
|---|---|
| `POST /v1/article` | `POST /article/v1/article` |
| `PUT /v1/article/{id}` | `PUT /article/v1/article/{id}` |
| `DELETE /v1/article/{id}` | `DELETE /article/v1/article/{id}` |
| `GET /v1/me/article/{id}` | `GET /article/v1/me/article/{id}` |
| `GET /v1/article/{id}` | `GET /article/v1/article/{id}` |
| `GET /v1/articles` | `GET /article/v1/articles` |
| `POST /v1/upload` | `POST /article/v1/upload` |

**执行要点**：
- 改动点 = `ArticleController.java:99` 的 `@RequestMapping("/v1")` ⇒ `@RequestMapping("/article/v1")`（**单行改动，7 个端点自动跟随**）。
- ★ **这是对外可观测的 L1 行为变更**（与 B 侧路径不一致）⇒ **必须登记签字偏离**（`docs/Intentional_Deviations/global/`）。

## 七、给下一个执行者的三句话
