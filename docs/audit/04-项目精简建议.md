# 04 · 项目精简建议

> 原则（来自任务书）：**项目不是八股知识的展示柜**；不要为了让每个板块都有对应技术而增加复杂度。
> 本项目的真实情况与任务书的默认假设**不同**：它**没有堆砌中间件**（无 ES / Milvus / Neo4j / Dubbo / RocketMQ / RabbitMQ / ZooKeeper / 分库分表 / AI Agent）。
> ⇒ 因此「精简」的对象**不是技术栈**，而是：**① 失效机制 ② 死代码与死配置 ③ 进程/模块粒度 ④ 重复抽象**。

## ⚠️ 前置声明：本项目的「精简」与项目自身政策存在张力（必须先说清）

| 项目政策 | 内容 | 对「精简」的影响 |
|---|---|---|
| **D16** | **B 侧（Go 仓）是唯一 oracle**；L1 契约 / L2 业务语义 / L4 机制**全部以 B 侧为准**；与 B 冲突即 C 错 | **任何删改若改变行为 ⇒ 都是「C 偏离 B」⇒ 属签字偏离，必须走决策流程**，不是「顺手清理」 |
| **D13** | L2 业务语义层以 B 侧为基准 | 同上 |
| **§五.2** | 三档台账：DRIFT（漂移）/ Intentional_Deviations（签字偏离）/ Pitfalls（踩坑） | 本文件**不重复登记**，只标注「是否构成偏离」 |
| **§五.3** | `common/**` 只有 `global` 收口任务能写 | 涉及 `common/` 的改动必须走 `global` 收口轮 |
| **§一.0** | 项目存在理由 = **把 B 侧的 api/rpc 分离压平成 Spring 形态** | 「合并进程」类建议会**动摇项目存在理由** ⇒ 属重大决策，不能由审计单方建议 |

⇒ **本文件所有建议按「是否构成签字偏离」分三档标注**：
- 🟢 **零偏离**（只删本仓自己引入的冗余，不改行为）—— 可直接做
- 🟡 **可能构成偏离**（行为有细微变化，如日志、错误码形状、默认值）—— 需登记 + 决策
- 🔴 **必然构成偏离**（行为改变，如进程合并、字段变更）—— **只给方案与代价，不建议执行**

## 二、逐项说明（每项回答 5 问）

### A 组 · 必须保留（9 项）

#### A-01 10 个业务域的限界上下文划分 —— **保留**
1. **当前怎么实现**：10 个独立 jar 模块，各自独立表集合、独立 Nacos 注册名（`<域>-rpc`）、独立 Kafka 通道。
2. **为什么有价值**：按**数据所有权**切分，不是按「显得微服务」切分。like 域有 `like_record` + `like_consume_inbox` + 3 张 outbox；article 域有 5 张表 —— 边界清楚，DDL 契约互不重叠。
3. **删掉会失去什么**：失去数据所有权边界（跨域直接改表，如 admin 改 `users_user` 就会变成常态），失去「每域独立演进」能力。
4. **替代机制**：无。
5. **影响**：业务功能无损；面试说服力**增强**（能讲清「为什么这么拆」）。

#### A-02 outbox 事件表模式 —— **保留并推广**
1. **当前**：article 域 `article_sync_outbox`（状态机 + `retry_count` + 唯一幂等键 + 定时中继）；like/comment/favorite 三域各有 `*_fact_outbox` + `FOR UPDATE SKIP LOCKED` 抢占 + 调度器。
2. **为什么是优点**：这是**真实解决「DB 写成功但 MQ 发送失败」**的标准答案，且已在仓内形成 4 个域的一致范式。
3. **删掉会失去什么**：失去「消息可靠投递」的唯一有效手段（当前 article 审核事件正是缺了它）。
4. **替代**：无。
5. **影响**：**这是本项目最该复用的模式**（见 B-01：审核事件改走同一范式）。

#### A-03 悲观锁 + `SKIP LOCKED` 的并发控制链路 —— **保留**
1. **当前**：`SELECT ... FOR UPDATE`（like 记录、comment 索引、article 主表/发布指针）+ `FOR UPDATE SKIP LOCKED`（3 个域的事实 outbox 抢占）。
2. **为什么值得保留**：注释写清了**为什么是悲观锁而不是乐观锁**（并发首次点赞靠这行把两个事务串行化）⇒ 有业务推理，不是炫技。
3. **删掉会失去什么**：并发首次点赞/关注的正确性。
4. **替代**：改乐观锁需全表加版本列 ⇒ **成本更高、收益更低**。
5. **影响**：保留。★ **面试时这是「锁选型」题的标准答案，且有代码可指**。

#### A-04 Kafka 五域真实使用 + **按域刻意不同的重试策略** —— **保留**
1. **当前**：9 topic；like = 不重试且提交位点（对齐 B 侧 `ForceCommit`）；comment = 不提交位点 ⇒ 重投；task/hot = RECORD。
2. **为什么值得保留**：**差异是刻意的、有注释论证的**，这正是「消息可靠性」题的高分答案（没有一条万能策略，每条链路的选择取决于业务能否容忍重复）。
3. **删掉会失去什么**：失去差异化可靠性语义。
4. **替代**：无。
5. **影响**：★ **保留并在面试中作为「你如何权衡 at-least-once vs exactly-once」的素材**。

#### A-05 熔断 / 降载 / 限流三件套 —— **保留**
1. **当前**：Resilience4j 三态熔断（每路由独立 breaker）+ CPU 自适应降载（千分比阈值）+ `MaxConnsFilter` 连接数闸门 + `max-bytes` 字节闸门。
2. **为什么值得保留**：**全部有真实消费点**，且明确记录了「resilience4j 默认参数不等价 ⇒ 自定义滑动窗口与半开策略」。
3. **删掉会失去什么**：失去出向调用的自我保护（跨域 RPC 是 10 域之间的必经路径）。
4. **替代**：无（自研更重，Spring Cloud CircuitBreaker 更薄但要引新依赖）。
5. **影响**：保留。★ 直接对应「高并发/高可用」板块的 4 道题，且**有真实现**。

#### A-06 `common/` 的 auto-configuration starter 范式 —— **保留**
1. **当前**：14 个 auto-config + `AutoConfiguration.imports` + `MybatisPlusOrderingBridgeAutoConfiguration`（只建排序边、零 bean）。
2. **为什么值得保留**：**「哪些 bean 由谁装配」讲得清**，且有 `AutoConfigurationImportsTest` 断言无「注册了但没消费点」的假配。
3. **删掉会失去什么**：10 个域各自写一遍 Web/保护/观测装配 ⇒ 代码量 ×10。
4. **替代**：无。
5. **影响**：保留。★ 这是「Spring 自动配置」板块唯一的 A 级落地。

#### A-07 事务失效的系统性规避 + 断言 —— **保留**
1. **当前**：self-invocation ⇒ 事务方法独立成 Bean（4 处）；`readOnly` 与 `incr_view` 冲突 ⇒ 刻意不加 `@Transactional`；加了才会生效 ⇒ 刻意不加；`AopUtils.isAopProxy` 运行时断言。
2. **为什么值得保留**：★ **这是全项目最值得写进简历的一段** —— 它证明作者知道「事务失效的六种场景」并逐个处理，且用**变异测试式断言**（去掉注解就应失败）验证。
3. **删掉会失去什么**：失去最强的面试抓手。
4. **替代**：无。
5. **影响**：★ **不要精简，反而应把 comment/follow/message 域也补上同类断言**。

#### A-08 DDL 契约与「逐条注释索引用途」的写法 —— **保留**
1. **当前**：每个索引的 DDL 注释写明覆盖哪条查询；`CHECK NOT VALID` 的「存量放行/新写强制」语义；DB 层不可变触发器。
2. **为什么值得保留**：**这是「索引设计」板块从背书变实战的唯一材料**。
3. **删掉会失去什么**：失去可 review 的 schema 契约。
4. **替代**：无。
5. **影响**：保留。

#### A-09 逐域隔离的错误码契约 —— **保留**
1. **当前**：每域独立 `contract/ErrCodes`（article 中文文案、hot 英文文案，号码可重叠但语义不同）。
2. **为什么值得保留**：符合「未统一化」纪律（L1 契约逐域隔离）。
3. **删掉会失去什么**：破坏跨域错误码契约。
4. **替代**：无。
5. **影响**：保留，但**在 docs 里写清「号码可重叠、需按域判读」**（见 §04 补充文档项）。

### C 组 · 可以合并（4 项）

#### C-01 两套 JWT 栈 → 合并到 `users-common` 🟢/🟡
1. **当前**：`users/user/interceptor/{JwtAuthFilter,JwtSignatureVerifier,JwtAuthInterceptor,JwtAuthPaths,JwtVerificationResult}` 与 `users/admin/interceptor/{AdminJwtSignatureFilter,AdminJwtSignatureVerifier,AdminJwtAuthInterceptor}`（含嵌套的 `AdminJwtAuthPaths`/`AdminJwtVerificationResult`）几乎逐字重复。
2. **为什么重复**：两子域独立开发时的复制粘贴；**真实差异只有两点** —— 黑名单前缀（`user:` / `admin:`）与畸形 claim 处置（user → 200+业务码 1006；admin → 401）。
3. **合并后失去什么**：**会丢失那两点差异** ⇒ 必须显式参数化（`blacklistPrefix` + `malformedClaimPolicy` 两个策略参数），否则行为漂移 ⇒ 属 🟡 可能偏离（畸形 claim 的 200 vs 401 是**可观测的 HTTP 状态差异**）。
4. **替代机制**：仓内已有成熟范式 —— `common/` 的 starter 化（14 个 auto-config 正是这么做的）。
5. **影响**：业务功能不变；**维护成本降**；面试上「你怎么做公共能力抽取」有真实案例。**建议做，但走 `global` 收口轮，并登记差异参数化**。

#### C-02 `user/contract/ErrCodes` + `ErrMsg` 转发层 → 统一用共享层 🟢
1. **当前**：`service/users/user/.../contract/ErrCodes.java:40-85` 逐个常量转发 `users-common` 的真源；**admin 侧无对应层**，直接 import 共享层。
2. **为什么多余**：纯别名，零行为；两子域形态不对称反而误导。
3. **删掉会失去什么**：**什么都不失去**（调用点改 import 即可，码值不变 ⇒ HTTP 响应字节不变 ⇒ 🟢 零偏离）。
4. **替代**：直接用 `com.rag.users.common.ErrCodes`（admin 已经这么用）。
5. **影响**：**建议直接删**；可用 `FavoriteSqlStatementParityTest` 同款「逐字对拍」思路加一条「响应码值不变」的断言。

#### C-03 `SchemaInitializer` 的 4 个脚本 → 按表归属拆分 🟡
1. **当前**：`service/users/common/.../SchemaInitializer.java:73-78` 固定执行 4 个脚本（`db/01..04`），其中 03/04 是 **admin 的表**；`users/user/.../wiring/UserSchemaBootstrap.java:82-86` 也调它 ⇒ **启 user 服务会建 admin 的表**。
2. **为什么重复/越界**：users-common 是**共享库模块**，把「谁拥有哪张表」的知识漏进了共享层。
3. **拆分后失去什么**：**user 域启动将不再创建 admin 表** ⇒ 若部署时先启 user 后启 admin，admin 表的创建责任须明确归属 ⇒ 属 🟡 可能偏离（部署时序变化）。
4. **替代**：脚本清单参数化（`SchemaInitializer` 接「本进程要建哪些表」的清单，由各 app 传入）。
5. **影响**：架构更干净；**需与部署流程一起改**。

#### C-04 重试 / 幂等 / 锁机制 —— **明确不合并**（这是本节的重要否定结论）
1. **当前**：DB 唯一索引（like/follow/favorite）、inbox 表（like 消费）、Redis SETNX（task 幂等）、`FOR UPDATE`（并发串行）、`FOR UPDATE SKIP LOCKED`（多实例抢占）、outbox `retry_count`（投递重试）—— **6 种机制并存**。
2. **为什么看起来重复**：名字都像「保证只做一次」。
3. **为什么不合并**：它们解决的是**六个不同的问题**：
   | 机制 | 解决的问题 | 不能被谁替代 |
   |---|---|---|
   | DB 唯一索引 | 业务层重复写入 | Redis 做不到（无事务原子性） |
   | inbox 表 | 跨事务的消息幂等 + 可审计 | 唯一索引只判 msg_id 存在，不判状态流转 |
   | Redis SETNX | 高频快速标记（不想打 DB） | DB 会打爆 |
   | `FOR UPDATE` | 并发写串行化 | 唯一索引只防重复，不防竞态 |
   | `SKIP LOCKED` | 多实例抢占任务 | `FOR UPDATE` 会互相阻塞 |
   | outbox `retry_count` | 投递失败重试 | 其余五个都不管「投递」 |
4. **替代**：无。
5. **影响**：★ **保留全部 6 种**，但**必须在面试里说清每个机制解决哪一层** —— 否则听者会以为你在堆砌。这正是「消息不丢失 / 幂等 / 顺序」板块的高分答法。

### D 组 · 可以简化（6 项）

#### D-01 hot 域三层并发闸门 → 二选一 🟢
1. **当前**：`ThreadPoolTaskExecutor`(core=max=**64**, queue=**64**, `CallerRunsPolicy`) + `Semaphore(8)` + `CompletableFuture.orTimeout(2000ms)`。
2. **为什么复杂**：三个闸门都在管同一件事（并发度），**真正生效的是信号量 8** ⇒ 池参数形同虚设。
3. **简化后失去什么**：**什么都不失去**（当前有效并发度就是 8，简化后保持 8 即可）⇒ 🟢 零偏离。
4. **替代**：把并发度写进线程池参数（`core=max=8`），删掉信号量；或反过来保留池 64 删信号量并接受 64 并发。**建议前者**（与 `MAX_PAGE_SIZE=50` 同量级）。
5. **影响**：代码更短；★ 面试上「你怎么控制并发度」能一句话说清，而不是「三层都控了一下」。

#### D-02 `HeavyKeeper` 双结构 + 全量重建堆 → 单结构增量维护 🟢
1. **当前**：`topKMap`(HashMap) 与 `topKHeap`(PriorityQueue) **两份结构并存**（`HeavyKeeper.java:117,119`）；每次已存在 key 的更新都 `rebuildHeap()` 全量重建（:246-248,270-277）⇒ O(n log n)/次。
2. **为什么复杂**：想同时获得「按 score 查」和「按 rank 取」两种访问 ⇒ 用了两份结构，但**没有单一真源** ⇒ 会漂移。
3. **简化后失去什么**：**什么都不失去**（单结构也能满足两种访问：HashMap 保 score，rank 由惰性排序得到）。
4. **替代**：单 `HashMap` + 变更时增量维护小顶堆（避免每次全量重建）。
5. **影响**：性能提升 + 消除状态漂移风险；🟢 零偏离（输出顺序需保持一致 ⇒ 补一条排序断言）。

#### D-03 article 冗余作者校验清理 🟢
1. **当前**：domain 层 `getArticleBody` :343-345 与 API 层 `getAuthorArticle` :280-282 各查一次作者；`updateArticle`/`deleteArticle` 更严重：**先 `getArticle` 读一次再改**（TOCTOU）。
2. **为什么复杂**：HTTP 层与 domain 层重复校验，出错行为可能不一致。
3. **简化后失去什么**：**什么都不失去**（保留一层即可，保留 domain 层更安全）。
4. **替代**：单一校验点 + 异常统一映射。
5. **影响**：行为等价（错误码相同）；🟢 零偏离。

#### D-04 outbox 捞取加 `FOR UPDATE SKIP LOCKED` 🟢
1. **当前**：`ArticleSyncOutboxMapper.java:63-70` 与 `article_domain_outbox.fetchPending` **无锁** ⇒ 多实例重复投递。
2. **为什么复杂**：不是复杂，是**缺一样东西**。
3. **简化后失去什么**：**什么都不失去**（反而减少重复投递）。
4. **替代**：★ **仓内已有正确范式**：`LikeDomainFactOutboxMapper.java:106`、`CommentDomainFactOutboxMapper.java:119`。
5. **影响**：可靠性提升；🟢 零偏离（下游本就幂等）。

#### D-05 `CODE_POINT_ORDER` 比较器笔误修正 🟡
1. **当前**：`ArticleApiSupport.java:316-329` 比较器里第二个字符误用 `a.codePointAt(j)`（应为 `b`）。
2. **后果**：`ext_info` 的 JSON 键序可能不是真正码点序 ⇒ **可能与 A17「JSON 键序全用 jackson2」守门口径冲突**。

### G 组 · 完全没必要实现（7 项）—— **维持 D，不动**

| 技术 | 为什么不需要 | 引入它会带来什么 |
|---|---|---|
| **Elasticsearch** | 社区业务无全文检索需求；文章列表靠 PG 索引 + 排序白名单 | 索引双写一致性问题（新增一大类 bug）+ 集群运维成本 |
| **Milvus / 向量库 / RAG** | 项目名带 RAG 但**与检索增强无关**（RAG 是仓库代号）；无 embedding、无 LLM 调用 | 一整套新链路（切分、向量、召回、重排、评测）+ 语义漂移风险 |
| **Neo4j** | 关注关系是**有向边 + 唯一约束**，PG 表足够；图算法（推荐）已在应用层用 BFS 实现 | 图数据库运维成本 + 双写一致性问题 |
| **Dubbo** | 跨域调用已用 gRPC（自带流控/超时/拦截器） | 两套 RPC 体系 |
| **RocketMQ / RabbitMQ** | Kafka 已覆盖全部 9 个 topic 的需求 | 两套 MQ 语义（事务消息/延迟消息/死信各一套） |
| **ZooKeeper** | Nacos 已承担注册发现 + 配置 | 两套注册中心 |
| **分库分表** | 当前数据量与并发远未到门槛；★ **架构上已「能分」**（雪花 ID + 无外键 + 唯一索引幂等 + `public` schema 共享库） | 跨库 JOIN / 全局 ID / 分布式事务 / 数据倾斜全套复杂度 |

> 📌 **这一组是本项目相对同类「八股项目」的最大优势**：多数项目会被建议「加 ES 加缓存加 MQ 加分表」，而本项目**一个都没加**，且每个不用的理由都成立。**建议在面试中主动讲这一段** —— 「我明确评估过 ES/向量库/Milvus，并给出了不引入的理由与将来引入的触发条件」，比「我都用过了」更有说服力。

## 五、跨域合并方案（🔴 必然构成偏离 —— 只给方案与代价，不建议执行）

### R-01 「10 进程 → 1 进程」的合并评估

| 方案 | 内容 | 收益 | 代价 |
|---|---|---|---|
| **方案 1（推荐给面试版本）** | 保持 10 域模块化，**但合并为 1 个 Spring Boot app**（域内仍是独立包 + 独立 `Dispatcher`/port） | ① yml 从 3,668 行 → 约 500 行；② 部署从 10 个 → 1 个；③ compose 简单化；④ **仍能讲「限界上下文 + 微服务拆分演进路径」** | ① **失去「跨进程 gRPC 真实调用」的实战**（只能测同进程直调）⇒ 面试上「gRPC 跨服务调用」的说服力**下降**；② Nacos 注册/发现的实战面归零；③ 与项目存在理由（D1 压平 api/rpc，但**保留域间进程隔离**）**直接冲突** ⇒ 需修改 AGENTS.md 的核心决策 |
| **方案 2（中间态，推荐给工程版本）** | **保持 10 进程**，但把**重复的装配收进 `common/`**：JWT 栈、advice 映射、metrics、WebMvc 装配、DDL 初始化清单 | ① 代码量降；② 保留全部实战面；③ **不违反 D16**（行为不变） | 收益有限（yml 仍 3,668 行） |
| **方案 3（当前）** | 维持 10 进程 | — | 部署与配置成本高 |

> 📌 **审计立场**：本项目的 10 进程**不是「为微服务而微服务」** —— 它有独立表、独立注册名、独立消息通道，是 B 侧 `api/rpc` 分离形态的**忠实继承**。
> ⇒ **在 D16 政策下，「合并进程」= 改产品形态**，不是技术精简。
> ⇒ **建议**：若目标是「面试说服力」，**走方案 2**（零偏离、零风险、代码更干净）；若目标是「本地可跑、部署简单」，**走方案 1**（需拍板并改 AGENTS.md 决策）。
> ⇒ **明确不建议**：为了「看起来更单体」而合并**限界上下文**（会丢掉本项目最好的设计）。

### R-02 若要「减少组件」，真正该减的是这 3 个（而不是技术栈）

1. **减「失效机制」**：6 处占位/死路（E 组 + §03 P0）—— 这些比「多一个组件」更伤说服力，因为**面试官问「你用了 XX」时，一句「那个是占位、没实现」会毁掉整段话**。
2. **减「重复抽象」**：4 组（§四 检查表）。
3. **减「进程/配置面」**：R-01 方案 1/2。
