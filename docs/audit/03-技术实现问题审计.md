# 03 · 技术实现深度审计

> 范围：数据库与事务 / Redis 与缓存 / 消息队列 / Spring 与微服务 / 并发与高可用 / 代码结构与设计
> 判读口径：**问题按「是否影响业务正确性」排序**，不按「是否不优雅」排序。

## 1. 数据库与事务

### 1.1 表结构与索引 —— 整体质量高

| 维度 | 结论 | 证据 |
|---|---|---|
| 主键策略 | ★ **按域选型且有理由**：article 用 `VARCHAR(32)` 雪花串；like 用 `BIGSERIAL`；message 用 `BIGINT` 应用侧雪花；task 用**复合 PK `(user_id, task_id)`** | `service/article/.../V8__create_article.sql:22`；`service/like/.../V1__create_like_record.sql:12`；`service/task/.../V1__create_task_progress.sql:25` |
| 唯一索引 | ★ **幂等靠 DB 约束，不靠代码判断**：`uk_user_target`、`uk_follow_pair`、`uk_block_pair`、`uk_conversation_pair`、`uk_article_sync_outbox_event_key` | `service/like/.../V1__create_like_record.sql`；`service/follow/.../V1__create_follow_relation.sql:36` |
| 普通索引 | ★ 每个索引的 DDL 注释**直接写明覆盖哪条查询**（`idx_user_list` → `GetUserLikeList` 的 WHERE…ORDER BY） | `service/like/.../V1__create_like_record.sql` |
| 外键 | ★ **全仓零外键**（DDL 声明层面） | 三份 article DDL、like V1、follow V1/V2 均无 FK |
| JSONB | 真实使用（`secondary_tags`/`ext_info`/`payload`）+ 自研 typeHandler + 真 PG 测试 | `common/persistence/`；`service/article/src/test/.../ArticleJsonbResultMapRealPgTest` |
| CHECK 约束 | ★ `NOT VALID` CHECK 保证「新写入必须三件套齐全，存量放行」 | `service/comment/.../V6__create_comment_domain_fact_outbox.sql` |
| 触发器 | ★ 已发布 revision 不可变 = **DB 层强制**，不是应用层自觉 | `service/article/.../V10__create_article_community_revision.sql:60-70` |
| 分表/分区 | 无（**当前不需要**） | — |

**问题 1.1（🟡）`users_user_avatar_history` 无 FK ⇒ 删用户留孤儿行。**
- 现象：DDL 只有普通列，无 FK；但代码注释自述依赖 FK CASCADE。
- 证据：`service/users/common/src/main/resources/db/02_create_user_avatar_history.sql:22-33` vs `service/users/user/.../domain/service/UserDomainService.java:535`。
- 后果：删用户 ⇒ 头像历史行残留。
- 替代：**不建议加 FK**（与全仓「无外键」策略冲突，且 FK 会被锁竞争伤到）；**建议改代码**（删除时显式 `DELETE FROM users_user_avatar_history WHERE uid=?`）。

**问题 1.2（🟠）Flyway 账本表名撞号 —— 7 个域共用 `public` schema 且账本表名不统一。**
- 现象：`flyway_schema_history` 是 **schema 级**账本；like/comment/favorite/follow/message/task/article 各有 `spring.flyway` 段（独立表名已做对的部分在 like/article），但需逐域核对。
- 证据：根 `AGENTS.md` §六；`service/like/.../V1__create_like_record.sql` 尾部的 Flyway 说明（明确写「4 项必须齐、放顶层 ⇒ 静默失效」）。
- 后果：**后启动的域把自己的迁移判成「已应用」而静默跳过 ⇒ 表建不出来**。
- 现状判定：**部分域已修**（like 用 `flyway_schema_history_like`、article 用 `flyway_schema_history_article`），其余域**需逐域核对** ⇒ 本次未逐域实测启动行为，**标记「无法确认」**。

**问题 1.3（🟡）深度分页防护在 HTTP 与 gRPC 之间不一致。**
- 现象：HTTP 路径 clamp `size`（1..100），gRPC `ListArticles` 直接用 `in.getPageSize()`。
- 证据：`service/article/.../domain/service/ArticlePublicDomainService.java:214-220` vs `service/article/.../domain/service/ArticleDomainService.java:811-812`。
- 后果：绕过 HTTP 直连 gRPC ⇒ 超大 LIMIT + 深 offset 直达 DB；且每次列表还跑一次全表 `COUNT`（`ArticleMapper.java:135-152`）。
- 替代：**已有** `normalizeListReq` / `normalizeLimit` 归一化器（follow/message 域），**直接复用**即可，不需要新机制。

**问题 1.4（🟢）无乐观锁（`@Version` 全仓零命中）。**
- 后果：read-modify-write 路径后写覆盖（admin 封禁/解封、follow 关注计数、文章计数）。
- 判定：**当前不构成 P0**（这些字段无强一致要求，且多数路径有唯一索引或条件 UPDATE 兜底）。若要补，只补「有明确并发写冲突的字段」，不要全表加版本列。

**问题 1.5（🟢）幂等实现分散在三种机制上。**
| 机制 | 落点 | 适用 |
|---|---|---|
| DB 唯一索引 + `ON CONFLICT DO NOTHING` | like/follow/favorite | ★ 首选 |
| inbox 表（`msg_id` 主键 + status 状态机） | like 域消费侧 | 跨事务消费幂等 |
| Redis `SETNX` + TTL | task 域初始化/完成 | 快速幂等标记 |
- 判定：**不重复、不冲突**，各自有适用面（DB 唯一 / 消息幂等 / 快速标记）。**不建议合并**，但需在面试时说清「为什么这里用 DB、那里用 Redis」。

## 2. Redis 与缓存

### 2.1 现状盘点（9 域真实使用）

| 域 | 用途 | Key | TTL | 评价 |
|---|---|---|---|---|
| hot | ★ **核心存储**：全局榜 ZSET + 分片 + 影子键 + 合并锁 | `hot:articles` / `hot:articles:p{n}` / `hot:articles:shadow` / `hot:merge:lock` | 3600s / 300s / — / 10s | ★ **Redis 用得最有价值的一处** |
| task | 进度缓存 + 幂等标记 + 计数 + 奖励 Stream | `task:progress:*` / `task:init:*` / `task:done:*` / `task:goka:count:*` / `stream:task:reward` | 15min / 90d / 120d / **无** / — | 计数无 TTL 是隐患 |
| like | 动作脚本 / key 空间 | `LikeRedisKeys` | — | 中等 |
| comment | ★ **唯一完整缓存语义**：singleflight + 双检 + 4 个差异化 TTL + 分档降级（回源/不回源） | `CommentRedisKeys`（5 个 key 方法）；`CommentCacheService` | 5min / 3min / 10min / 24h | ★ **全仓 Redis 实现质量最高的一处** |
| users/user · users/admin · favorite · follow | ★ **只有 JWT 黑名单** | `user:jwt_blacklist:*` / `admin:jwt_blacklist:*` | 30d | fail-open |
| message | **零使用**（pom/yml 有、代码无） | — | — | ★ 应删 |

### 2.2 问题清单

**问题 2.1（🟠）hot 域 Redis 全挂 ⇒ 热榜接口返回空列表而非报错。**
- 证据：`service/hot/.../service/HotRankingQueryService.java:96-98`（Redis 空则返回空列表，无 DB 回源）。
- 判读：hot **零 DB**，无回源是设计选择（与 B 侧一致）。但**空列表与「真的没有热榜」不可区分** ⇒ 运维上无法察觉 Redis 故障。
- 替代：无需新组件；在读取失败（异常）与「key 不存在」两种情况**分开返回**即可（异常路径已有 5001 映射：`HotApiExceptionHandler.java:137-141`）。

**问题 2.2（🟠）hot 快照刷新失败 ⇒ 300s 后分片消失 ⇒ 全局榜变空。**
- 证据：分片 TTL **300s 硬编码在 Lua 里**（`HotRedisSnapshotStore.java:113`），刷新周期 30s（`periodicSync` :292-299）⇒ 容忍 10 个周期失败；yml `:236-241` 另注明「`partition-count` 必须等于 topic 分区数，否则多分片永不合并」。
- 后果：**一个静默的参数不匹配就会让整榜为空**。
- 替代：启动期加一条**分片数一致性断言**（对齐 `ArticleSchemaGate` 的做法：`service/article/.../wiring/ArticleSchemaGate.java:110-115`）。

**问题 2.3（🟡）`task:goka:count:*` 计数无 TTL ⇒ 内存单调增长。**
- 证据：`service/task/.../messaging/TaskCountStore.java:21-28`（`INCR` 无过期）。
- 后果：长期运行 ⇒ key 数与用户数同阶增长。
- 替代：**加 TTL**（与 `task:init`/`task:done` 的 90d 一致）—— 一行改动。

**问题 2.4（🟡）JWT 黑名单 fail-open。**
- 证据：`service/users/user/.../interceptor/JwtAuthInterceptor.java:135-145`（Redis 异常 ⇒ 放行）；`service/follow/.../interceptor/FollowBlacklistInterceptor.java:63-66` 同款。
- 后果：Redis 故障窗口内，已注销的 token 可继续使用。
- 判读：**与 B 侧一致（继承行为）**，且 fail-open 是「可用性优先」的常见选择 ⇒ **不建议单方面改**，若要改属签字偏离，需走决策流程。

**问题 2.5（🔴）`message` 域 Redis 依赖与配置是纯残留。**
- 证据：pom `service/message/pom.xml:140` 引 `spring-boot-starter-data-redis`；yml `service/message/src/main/resources/application.yml:13-14` 有 redis 段；`service/message/src/main` 中 `redis` **零命中**。
- 后果：① 镜像多一个依赖；② **误导性配置**（后来者会以为 message 域用了缓存）；③ 启动时多一次连接创建。
- 替代：**删依赖 + 删配置**（零行为影响）。或明确注释「预留」并在台账登记。

**问题 2.6（🟡）缓存穿透/击穿三件套未做 —— 但**当前不需要**。**
- 判读：本项目无「按 ID 查缓存」的热点读路径（hot 的读是 ZSET 常驻；comment 的缓存非核心读路径）⇒ 引入空值占位/互斥重建属于**无业务价值的复杂度**。
- **结论：不做。** 这正是任务书里「不要为了体现 Redis 而引入 Redis」的正确落点。

## 3. 消息队列

### 3.1 现状（唯一 MQ = Kafka，9 topic，5 域）

| topic | 生产 | 消费 | 幂等 | 重试 |
|---|---|---|---|---|
| `like_promotion_topic` | like | like（`LikeUpdateKafkaListener`） | ★ inbox 表 | 不重试、提交位点 |
| `article-creation-topic` | article | article（审核） | 四元组匹配 | **零重试 drop**（日志写 "will retry"，矛盾） |
| `article-sync-events` / `article-sync-results` | article outbox relay | article | ★ event_key 唯一索引 + payload 校验 | outbox `retry_count`（max 10） |
| `comment-audit-topic` | comment | comment | 幂等探针 | ★ **不提交位点 ⇒ 重投** |
| `article-hot-events` | like（outbox relay） | hot | ❌ **无幂等** | 零重试 |
| `task.logs.*`（5 个） | like + task 路由 | task（8 listener） | SETNX + GREATEST | RECORD |

### 3.2 问题清单

**问题 3.1（🔴）hot 域消费者无幂等 ⇒ 重复投递放大热度计数。**
- 证据：`service/hot/.../messaging/HotEventConsumer.java:229`（`hk.add(articleId, weight)` **无去重键**）；`service/hot/.../contract/ArticleHotEvent.java:38-41`（payload **只有 2 个字段，无 event_id**）。
- 后果：至少一次语义下，article 审核重投 / like outbox 重推 ⇒ 热度值虚高 ⇒ **热榜排序失真**（业务可见的错误）。
- 替代：**不需要新中间件** —— 只需给 `ArticleHotEvent` payload 加一个 `event_id`（proto/JSON 契约加字段属 L1 变更 ⇒ 需走决策流程），消费侧用 SETNX 去重（与 task 域现成做法一致：`TaskUserLikeProgressSink.java:303-309`）。
- ⚠️ 备选方案：**不改契约**，改为「按 `article_id + type` 去重 + 短 TTL」，会牺牲「同一文章多次互动」的计数 ⇒ **不推荐**。

**问题 3.2（🔴）全仓无死信队列（DLQ）。**
- 证据：全仓 grep `@DltHandler` / `@RetryableTopic` / `DeadLetter` **零命中**。
- 后果：article 审核消息失败 ⇒ 静默丢弃 ⇒ **文章永久卡在 REVIEWING，且无痕迹可查**（只留一行 debug 日志）。
- 替代：Spring Kafka 原生 `DeadLetterPublishingRecoverer`（**不需要新中间件**，Kafka 自带 DLQ topic）⇒ 成本极低。

**问题 3.3（🟠）消费者日志与实际重试语义相反（article 域）。**
- 证据：日志 "will retry"（`ArticleReviewConsumer.java:277,421`；`ArticleSyncResultConsumer.java:265`）vs error handler `FixedBackOff(0L,0L)`（`ArticleServiceApplication.java:185`，注释自陈 "the message is dropped, not redelivered"）。
- 后果：**运维排障被误导** —— 看日志以为会重投，实际不会。
- 替代：**改日志**（零风险）或**改配置**（配合 DLQ）。

**问题 3.4（🟠）article 审核消息无 outbox 兜底。**
- 证据：`service/article/.../domain/service/ArticleDomainService.java:248`（insert）→ `:262`（`kafkaTemplate.send(...).get()`）—— **两步之间无事务、审核消息没有对应的 outbox 表**（`article_sync_outbox` 只覆盖同步事件）。
- 后果：DB 已提交、Kafka 发送失败 ⇒ 文章永久卡审核且**无法重放**。
- 对照：`article_sync_outbox` 已经把「同步事件」做对了 ⇒ **复用同一 outbox 模式**即可，不需要新机制。

**问题 3.5（🟠）生产端在请求线程内同步阻塞等 broker ack。**
- 证据：`ArticleDomainService.java:262`（`.send(...).get()`，注释自陈与 Go 同步 PushWithKey 对齐）。
- 后果：broker 抖动 ⇒ 请求线程阻塞 ⇒ **HTTP/gRPC 线程被拖住**。
- 对照：**outbox relay 已是异步**（`ArticleSyncOutboxRelay.java:178`）⇒ 审核事件改走同一模式即解决。

**问题 3.6（🟡）`fetchPending` 无 `FOR UPDATE SKIP LOCKED` ⇒ 多实例重复投递。**
- 证据：`service/article/.../mapper/ArticleSyncOutboxMapper.java:63-70`（捞取条件 `status IN (0,2) AND retry_count < maxRetry`，**无锁**）；同款 `article_domain_outbox.fetchPending`。
- 对照：**like/comment 域的 fact outbox 都用了 `FOR UPDATE SKIP LOCKED`**（`LikeDomainFactOutboxMapper.java:106`、`CommentDomainFactOutboxMapper.java:119`）⇒ **仓内已有正确范式，直接复用**。

**问题 3.7（🟡）task 域奖励幂等键有碰撞缺陷（继承 B 侧）。**
- 证据：`service/task/.../messaging/TaskRewardPublisher.java:24-28`（幂等 ID 是 `uid + taskID` 的**加法**而非拼接 ⇒ `1+23` 与 `12+3` 相同）。
- 后果：重复发奖 / 漏发奖。
- 替代：改成分隔符拼接（**L1 契约变更 ⇒ 需决策**）。

**问题 3.8（🟢）task 域计数 `INCR` 非严格幂等，但下游 `GREATEST` 收敛。**
- 证据：`TaskCountStore.java:21-28` + `TaskProgressMapper.java:35-41`。
- 判读：**设计正确**（至少一次 + 收敛），与 kafka「只消费一次」题的标准答案一致 ⇒ **保留，且这是很好的面试素材**。

## 4. Spring 与微服务

### 4.1 优点（应保留且值得讲）

| 点 | 证据 | 为什么有价值 |
|---|---|---|
| ★ **自动配置自研 14 个 + 排序边** | `common/.../AutoConfiguration.imports:1-14`；`MybatisPlusOrderingBridgeAutoConfiguration.java:71-77` | 「哪些 bean 由谁装配」讲得清 |
| ★ **事务失效系统性规避 + 断言** | `AdminCreateAtomicService.java:41-56`；`ArticlePublicDomainService.java:127-140`；`ArticleAtomicServiceRealPgTest.java:282-285` | ★ 最强的一段 |
| ★ **AOP 代理真的生效有运行时断言** | `service/article/.../wiring/SnowflakeBootstrap.java:99-114`（`AopUtils.isAopProxy`） | 破除「注解即生效」的幻觉 |
| ★ **gRPC 异常映射进 trailer** | `common/autoconfigure/GrpcExceptionMapperAutoConfiguration.java:57,115` | 跨域错误码保真 |
| ★ **共享层自带装配层测试** | `common/src/test/.../AutoConfigurationImportsTest.java:33-56` | 防止「注册了但没消费点」 |
| ★ **Lombok 纪律机器化** | A13 断言 55/55 PASS；A9 断言 142/142 DTO immutable | 规范不靠自觉 |

### 4.2 问题清单

**问题 4.1（🔴）10 个域 = 10 个进程 + 10 个 Tomcat + 10 套配置（约 3,668 行 yml）。**
- 证据：各域 `application.yml` 行数 165–548，合计 **3,668 行**。
- 后果：① 配置漂移风险高（已有 3 处死配置 + 1 处 Tomcat 参数冲突）；② 部署/运维 10 倍成本；③ 面试时「微服务」的说服力需要额外解释「为什么拆」。
- ⚠️ **重要判读**：这些域**不是「拍脑袋拆」的** —— 每个域有独立的表、独立的注册名、独立的 Kafka 通道，是按**数据所有权**拆的（这符合 DDD 的限界上下文）。但**进程粒度**是否需要 10 个，值得质疑（见 §04 精简建议 R-01）。

**问题 4.2（🟠）一域两套异常体系。**
- 证据：`advice/`（HTTP，`@RestControllerAdvice`）+ `exception/` + `GrpcExceptionMapperAutoConfiguration`（gRPC）；users 域还出现**域内两套**（user 用 `BusinessException`，admin 用 `StatusRuntimeException`，理由见 `AdminExceptions.java:22-40`）。
- 后果：新人要学 4 套错误处理心智模型。
- 判读：**L1 契约要求**（错误码是跨域契约）⇒ 保留是对的；但**域内两套**（user vs admin）纯属不一致，可统一。

**问题 4.3（🟡）`max-parameter-count` 冲突 + 无生效值断言。**
- 证据：8 域 yml 配 2048；`common/autoconfigure/WebAutoConfiguration.java:71` 硬编码 10001 并 `:166-173` 无条件注册 customizer；hot 域已刻意规避（`service/hot/.../application.yml:148-149`）。
- 后果：生效值不确定 ⇒ **两种参数上限下 HTTP 行为可能不同**（超限请求一个被拒一个不被拒）。
- 替代：**加一条真实 Tomcat 断言**（发 2049 个参数的请求，看是否 400）—— 零新组件。

**问题 4.4（🟡）部署面缺失。**
- 证据：全仓无 Dockerfile / docker-compose / CI（find 命中 0）；而 `service/article/.../application.yml` 的注释却写着「部署侧：根级 compose 需注入 USER_JWT_SECRET」⇒ **配置面引用了不在本仓的文件**。
- 后果：① 新人无法本地起全套；② 「高可用/部署」类面试题无实物可讲；③ yml 里 `${POSTGRES_PASSWORD}` 等裸占位符 fail-closed ⇒ 没有 compose 就没法起服务。
- 替代：**补一个 compose + 一个 CI**（`check-arch-invariants.py` 与 `check-mapping-coverage.py` 实测 EXIT=0，可直接进 CI）—— 零新中间件。

**问题 4.5（🟢）Nacos 自动注册被显式关闭（`register-enabled: false`），改用手写 gRPC 端口注册。**
- 判读：★ 这是**正确且有深度**的决定（避免同名双端口），理由写在 yml 注释里。**保留，不要「修」成自动注册。**

## 5. 并发与高可用

### 5.1 优点

| 点 | 证据 |
|---|---|
| ★ 悲观锁 + `SKIP LOCKED` 抢占 | `LikeRecordMapper.java:225`、`CommentDomainFactOutboxMapper.java:119`、`LikeDomainFactOutboxMapper.java:106` |

### 5.2 问题清单

**问题 5.1（🔴）hot 域三层并发闸门职责重叠（过度设计）。**
- 现象：线程池（core=max=64, queue=64, CallerRuns）之上再叠 `Semaphore(8)`。
- 证据：`service/hot/.../config/HotHydrationExecutorConfiguration.java:76,101-107` + `service/hot/.../service/HotApiService.java:124,307`。
- 后果：真正生效的上限是信号量 8 ⇒ **池参数形同虚设**，但读者会误以为并发度是 64。
- 替代：**删掉信号量，把并发度写进线程池参数**（二选一即可）—— 零新组件。

**问题 5.2（🟠）hot 分布式锁丢失不中断合并。**
- 证据：`service/hot/.../messaging/HotMergeScheduler.java:250-252`（续期失败只 `log.error("lost lock")` 后 return，主流程继续 :190）。
- 后果：两实例可同时进入合并 ⇒ shadow 键互相覆盖 ⇒ **结果不确定**（Lua 内有 lock 校验会拒部分写入，但已写部分可能被对方覆盖）。
- 替代：续期失败**抛异常终止本轮合并**即可。

**问题 5.3（🟡）`HeavyKeeper.updateTopK` 每次更新都全量重建堆。**
- 证据：`service/hot/.../domain/model/HeavyKeeper.java:246-248,270-277`；且 `topKMap`(HashMap) 与 `topKHeap`(PriorityQueue) **两份结构并存**（:117,:119）⇒ 状态易漂移。
- 后果：高频事件下 O(n log n)/次；且两份结构不一致时结果不可预期。
- 替代：单份结构 + 增量维护（不重建堆）。

**问题 5.4（🟡）`LongAdder` 未用，热点计数用 `AtomicLong`。**
- 证据：`service/hot/.../messaging/HotEventConsumer.java:96`。
- 后果：高频自增下 `AtomicLong` 存在 CAS 竞争。
- 替代：改 `LongAdder`（一行）。

**问题 5.5（🟡）无死锁检测、无死锁重试。**
- 证据：全仓无死锁处理代码；`common/persistence/SqlTimeoutStatusTranslator.java:92` 的注释提到「外部持锁卡住 W1 的 SELECT FOR UPDATE」场景，说明**已知会有锁等待**。
- 后果：DB 死锁（SQLSTATE 40P01）直接冒泡为 500。
- 替代：**在共享层加一次死锁重试**（`SqlTimeoutStatusTranslator` 已是天然的翻译点）—— 零新组件。

**问题 5.6（🟡）调度线程未显式 daemon ⇒ 可能阻碍 JVM 退出。**
- 证据：`common/observability/ObservabilityRuntime.java:62,75`；`common/protection/SheddingStat.java:175`；`common/observability/RpcStatMetrics.java:407`。
- 后果：关停时挂起 ⇒ 优雅停机超时。
- 替代：`Executors.newSingleThreadScheduledExecutor(r -> { r.setDaemon(true); return r; })`。

**问题 5.7（🟢）无集群限流。**
- 判读：当前是单机限流（JVM 内闸门）。集群限流需要 Redis 令牌桶 ⇒ **当前规模不需要**，不引入。
