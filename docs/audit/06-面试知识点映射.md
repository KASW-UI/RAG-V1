# 06 · 面试知识点映射（从项目中提取的真实知识点）

> 挑选标准：**能拿出代码证据 + 能讲清「为什么这么选」+ 能诚实说出局限**。
> 不收录：只能靠背书回答的题（如「HashMap 红黑树阈值」）、项目里没做过的技术（ES / RocketMQ / 分库分表）、以及**代码里能看出是假成功/占位**的地方（如 hot 的 `commentArticle`）—— 讲占位实现会毁掉整段话。

> 📌 **每个知识点五段式**：业务场景 → 具体实现 → 核心原理 → 技术选型 → 局限性。

## 一、数据库与事务（★★★ 最强）

### K-01 · Spring 事务失效的六种场景与系统性规避
- **业务场景**：文章发布的多个写步骤（锁行 → 改发布指针 → 写 outbox → 推进状态）必须原子；评论点赞的并发首次必须串行化。
- **具体实现**：
  - **self-invocation**：事务方法被拆到独立 Bean（`service/article/.../domain/service/ArticleAtomicService.java:164,210,316,388`；`service/users/admin/.../domain/service/AdminCreateAtomicService.java:82,128`；`service/message/.../domain/service/MessageAtomicService.java:33-82`；`service/comment/.../domain/service/CommentTransactionalService.java`）。
  - **`readOnly` 与写冲突**：`ArticlePublicDomainService.getPublicArticle` **刻意不加 `@Transactional`**（`:127-140`）——因为 `readOnly` 事务下 `incr_view` 路径会失败。
  - **「加了才会生效」的反向规避**：`publishApprovedRevision` / `markSyncFailed` 刻意 **package-private 且不加 `@Transactional`**（`ArticleAtomicService.java:520-522,581`），只在已有事务内被调。
  - **代理真的生效的运行时断言**：`AopUtils.isAopProxy(atomicService)`（`service/article/.../wiring/SnowflakeBootstrap.java:99-114`），非代理时打 ERROR 列出将失去事务的 4 个操作。
  - **变异测试式断言**：去掉 `@Transactional` 就应失败（`service/article/src/test/.../ArticleAtomicServiceRealPgTest.java:53,282-285`）。
- **核心原理**：Spring AOP 代理的「代理对象 ≠ 目标对象」导致内部调用绕过代理；`@Transactional` 的失效场景（自调用、非 public、非代理对象、异常类型不匹配、类未被 Spring 管理、事务管理器缺失）；`readOnly` 下连接被设为只读 ⇒ 写操作失败。
- **技术选型**：选择「**独立 Bean 承载事务**」而不是「注入自己」（`@Lazy` 自注入）或 `AopContext.currentProxy()`，因为前两者在 Boot 3.x 下都有隐患，独立 Bean 最直白且可被测试断言。
- **局限性**：`ArticleDomainService` 的**主写路径没有事务**（`createArticleBody` 的 insert → 发 Kafka 两步裸奔），是刻意继承 B 侧的语义还是遗漏，需在面试中如实说明「我知道这里没有事务，风险是消息丢失导致卡审核，改进方案是 outbox」。

### K-02 · 悲观锁 vs 乐观锁：用业务推理选型
- **业务场景**：同一用户对同一目标的首次点赞/关注可能并发到达。
- **具体实现**：`SELECT ... FOR UPDATE` 把两个事务串行化（`service/like/.../mapper/LikeRecordMapper.java:216-225`；`service/comment/.../mapper/CommentLikeMapper.java:69`；`service/article/.../mapper/ArticleMapper.java:237`）。**全仓 `@Version` 零命中** ⇒ 没有乐观锁。
- **核心原理**：悲观锁「读即加锁」；乐观锁「读不带锁，提交时 CAS 校验版本」。前者适合写冲突高、单行热点；后者适合读多写少。
- **技术选型**：选悲观锁，因为**幂等行还不存在**（首次点赞要插入），乐观锁无从校验；且写入量小、冲突窗口短。代码注释明确写了这个理由（`service/like/.../domain/entity/LikeRecordEntity.java:27`：「并发首次点赞靠这行把两个事务串行化」）。
- **局限性**：悲观锁在热点行上会串行化 ⇒ 高并发下是瓶颈；`admin` 的封禁/解封等 read-modify-write 路径**没有版本号** ⇒ 后写覆盖先写。

### K-03 · `FOR UPDATE SKIP LOCKED`：多实例抢占式任务分发
- **业务场景**：3 个域都要「定时把待投递的事实事件推给下游」，而服务是多实例部署。
- **具体实现**：`service/like/.../mapper/LikeDomainFactOutboxMapper.java:106`、`service/comment/.../mapper/CommentDomainFactOutboxMapper.java:119` —— `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` 抢一行，锁持有到事务提交。
- **核心原理**：`SKIP LOCKED` 让其他实例**跳过已被锁定的行**直接取下一行 ⇒ 无需分布式锁即可实现「谁抢到谁处理」；配合 `status` 状态机实现「取件—处理—标记」。
- **技术选型**：对比方案是 Redis 分布式锁 + 轮询（多一次网络往返 + 锁泄漏风险）、或 `LISTEN/NOTIFY`（PG 通知，跨版本行为差异大）。`SKIP LOCKED` 是**零额外组件**的最优解。
- **局限性**：`article` 域的两个 outbox 捞取**没加锁**（`ArticleSyncOutboxMapper.java:63-70`）⇒ 多实例重复投递（靠下游幂等兜住）；且 `SKIP LOCKED` 在长事务下会降低批量效率。

### K-04 · 幂等的六层防线与「为什么不能用 Redis 替代 DB」
- **业务场景**：点赞消息可能重复投递；用户可能重复点击关注；同一业务事件可能被多个入口触发。
- **具体实现**（六层，各解一个问题）：
  | 层 | 机制 | 落点 |
  |---|---|---|
  | 1 | DB 唯一索引 + `ON CONFLICT DO NOTHING` | `uk_user_target`、`uk_follow_pair`、`uk_block_pair` |
  | 2 | 消费幂等 inbox 表（`msg_id` 主键 + status 状态机） | `service/like/.../service/LikeMessageIngestService.java:185,191,243,274` |
  | 3 | Redis `SETNX` + TTL 快速幂等标记 | `service/task/.../messaging/TaskUserLikeProgressSink.java:303-309,451-456` |
  | 4 | 行级悲观锁串行化并发写 | `LikeRecordMapper.java:225` |
  | 5 | outbox `event_key` 唯一索引 + `retry_count` | `service/article/.../V9__create_article_sync_outbox.sql:27-28` |
  | 6 | SQL 层收敛（`ON CONFLICT + GREATEST`、`status='done' 不可回退`、`done_at` 不可变） | `service/task/.../mapper/TaskProgressMapper.java:35-41,54` |
- **核心原理**：幂等的前提是**「判重 + 落库」要么同一事务，要么有更强的存储保证**。Redis 判重与 PG 落库跨存储 ⇒ 无法原子 ⇒ 只能做「快速标记」不能做「真相」。
- **技术选型**：优先 DB 唯一索引（事务内原子、零额外组件）；消息场景才加 inbox 表（需要记录处理状态与审计）；高频读路径才用 Redis 标记。
- **局限性**：task 域的「完成幂等」同时存在于 Redis SETNX 与 PG `status='done'` ⇒ **轻度重复**（Redis 快、PG 真），需讲清两者分工；`TaskRewardPublisher` 的幂等 ID 用**加法**拼接（`uid + taskID`）⇒ 存在碰撞（继承 B 侧）。

### K-05 · 索引设计：让 DDL 注释成为索引说明书
- **业务场景**：点赞记录的 4 类查询（我的点赞列表 / 目标的点赞者列表 / 作者总赞 / 软删过滤）要走不同的索引。
- **具体实现**：`service/like/src/main/resources/db/migration/V1__create_like_record.sql` —— 每个索引的注释**直接写明它覆盖哪条查询的 WHERE + ORDER BY**：
  - `uk_user_target(user_id, target_type, target_id)` ← 幂等 + 并发
  - `idx_user_list(user_id, updated_at)` ← `GetUserLikeList`
  - `idx_target_list(target_type, target_id)` ← `GetTargetLikerList`
  - `idx_author(author_id)` ← `GetTotalLikeCount`
  - `idx_like_record_deleted_at(delete_at)` ← 软删除过滤
- **核心原理**：复合索引的最左前缀匹配；覆盖索引避免回表；索引顺序按「等值列在前、范围/排序列在后」排列。
- **技术选型**：★ **主动不加 GIN 索引**——Go 侧从未建过，补一个属于「新增结构」⇒ 会引入灰度期两侧读写不同结构的问题（DDL 注释里明确写了这个取舍）。
- **局限性**：无 `EXPLAIN` 验证（没有真实数据量下验证过是否命中）；article 域的 `secondary_tags @>` 过滤**无索引**（同理由继承 B 侧）。

## 二、消息队列（★★★）

### K-06 · 「至少一次 + 幂等」而不是「恰好一次」：分域设计重试策略
- **业务场景**：like / comment / article / task / hot 五个域消费同一批业务事件，但**对重复的容忍度完全不同**。
- **具体实现**（**按域刻意不同，且有注释论证**）：
  - **like**：不重试、失败也提交位点（对齐 Go `kq.ForceCommit=true`）—— `service/like/.../messaging/LikeUpdateKafkaListener.java:171-177`（`DefaultErrorHandler(recoverer, new FixedBackOff(0,0))`）。
  - **comment**：**失败不提交位点 ⇒ 必定重投**——`service/comment/.../CommentServiceApplication.java:129-144`（只记日志的 recoverer，刻意不抄 like 的 `FixedBackOff(0,0)`）。
  - **article**：`FixedBackOff(0,0)` 零重试 drop（`ArticleServiceApplication.java:185`，注释自陈 "the message is dropped, not redelivered"）。
  - **task / hot**：`AckMode.RECORD`。
- **核心原理**：Kafka 的交付语义只保证「至少一次」；「恰好一次」需要「幂等消费者 + 事务边界对齐」；**重试策略必须由业务语义决定**：可重复的写（计数类）用「幂等 + 立即提交位点」；不可重复的写（审核类）用「不提交位点 + 重投」。
- **技术选型**：不用事务消息（RocketMQ 特性，Kafka 没有）；用「位点提交策略 + DB 幂等」组合达成等效效果。
- **局限性**：★ **全仓无 DLQ** ⇒ 失败消息静默消失（article 审核消息丢失 ⇒ 文章永久卡 REVIEWING）；且 article 的日志写 "will retry" 与实际 drop 相反 ⇒ **对运维是误导**。

### K-07 · Outbox 模式：把「DB 写成功但 MQ 失败」变成可重放
- **业务场景**：文章审核通过后要发同步事件给下游（message 域）。
- **具体实现**：事务内写 `article_sync_outbox`（状态机 0待发/1已发/2失败 + `retry_count` + 唯一幂等键 `event_key = articleId:op:eventId`）→ `ArticleSyncOutboxRelay` 定时捞取（`status IN (0,2) AND retry_count < maxRetry`，maxRetry 默认 10）→ 成功 `markSent`，失败 `markFailed`（`service/article/.../messaging/ArticleSyncOutboxRelay.java:169-201`）。类似机制在 like/comment/favorite 三域各有 `*_fact_outbox`。
- **核心原理**：把「跨存储的原子性」降级为「同一事务内写本地消息表 + 至少一次投递 + 消费端幂等」；**不依赖分布式事务**。
- **技术选型**：对比「事务消息」（需 MQ 特定能力，Kafka 没有）、「先发 MQ 再写 DB」（消息会先于数据到达）、「全局事务」（性能与复杂度代价高）。
- **局限性**：① `fetchPending` **无 `FOR UPDATE SKIP LOCKED`** ⇒ 多实例重复投递（下游幂等兜住）；② **审核事件没有对应的 outbox** ⇒ 该路径仍是裸奔（这是 P0-2/P2-2 的改进点）；③ `article_domain_outbox` **只写不投** ⇒ 行只增不减。

### K-08 · 分区级有序性 + 重平衡不丢数据
- **业务场景**：热榜的统计必须在分区内保持顺序，否则热度值错乱；且消费者重平衡时不能丢已统计的数据。
- **具体实现**：`service/hot/.../config/HotKafkaConfig.java:136,165-187` 注册 `ConsumerRebalanceListener`：`onPartitionsAssigned` 从 Redis 载入该分区的 HeavyKeeper 快照（`HotEventConsumer.java:251-254`），`onPartitionsRevoked` 把状态 flush 回 Redis（`:264-267`）。
- **核心原理**：Kafka 的分区是并行度与有序性的基本单位；重平衡会重新分配分区，若状态只在内存里就会丢 ⇒ 必须有「分区间状态转移介质」（这里是 Redis ZSET + 影子键）。
- **技术选型**：对比「按分区独占进程」（无法水平扩展）、「全局锁串行」（吞吐塌）、「Redis 作为唯一真源」（内存与一致性问题）。
- **局限性**：Redis 快照有 TTL（分片 300s / 全局 3600s），**周期刷新失败 ⇒ 分片消失 ⇒ 全局榜变空**；且 `partition-count` 必须等于 topic 分区数，否则多分片永不合并（此约束只写在 yml 注释里，无断言）。

### K-09 · 至少一次下的「热度放大」陷阱（诚实讲局限的加分项）
- **业务场景**：hot 域消费 `article-hot-events` 累加热度权重。
- **具体实现**：`service/hot/.../messaging/HotEventConsumer.java:229` `hk.add(articleId, weight)`；payload `ArticleHotEvent` **只有 2 个字段（article_id + type），没有 event_id**（`service/hot/.../contract/ArticleHotEvent.java:38-41`）。
- **核心原理**：至少一次语义下重复消息必然到达；没有去重键 ⇒ 累加型消费者会被重复放大。
- **技术选型**：正确做法是 payload 带 `event_id` + SETNX 去重（task 域已有现成范式），但这属于契约变更（L1）⇒ 需决策。
- **局限性**：★ **这是本项目已知的真实缺陷**。面试中主动讲「我定位到了这个问题并给出了方案，但契约变更要走决策流程」，比假装没有更能体现工程判断。

## 三、缓存与 Redis（★★★）

### K-10 · 影子键 + Lua `RENAME`：让读者永不看到半份数据
- **业务场景**：热榜由多个分片合并而成，合并过程要改名多个 key；如果直接改，读者会读到中间态。
- **具体实现**：`service/hot/.../messaging/HotRedisSnapshotStore.java:108-135` —— 分片写入 `hot:articles:p{n}`，合并时先写 `hot:articles:shadow` 再用 Lua 原子 `RENAME` 替换；分片键 TTL 300s 硬编码在 Lua 内，全局键 3600s（yml 明确「两个过期时间不同，切勿统一」）。
- **核心原理**：Redis 的 `RENAME` 是原子的 ⇒ 名字切换瞬间完成 ⇒ 读者要么看到旧快照要么看到新快照；Lua 保证多步操作的原子性（Redis 单线程执行脚本）。
- **技术选型**：对比「MULTI/EXEC 事务」（多轮网络往返，且不解决跨 key 可见性）、「版本号 + 客户端重试」（把复杂度推给读侧）、「DEL + SET」（中间有空窗）。
- **局限性**：★ 影子键无 TTL ⇒ 异常路径可能残留；且**锁丢失不中断合并**（`HotMergeScheduler.java:250-252` 只 log.error）⇒ 两个实例可同时改名，结果不确定。

### K-11 · 分布式锁的完整形态：SETNX + 看门狗续期 + Lua 比对释放
- **业务场景**：多实例部署下，热榜合并必须单实例执行。
- **具体实现**：`service/hot/.../messaging/HotMergeScheduler.java:201-268` —— `SETNX` + TTL 10s 抢锁；看门狗每 3s 用 Lua **比对 value 后** `EXPIRE` 续期（`:107-112`）；释放用 Lua **比对 value 后** `DEL`（`:115-120`）⇒ 不会误删他人锁。
- **核心原理**：Redis 锁必须防「过期后被他人获取，原持有者却误删」⇒ 释放必须**校验持有者身份**；业务耗时可能超过 TTL ⇒ 必须**自动续期**（或用看门狗线程）。
- **技术选型**：对比「`SETNX` + 固定 TTL 不续期」（长任务必然误删）、「Redisson」（引新依赖，收益不匹配本项目规模）、「PG advisory lock」（无跨语言一致性但本项目全 Java）。
- **局限性**：★ **续期失败只打日志不中断合并** ⇒ 锁失效后业务仍在跑；且锁是**单机 Redis 锁** ⇒ Redis 故障切换时锁语义不保证。

### K-12 · 缓存击穿的教科书解法：singleflight + 双检 + 分档降级
- **业务场景**：评论主题信息、回复 ID 分页、评论索引、回复正文 —— 四类热点读，既不能每次打 DB，也不能因为缓存故障把 DB 打爆。
- **具体实现**：`service/comment/.../service/CommentCacheService.java`
  - **singleflight**：`:132` `private final ConcurrentHashMap<String, CompletableFuture<Object>> singleflight = new ConcurrentHashMap<>();`；`:192-193` `singleflight("subject:" + subjectId, () -> {…})` ⇒ **同一 key 的并发 miss 只回源一次**；`:375` 分页缓存同样走 singleflight。
  - **双检**：`:242`（外层一次 + singleflight 内一次）。
  - **差异化 TTL**：`:98-110`（5min 主题 / 3min 回复 ID 页 / 10min 评论索引 / 24h 回复正文）⇒ 不同数据变更频率不同，TTL 不统一。
  - ★ **分档降级（最有价值的部分）**：`:51-57` —— 缓存读失败时，`getSubjectWithCache` / `getReplyIdsPageCache` 打点后**继续回源 DB**（可用性优先），而 `getCommentIndexCache` / `batchGetContentCache` 打点后**直接返回错误不回源**（保护 DB）；`:70` 注释明确点出「读不到表现为静默回源 ⇒ 放大 DB 压力但不出错 ⇒ 这类漂移最难发现」。
  - **回填失败被显式忽略**：`:208-209`（对齐 Go `_ = c.SetSubjectCache(...)`）⇒ 缓存与 DB 存在短暂不一致，是**有意识的取舍**。
- **核心原理**：缓存击穿 = 热点 key 过期瞬间大量请求同时回源；解法是「互斥重建 + 双检」；singleflight 用「同一 key 共享一个 Future」把 N 次回源压成 1 次。缓存雪崩的解法是「TTL 差异化 + 容量冗余 + 降级策略」。
- **技术选型**：不引 Caffeine / 不引分布式锁 ⇒ 因为要防的是**单实例内的并发回源**，用进程内 singleflight 足够；跨实例防击穿靠 TTL 抖动/预热（当前未做）。
- **局限性**：① singleflight 是**单实例**语义 ⇒ 多实例下仍有 N 个回源（当前未做分布式锁或 TTL 抖动）；② 回填失败忽略 ⇒ 短窗口内数据可能陈旧；③ 缓存故障时「有的回源」仍会放大 DB 压力。

### K-12b · 什么时候**不该**用 Redis / 不该引入缓存治理三件套
- **业务场景**：面试高频问「怎么防缓存穿透/击穿/雪崩」「你用了 Caffeine 还是 Redis」。
- **具体实现**：★ **同一个项目里两种相反的决策并存** —— comment 域**确实需要**缓存（有热点读）⇒ 实现了 singleflight；而其余域**没有按 ID 查缓存的热点读路径**（hot 的读是常驻 ZSET；task 的读是进度缓存）⇒ **没有引入**空值占位、互斥重建、随机 TTL。
- **核心原理**：缓存治理手段是为「缓存读热点」服务的；没有这种读路径时引入它们是**纯粹的复杂度**（且空值占位会引入「假数据」语义问题）。用**数据库唯一索引 + 条件 UPDATE** 替代缓存层去重是更优解（如「标记已读」用 `WHERE is_read=FALSE` 的条件更新，天然幂等 —— `service/message/.../mapper/ConversationMessageMapper.java:41-52`）。
- **技术选型**：先问「**这个域有没有热点读**」，再决定要不要缓存；不是每个域都要配齐缓存全家桶。
- **局限性**：★ 面试时必须**两面都讲** —— 只讲「我实现了 singleflight」会被问「其他域为什么没有」，只讲「我没做缓存治理」会被问「那你们缓存怎么防击穿」。正确讲法是：「comment 有热点读所以做了，message/follow 的读是一次性事务性读所以用 DB 条件更新直接解决。」

## 四、并发与高可用（★★★）

### K-13 · Resilience4j 三态熔断器 + 每路由独立实例
- **业务场景**：10 个域之间有出向 gRPC 调用（article→message、comment→article 等）；下游抖动不能扩散。
- **具体实现**：`common/protection/RpcCircuitGateInterceptor.java:140`（服务端侧）与 `ClientCircuitGateInterceptor.java:140`（客户端侧）；`common/autoconfigure/ProtectionAutoConfiguration.java` 装配滑动窗口/半开策略/错误率阈值**自定义**参数；`RouteTemplateSource`（`:210,565`）让**每条路由有独立的 breaker**。
- **核心原理**：熔断三态（关闭/打开/半开）；滑动窗口统计错误率；半开状态放少量探测请求决定是否恢复；按路由隔离避免「一条慢路由拖垮整个客户端」。
- **技术选型**：★ **不用 Hystrix / Sentinel** —— Hystrix 已停止维护，Sentinel 需引入独立控制台；Resilience4j 是纯 Java 库、可编程装配、能表达 Go 侧的三态语义（注释自陈「Go 侧 force-pass + 无三态 ⇒ C 侧统一用 resilience4j」）。
- **局限性**：熔断参数是**自定义**的（不是 resilience4j 默认），需要按业务压测校准；当前无熔断指标的告警联动。

### K-14 · CPU 自适应降载：用千分比阈值做「丢车保帅」
- **业务场景**：Go 侧 `rest` 中间件有 CPU 阈值降载（`CpuThreshold: 900` = 90%），Java 侧要复刻。
- **具体实现**：各域 yml `rag.protection.cpu-shedding.enabled: true` + `cpu-threshold: 900` + `cpu-source: SYSTEM`；实现 `common/protection/CpuThresholdHealthIndicator.java`（注释明确写「resilience4j 无 CPU 降载等价物 ⇒ 若不自研就没有这个能力」）。
- **核心原理**：过载保护的三板斧（限流 / 熔断 / 降级）；CPU 阈值是**系统级**信号（区别于单请求的限流）；千分比避免浮点比较。
- **技术选型**：对比「Hystrix 的线程池隔离 + 信号量」（不能按 CPU 动态调整）、「只做限流」（不解决下游变慢导致的堆积）。
- **局限性**：单机口径（每实例独立判断）⇒ 集群下不精确；无「自适应阈值」（固定 90%，不是按延迟动态调）。

### K-15 · `MaxConnsFilter`：为什么 Tomcat 的 200 线程不够
- **业务场景**：Tomcat 默认 `max-threads=200`，超出后**请求排队**；而 Go 侧是**立刻 503**。
- **具体实现**：`common/protection/MaxConnsFilter.java:43-85` —— 注释把这段推理写得很清楚：「Tomcat 默认 max-threads=200 时请求会先在容器层排队，那时 Tomcat 的 200 早已先成为瓶颈；而运维把 max-threads 调到万级做压测时，B 侧会返回 503 而本仓若无此层会一直排队」。
- **核心原理**：**线程池排队 ≠ 快速失败**。当上游需要快速失败语义时，必须在容器之前加一层连接数闸门。
- **技术选型**：放在 `Filter`（Servlet 规范层，早于 Spring MVC）而不是 `Interceptor` ⇒ 因为要拦住**所有**请求（含静态资源）且在业务之前。
- **局限性**：★ 该闸门是**单机**的（不构成集群限流）；且 `server.tomcat.max-parameter-count` 的 yml 值与共享层硬编码值冲突（见 K-21）。

### K-16 · 线程池三层闸门为什么是过度设计（诚实讲「我改了什么」）
- **业务场景**：热榜列表需要为每篇文章补齐详情（hydrate），要限制并发。
- **具体实现**：`ThreadPoolTaskExecutor`(core=max=**64**, queue=**64**, `CallerRunsPolicy`)（`service/hot/.../config/HotHydrationExecutorConfiguration.java:101-107`）之上再叠 `Semaphore(HYDRATION_CONCURRENCY=8)`（`service/hot/.../service/HotApiService.java:124,307`）。
- **核心原理**：线程池的 `core/max/queue` 已经定义了并发上限；额外加信号量只会让「配置宣称的并发度」与「实际生效的」不一致。
- **技术选型**：★ **正确做法是二选一**（本次审计的 P1-1 建议删信号量，把并发度写进池参数）。
- **局限性**：★ 面试中讲「我发现自己写了三层闸门、真正生效的是信号量 8，于是合并成一层」是**非常好的反思型素材**，比「我用了线程池 + 信号量」更好。

### K-17 · ThreadLocal 传 deadline：跨线程 / 跨 Redis / 跨 gRPC 的请求级超时
- **业务场景**：一次请求有 70s 预算（HTTP + gRPC 两套），但 Redis 调用、gRPC 调用可能换线程 ⇒ 超时预算会丢失。
- **具体实现**：`common/redis/DeadlineConnectionFactory.java`（把 deadline 注入 Redis 连接）、`common/observability/` 的 deadline 载体、`common/persistence/` 的 SQL 超时注入（`DeadlineQueryTimeoutInjector`）。
- **核心原理**：`ThreadLocal` 让「请求上下文」随线程传递；配合 `InheritableThreadLocal` / 线程池包装可跨线程；Spring 的 `RequestContextHolder` 是同类思路的框架版。
- **技术选型**：对比「参数显式层层传」（侵入所有方法签名）、「全局变量」（并发不安全）、「`CompletableFuture` 上下文传播」（Java 21 尚无官方 API）。
- **局限性**：★ **ThreadLocal 内存泄漏**是本题必追问 —— 本项目靠「连接创建时读取并清理」规避，但若在线程池中长期驻留仍需 `remove()`；且 `InheritableThreadLocal` 在线程池场景会拿到**创建时**的上下文（经典坑）。

## 五、Spring 与工程化（★★★）

### K-18 · 自研 14 个 AutoConfiguration：讲清「谁装配了什么」
- **业务场景**：10 个域都需要同一套 Web 强转、链路透传、熔断、SQL 超时、Jackson coercion。
- **具体实现**：`common/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports:1-14`；`MybatisPlusOrderingBridgeAutoConfiguration.java:71-77`（**只建立 `@AutoConfiguration(afterName/beforeName)` 排序边、零 bean**）；`common/src/test/.../AutoConfigurationImportsTest.java:33-56` 断言每个 auto-config 都有真实消费点。
- **核心原理**：Spring Boot 3 的自动配置 = **SPI（`AutoConfiguration.imports`）+ 条件装配（`@ConditionalOnClass`/`@ConditionalOnMissingBean`）+ 排序边（`after`/`before`）**；`@ConditionalOnMissingBean` 让业务侧能覆盖默认实现。
- **技术选型**：不用 `@Import` 清单（那是 B 侧 go-zero 的做法，本项目按 D3 决策放弃）；不用 `spring.factories`（Boot 2 旧机制，Boot 3 已废弃）。
- **局限性**：★ 排序边的 groupId 写错（`org.xolstice.maven.plugins` 应为 `kr.motd.maven`，`proto/pom.xml:29-32` 已自述）⇒ 靠各模块显式 `<extension>` 绕开；且「零 bean 的 auto-config」容易让新人误以为是空壳。

### K-19 · 框架机制必须验证实际生效（本项目最有价值的工程纪律）
- **业务场景**：「类上有 `@Transactional`」「有 `@KafkaListener` 依赖」**都不等于机制生效**。
- **具体实现**：
  - `@KafkaListener` 必配**装配层断言**：listener 真进 `KafkaListenerEndpointRegistry`（`service/like/.../LikeServiceApplicationTests.java:109-115`；`service/comment/.../CommentServiceApplicationTests.java:119-125`；`service/task/.../TaskKafkaListenerAssemblyTest.java:24-26`）。
  - AOP 代理断言（`service/article/.../wiring/SnowflakeBootstrap.java:99-114`）。
  - **变异测试式断言**：去掉 `@Transactional` 就应失败（`ArticleAtomicServiceRealPgTest.java:53,282-285`）。
  - 已按纪律**删除 `@EnabledIfDockerAvailable`**（`service/comment/.../support/TestPostgres.java:25-28`）⇒ 容器不可用直接红，不假绿。
  - 「配置里没写 ≠ 没开」：`observability.http-timeout`/`rpc-timeout` 缺省即 `Duration.ZERO`（不限时）⇒ 注释明确写出这个隐性坑（各域 yml observability 段）。
- **核心原理**：Spring Boot 的条件装配、AOP 动态代理、`@KafkaListener` 的容器注册都是**运行期**行为；**编译通过 / 能启动 / 类上有注解**三者都不构成证据。
- **技术选型**：用**真容器 + 装配层断言 + 变异测试**替代「Mock 一切」；Testcontainers 提供真 PG/Kafka/Redis/MinIO。
- **局限性**：★ 真 Kafka 测试只有 8 个文件（3%），**task 域的 Kafka 端到端被 `@Tag("external-env")` 默认排除** ⇒ **从未在默认回归跑过**；users/user 域仅 7 个测试类（admin 有 23）⇒ 登录/注册主链路缺真 PG 断言。

### K-20 · 「不引入」的技术也要能讲（选型判断力）
- **业务场景**：面试官问「为什么没上 ES / 向量库 / 分库分表」。
- **具体实现**：全仓 pom + java + yml 三重 grep 命中 0（ES / Milvus / Neo4j / RocketMQ / RabbitMQ / ZooKeeper / Dubbo / 分库分表中间件）；且**架构上已「能分」**：雪花 ID（全局唯一）+ 无外键（免跨库 JOIN）+ 唯一索引幂等（不依赖分布式锁）+ `public` schema 共享库（易于垂直拆库）。
- **核心原理**：技术选型的第一问是「**当前业务规模需要吗**」；以及「**不引入的代价是什么**」（引入 ES 就要处理双写一致性、引入分库分表就要处理全局 ID/跨库 JOIN/分布式事务）。
- **技术选型**：本项目选了「**按数据所有权划限界上下文 + 单库 + 一个 MQ + 一套缓存**」的最小充分集；热度用 Redis ZSet + HeavyKeeper 解决（未上 ES）。
- **局限性**：★ 这也是**双刃剑** —— 面试若只问「你用过 ES 吗」，本项目答不上来；因此建议在简历里**明确写出「为什么没上」**，把它变成选型能力而不是短板。

## 六、网络与协议（★★）

### K-21 · HTTP 与 gRPC 同进程双通道的异常处理分离
- **业务场景**：D1 决策把 api 与 rpc 合并为一个进程 ⇒ 同一进程同时起 Tomcat 与 gRPC server。
- **具体实现**：`advice/`（`@RestControllerAdvice`，HTTP）vs `exception/` + `GrpcExceptionMapperAutoConfiguration`（gRPC，业务码进 trailer，`GrpcExceptionMapperAutoConfiguration.java:57,115,156`）；`common/web/GrpcStatusMapper.java` 做状态码 ↔ 业务码双向映射。
- **核心原理**：HTTP 的错误形状（HTTP 状态码 + JSON 信封）与 gRPC 的错误形状（Status code + description + trailer 业务码）**是两套契约**；同一进程里必须分别处理，且**业务错误码要能跨通道保真**。
- **技术选型**：用 trailer 携带业务码 ⇒ 跨域调用方拿到的仍是**业务码**而非 `UNKNOWN`。
- **局限性**：★ 出现了**四套**错误处理心智模型（HTTP advice / gRPC mapper / users 的 `BusinessException` / users-admin 的 `StatusRuntimeException`）⇒ 新人成本高（users 域内两套纯属不一致，可统一）。

### K-22 · 两套超时预算与出向 deadline
- **业务场景**：一次请求有 70s 总预算，但内部还要调下游。
- **具体实现**：`observability.http-timeout: 70s` + `observability.rpc-timeout: 70s`（**缺省即不限时** ⇒ 注释明确写出这个坑）；出向 `rag.protection.outbound-deadline.cap-millis: 2000` + 每路由 breaker；Redis/SQL 侧由 `DeadlineQueryTimeoutInjector` 注入。
- **核心原理**：**分布式超时预算**必须自顶向下传递（deadline 传播），否则每一跳都重置超时 ⇒ 总时长不可控；且「配置缺键 = 不限时」是 Spring `Duration` 绑定的隐性行为。
- **技术选型**：用 ThreadLocal 载体传播 deadline（见 K-17），而不是给每个方法加 timeout 参数。
- **局限性**：★ 共享层的 `cap-millis` 是**模块级一个数**，**表达不了 Go 侧 per-client 的 timeout 语义**（Go 的 `Timeout` 挂在 client 配置上）⇒ 已在 yml 注释登记为「归 G4 写权，不擅自绕开」。

### K-23 · JWT：自研 Filter + Interceptor 而非 Spring Security
- **业务场景**：8 个域都要「Bearer token 验签 + 身份注入 + 登出即失效」。
- **具体实现**：jjwt 0.12 + HS256（`common/security/JwtUtil.java:44`，HMAC key 不足 32 字节时补齐）；Filter 验签放 request attribute → Interceptor 消费 + 查黑名单 + 注入 `userId`（`service/users/user/.../interceptor/{JwtAuthFilter,JwtAuthInterceptor}.java`）；密钥只从 env 注入，**无默认值**，缺变量则**启动失败**（`ArticleApiProperties#verifyAccessSecret`）。
- **核心原理**：Spring Security 的默认栈是「form login + session」，与本项目的「无状态 JWT + 自定义错误形状」不匹配 ⇒ 自研更省；`@PreAuthorize` 需要方法级启用且要引入完整 Security 上下文。
- **技术选型**：不引入 `spring-boot-starter-security`（只引 `spring-security-crypto` 用它的 BCrypt）⇒ 避免「默认安全头/默认登录页/默认 CSRF」等与 B 侧行为冲突的副作用。
- **局限性**：★ claims 只有 `userId`、**没有 `status`**（封禁靠每次查库）⇒ 每次请求都打一次 DB；**无 refresh token**（错误码 1007 继承 B 侧但未使用）；黑名单查询 **fail-open**（Redis 故障放行）；两套近同构栈（user/admin）。

### K-24 · 密码哈希与 bcrypt 的 72 字节边界
- **业务场景**：注册 / 改密 / 管理员建号 / 重置密码。
- **具体实现**：`common/security/PasswordUtil.java:49`（`BCryptPasswordEncoder(10)`）；★ bcrypt 的 **72 字节上限**被刻意置于「邀请码校验 / 重名检查」之后（`service/users/admin/.../domain/service/AdminCreateAtomicService.java:89-107`，含实测证据）；HTTP DTO 不含 password（`service/users/user/.../dto/user/UserInfo.java:40-46`）。
- **核心原理**：bcrypt 自带 salt + 故意慢 ⇒ 抗暴力破解；代价是**超过 72 字节的部分被静默截断** ⇒ 两个不同的超长密码可能哈希相同。
- **技术选型**：不用 MD5/SHA（快 ⇒ 可暴力）、不用裸 SHA 加盐（不够慢）。
- **局限性**：⚠️ **默认管理员 `admin/admin` 硬编码**（`AdminDomainService.java:154,164`）+ 重置密码默认明文 `123456`（`admin-rpc.system.default-password`）⇒ 本次审计列为 **P0-3**。

## 七、可观测性与运维（★★）

### K-25 · 「业务失败恒 200 + 信封」与逐域错误码隔离
- **业务场景**：跨域调用方需要用**业务码**而不是 HTTP 状态码判断失败。
- **具体实现**：每域独立 `contract/ErrCodes`（article 中文文案、hot 英文文案）；`advice/*ApiResponseAdvice` 统一包信封；`advice/*ApiExceptionHandler` 把异常映射到「200 + 信封」/ 401 / 400 裸文本 / 404 裸（article 的 405 → 404 是已登记漂移，`ArticleApiExceptionHandler.java:375-380`）。
- **核心原理**：HTTP 状态码表达**传输层/协议层**结果，业务码表达**业务语义**；混用会导致「404 既表示资源不存在又表示方法不允许」。
- **技术选型**：逐域隔离而非提取共享基座（项目纪律「未统一化」）。
- **局限性**：★ **号码可重叠、语义不同**（hot 的 5002 = invalid_param，article 的 5002 = db_update）⇒ 跨域聚合日志必须按域判读；users 域还有两套错误码形态。

### K-26 · 自研日志载体（`GoStyleLogger`）的动机与代价
- **业务场景**：需要保留 B 侧 `call_chain` 字段以便对照排障，但 Spring Boot 默认的 SLF4J 载体不带它。
- **具体实现**：`common/logger/GoStyleLogger.java`（992 行）+ `LoggerFactoryBean` + `LogOptions`；因此**禁 `@Slf4j`**（项目纪律）。
- **核心原理**：日志载体与 `slf4j` API 解耦 ⇒ 可在实现层加结构化字段，不影响调用方写法。
- **技术选型**：不用 `@Slf4j`（拿不到 `call_chain` 字段）⇒ 全部改为 `LoggerFactoryBean` 显式获取。
- **局限性**：992 行的自研日志组件是**全仓最大的单类**，属于「为了行为等价而付出的表达层成本」；面试讲「我为什么不用 @Slf4j」是加分，但被追问「这 992 行值得吗」时，唯一诚实答案是「在 D16 政策下值得，若允许自由设计则不必」。

   - **Redis 的原子性设计：影子键 RENAME + 看门狗锁**（K-10/K-11）—— 与「分布式锁为什么要校验持有者」这一高频追问对上。
3. **技术选型判断力**（30 秒）：明确说出 **ES / 向量库 / Milvus / 分库分表 都不需要**，并给出「架构上已能分」的证据（K-20）。
4. **诚实讲局限**（30 秒）：hot 消费者无幂等（K-09）；article 审核事件无 outbox（K-07）；并发闸门三层重叠（K-16）—— **每个都带改进方案**。
5. **不要主动讲的**：任何占位实现（hot 的 4 个交互方法、article 的内容审核桩）—— 面试官一问「这个真的实现了吗」，答「是占位」会毁掉前面 4 分钟。
