# 架构符合性断言（A1–A15）

> **本文档回答一个具体问题**：*「文件树有没有漂移」怎么测？*
>
> **答案**：它**不是差分问题**（两个实现比行为），而是**符合性问题**（一个实现比规范）。差分需要真源，符合性只需要**可执行的规则**。

---

## 〇、为什么不是差分对拍

| | 差分对拍 (differential) | 符合性检查 (conformance) |
|---|---|---|
| 问什么 | A 和 B **行为一样**吗? | 这个实现**符合约定**吗? |
| 需要几个实现 | **2 个** | **1 个** + 一份可执行规则 |
| 证据形态 | 请求矩阵 + 双进程 + 字节 diff | 断言集（红的 = 漂移） |
| B ↔ C | ✅ 就是这个 | — |
| 「像不像纯 Spring」 | ❌ **做不了**（都不是 B 侧的东西，没有可比基线） | ✅ **这个能测** |

⇒ **"纯 Spring 的文件树"没有客观答案** —— Spring 官方从未规定过文件树，它规定的是 ① API 契约 ② auto-configuration 清单。
⇒ 所以真正可测的命题是：

> **这个能力 Spring 已经提供了 —— 你是自己手写了一遍，还是用了它？**

---

## 一、断言清单

### A1 · `*-rpc` 的 classpath 不得有 `spring-boot-starter-web`

| 项 | 内容 |
|---|---|
| **判据** | `mvn dependency:tree` ⇒ `*-rpc` 模块不得出现 `spring-boot-starter-web` |
| **理由** | `*-rpc` 是纯 gRPC 进程。引入 web starter 会被拉起 Servlet 容器，白占一个 HTTP 端口。 |
| **例外** | `task-rpc` / `message-rpc` 需 `spring-boot-web-server` 里的某个类 + 抽象接口 ⇒ 用**精确 artifact 坐标**引入 `spring-boot-web-server`，**不是** starter。 |
| **RAG 现状** | 🟢 10/10 通过 |

### A2 · `*-api` 必须有 `spring-boot-starter-web`

| 项 | 内容 |
|---|---|
| **判据** | `mvn dependency:tree` ⇒ `*-api` 必须出现 `spring-boot-starter-web` |
| **理由** | `*-api` 是 HTTP 进程。 |
| **RAG 现状** | 🟢 10/10 通过 |

### A3 · gRPC 拦截链必须**真挂到 server 上**（两个契约各一套判据）

| 项 | 契约 A（api/rpc 分离 · RAG 形态） | 契约 B（api+rpc 合并 · **RAG-V1**） |
|---|---|---|
| **判据** | 解析 `*Application.java` ⇒ 存在 `GrpcServerConfigurer` 实现，且其中调用了 `server.intercept(...)` | ① `common/` 必须**声明** `GrpcServerConfigurer` 且真调 `server.intercept(...)`；② **域内不得再声明** `GrpcServerConfigurer` |
| **理由** | `RpcServerInterceptorFactory` 只产出 `ServerInterceptor` **Bean**；**不挂到 server 上则整条拦截链静默失效**（超时 / 业务码分类 / `sea.slow` 标记全丢）。⚠️ 这是"注解存在 ≠ 机制生效"的活样本。 | ① 同左（devh starter 只注入 `List<GrpcServerConfigurer>` ⇒ 不产 Configurer ⇒ 链装不上）；② 重复声明 ⇒ **同一条链被挂 2 次** ⇒ span 重复、timeout 叠加 |
| **落点** | 每个 `*-rpc` 模块各写一遍 | **共享层 1 份**（D1 合并的收益：一域一进程 ⇒ 每进程 1 个 gRPC server ⇒ 1 个全局 Configurer 即覆盖 10 个域） |
| **RAG 现状** | 🟡 **10 个 rpc 模块只有 6 个真挂了**（like / comment / follow / favorite / task / hot）⇒ **message / user / admin 三个域的拦截链静默失效**；RAG 自己的 javadoc 承认「锁死用例 `LikeGrpcInterceptorWiringTest` **全仓不存在**」<br>⚠️ **（2026-11-02 核对）**：B 侧已补齐 ⇒ **10/10 都有 `public GrpcServerConfigurer rpcInterceptorConfigurer(...)`** ⇒ 上面的「6/10」是 **2026-10-26 快照**，不是当前态 | —— |
| **RAG-V1 现状** | —— | ⏳ **PENDING** —— 挂载点类 `ProtectionAutoConfiguration` 仍是空壳 ⇒ 判据未施加（落地实现后自动转 PASS/FAIL） |

> ⚠️ **这条断言**不是**「api/rpc 分离」的派生物** —— **B 侧范围内 10 个 rpc 模块逐条显式**实现
> `GrpcServerConfigurer`，在 `server.intercept(...)` 里挂上 `RpcServerInterceptorFactory` 产出的拦截链
> （`service/{like,comment,follow,message,favorite,task,hot,article}/*-rpc` + `service/users/{user,admin}/*-rpc`）
> ⇒ 合并后仍要挂，只是**挂载点从「每 rpc 模块」变成「共享层 1 份」**。
> ⇒ 设计依据 ⇒ [`完全spring化的文件树.md`](完全spring化的文件树.md) §5.5.2。

> ⚠️ **源码扫描只是「形状守门」，不是「机制验证」** —— A3 判的是源码里**有没有** `server.intercept(...)`，
> 而**真的挂上了**要靠运行期证据（§3.3 的「真触发」测试）⇒ 落地实现时必须补一条
> 「起真 gRPC server ⇒ 断言拦截器真的进了调用链」的测试（RAG 缺的就是这条）。

### A4 · 每个 `@GrpcClient("X")` 必须在同模块 yml 有 `negotiation-type: plaintext`

| 项 | 内容 |
|---|---|
| **判据** | 交叉引用：`src/main/java` 里的 `@GrpcClient("X")` ⟷ 同模块 `application.yml` 的 `grpc.client.X.negotiation-type` |
| **理由** | devh `GrpcChannelProperties` 的默认值是 **TLS**；**B 侧全靠 yml 显式写 `negotiation-type: plaintext`** 才拿到明文通道 ⇒ **不写会静默变 TLS**。 |
| **RAG 现状** | 🟡 **2 处哑弹**（见下） |

### A5 · 每个模块的 `@Import` 清单为空（starter 化之后）

| **RAG 现状** | 🔴 9 份重复 |

| 项 | 内容 |

### A11 · B 侧 `fact-*` 装配能力 ⇒ 域内必须有对应装配落点

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ `comment` / `favorite` / `like` 三域各须存在 `wiring/<域>FactDispatchScheduler` 与 `wiring/<域>AuthorityEndpointConfig`；三域各须存在 `wiring/<域>FactProcessLogging` |
| **理由** | **B 侧**这三域各有 fact-dispatch 调度器 + authority 端点配置 + 进程日志身份类（`LikeFactDispatchScheduler` / `LikeAuthorityEndpointConfig` / `LikeFactProcessLogging` 等），**全部零对外服务** ⇒ 可并入域内组件（见 [`决策记录.md`](决策记录.md) D1 的例外判定撤销）。<br>⚠️ 但「可合并」≠「已合并」—— 树里没有落点 = **该能力在实现阶段会被整个漏掉**，而漏掉它不会有任何编译错误或测试红灯（正是 RAG `article-rpc` 2 颗哑弹的同款形态）。 |
| **RAG 现状** | 🟢 三域均有（`mq/` 与 `fact/` 包下各 2 个 + `bootstrap/LikeFactProcessLogging`）—— ⚠️ 但 RAG 把它们放三个不同的包（`mq/`·`fact/`·`bootstrap/`），本身就不一致 |
| **RAG-V1 现状** | 🟢 2026-10-25 补齐：三域统一放 `wiring/`（6 个装配类 + 3 个日志身份类）<br>✅ **2026-10-25 二次订正**：守门脚本首次实跑发现 **`comment` 域实际缺 `CommentFactProcessLogging`**（只有 like / favorite 域有）⇒ 三份 logger 身份在该域**没有落点** ⇒ 已补，三域各 3 个落点齐备。⚠️ 该缺口**零编译错误 + 零测试红灯**，只有机器能抓 ⇒ 见 [`Pitfalls/_cross/P-08-落地证据未经机器复算.md`](Pitfalls/_cross/P-08-落地证据未经机器复算.md) |

### A12 · 一个模块内不得有同名简单类

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ 同一 Maven 模块内，两个 `.java` 文件的**简单类名**不得相同（不同包也不行） |
| **理由** | 同名类 ⇒ 职责重复，且**按简单类名检索时必然二义**。RAG-V1 曾有 `com.rag.like.mq.metrics.LikeMqMetrics` 与 `com.rag.like.rpc.metrics.LikeMqMetrics` 并存，且其中一个是**无契约的空壳** ⇒ 后写实现的人会填错那一个。 |

### A13 · 用了 Lombok ⇒ 必须在该注解正上方写「原本的完整代码」展开块

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ **凡类上出现 Lombok 注解**（`@Data` / `@Getter` / `@Setter` / `@NoArgsConstructor` / `@AllArgsConstructor` / `@RequiredArgsConstructor` / `@Builder` / `@Value` / `@EqualsAndHashCode` / `@ToString` / `@Slf4j` / `@Cleanup` / `@SneakyThrows` / `@UtilityClass`）⇒ 该类**紧贴声明**的 javadoc 必须含 **`Lombok 展开` 标记** + 一个 **`<pre>{@code …}</pre>`** 块 |
| **理由** | Lombok 把代码移出源码 ⇒ **review 的人看不到「原本长什么样」** ⇒ 而 B 侧是唯一 oracle（D16）⇒ 没有展开块 ⇒ Lombok 化 = **不可对照的黑盒**（正是「拿一面没人校过的镜子照自己」的同款形态）⇒ ⇒ 本条把 §3.1 的对照纪律**机械化** |
| **边界** | ① 只认**类上**的注解（字段级/方法级不在本条范围）② 只认**紧贴类声明**的那段 javadoc（远处无关的 javadoc 不算 ⇒ 防假绿）③ 展开块**内容是否与代码一致**仍需人眼（机器只验「有没有」） |
| **RAG-V1 现状** | 🟢 **2026-11-02 已实现** —— D18 落地后补齐现存 5 个 Lombok 类的展开块（`common/contract/ApiResponse` · `common/communityfact/SubjectRef` · `admin` 域 3 个实体）；**2026-11-02 阶段二**：`service/users` 下 **10 个纯样板类** Lombok 化（2 实体 + 4 metrics + 4 Properties）⇒ **全仓 15/15 个 Lombok 类均带展开块**（A13 实测 PASS 15/15）⚠️ 其中 `user` 域 2 个实体**只加 `@Getter`+`@Setter`**（原本无 `equals`/`hashCode`/`toString` ⇒ 加 `@Data` 会**新增方法 = 行为变化**）⇒ **Lombok 注解的选用本身也是行为决策** |
| **落地证据** | `tools/difftest/check-arch-invariants.py --self-test` ⇒ **14/14 判据均能红**（含 A13：造「有 `@Data` 但缺展开块」的假树 ⇒ 判红）⇒ **不是假绿断言** |

### A14 · 追踪导出配置（`otel:` 段）齐备且服务名自洽

| 项 | 内容 |
|---|---|
| **判据** | 静态检查（yml）⇒ **① 白名单**：清单内各域的 `application.yml` 必须有 `otel:` 段，且 `otel.exporter.otlp.endpoint` **非空**、`otel.exporter.otlp.protocol` = `grpc`、`otel.traces.sampler` ∈ {`always_on`, `parentbased_always_on`}、服务名与该域 `spring.application.name` **相等**（两套拼法 `otel.service.name` / `otel.resource.attributes.service.name` 同时出现时**还须彼此相等**）；**② 通用规则**：**任何**域只要 yml 里**有** `otel:` 段，就必须满足上面那组条件 |
| **理由** | 共享层 `GoStyleOtelConfig` 按 B 侧的 ``if len(c.Endpoint) > 0`` 口径 —— **端点为空就不装 exporter** ⇒ ⇒ 缺 `otel:` 段 ⇒ **零编译错误、零测试红灯**（配置面缺一整段 ⇒ 没有任何代码路径会报错）⇒ ⇒ 该域的 span **一条都导不出去**（跨域链路在 Jaeger 侧断链）⇒ ⇒ **静默失效**（与 A2/A3/A4 同款「哑弹」形态，只是这次哑的是**配置面**） |
| **边界** | ① **判据钉的是「不变量」而不是「字面值」** —— 服务名一律与该域自己的 `spring.application.name` 比 ⇒ ⇒ 域改名 / 目录改名时判据**自动跟随** ⇒ ⇒ 不会假红；② 值侧只钉住「协议 = `grpc`」（= B 侧 `Telemetry.Batcher: otlpgrpc`）与「sampler 属两族」（两者都被共享层 `toRatio` 映射成 ratio = 1.0 ⇒ 行为等价）；③ 白名单是**显式清单**（新增域由人决定要不要进）⇒ ⇒ **通用规则**负责兜住清单外的域（写出来就必须合规）⇒ ⇒ 白名单不会随每次合入而腐烂 |
| **RAG-V1 现状** | 🟢 **2026-11-05 已实现** —— A14 实测 **PASS 9/9**（清单：article / comment / favorite / follow / like / message / task / users-admin / **users-user**）⇒ 起因 = **comment / favorite / message / task / user-service 五域 + hot 域**的 `otel:` 段**整段缺失** ⇒ 端点为空 ⇒ 不装 exporter ⇒ span 导不出去 ⇒ 已由 `global` 收口域**统一补齐**（6 域同构）⇒ ⚠️ **`hot` 域的实现尚未合入 main**（主干里还是空壳 + 48 行的 yml 桩）⇒ 它那份 `otel:` 段在 `align/hot` 分支上 ⇒ **合入后自动被通用规则覆盖**（⚠️ **不要**为了让它进清单而去改主干的 hot yml ⇒ 那是 48 行的桩 ⇒ 合并必冲突） |
| **落地证据** | `tools/difftest/check-arch-invariants.py --self-test` ⇒ **14/14 判据均能红**（含 A14：造「有 yml 但缺 `otel:` 段」的假树 ⇒ 判红）⇒ **不是假绿断言**；另做**变异实测**（删掉某域的 `otel.exporter.otlp.endpoint` ⇒ A14 当场报「缺失或为空 ⇒ 不装 exporter」⇒ 还原后复绿） |

### A15 · 保护层的每个 `enabled` 开关都必须**真的接到层上**（接线守门）

| 项 | 内容 |
|---|---|
| **判据** | 静态检查（Java 源码）⇒ 从 `common/…/protection/ProtectionProperties.java` 里**解析出带 `enabled` 字段的嵌套类** ⇒ 每个就是一枚开关 ⇒ ⇒ 逐枚核对：**共享层**（`common/src/main/java`）里**必须有人读它的 `isEnabled()`**（直接形态 `getX().isEnabled()`，或间接形态「先把开关对象存进局部变量再读」） |
| **理由** | `DRIFT-COMMON-V16` 的原形态 —— `rag.protection.stat.enabled` / `rag.protection.prometheus.enabled` 这两个开关在 C 侧**从来没被读过** ⇒ ⇒ 置 `false` 也毫无效果（**该层恒装**）⇒ ⇒ **零编译错误、零测试红灯** ⇒ ⇒ 只有「某个域真的去关它」的那一天才会显形 ⇒ ⇒ **静默失效**（与 A2/A3/A4/A14 同款「哑弹」形态，这次哑的是**开关面**） |
| **边界** | ① **判据钉的是「不变量」而不是「字面值」** —— 清单由脚本**自己从属性类里解析** ⇒ ⇒ **将来新增的开关自动进清单** ⇒ ⇒ 不必改脚本 ⇒ ⇒ 清单不会腐烂；② **消费点只在共享层找** —— 保护层的装配点全在 `common/` ⇒ ⇒ 域侧读它不构成「这层装不装」的判据；③ ⚠️ **判据会先剥掉注释与字符串字面量** —— 本仓 javadoc 里**大量引用 B 侧源码**（如 `if (props.getStat().isEnabled())`）⇒ ⇒ 不剥离的话，「接线被摘掉」也照样绿 ⇒ ⇒ **假绿**（AGENTS.md §3.1「不要拿代码注释当对照基准」的机器化形态） |

| **落地证据** | ① `tools/difftest/check-arch-invariants.py --self-test` ⇒ **15/15 判据均能红**（含 A15：造「有开关但零消费点」的假树 ⇒ 判红；⚠️ 该假树里**故意**放了一句**注释里**的 `props.getStat().isEnabled()` ⇒ 判据仍判红 ⇒ **证明它不会被注释骗到**）⇒ **不是假绿断言**；② **真仓变异实测**：把 `rpcStatInterceptor` 的接线摘掉（写死 `true`）⇒ A15 当场报「`Stat` 共享层零消费点 ⇒ 该层恒装（零编译错误、零测试红灯 ⇒ 静默失效）」⇒ 还原后复绿；③ 另有**行为层守门** `common/src/test/java/com/rag/common/observability/ProtectionLayerSwitchWiringTest.java`（**4 例 · 真 Spring 装配 + 真 in-process gRPC 调用** ⇒ 开关关掉 ⇒ Stat 层不记样本 ＋ 不起那条 60s 上报线程、Prometheus 层一条指标都不写；**两轮变异** ⇒ 抽接线 2 红 / 只抽线程门 1 红且红在 `reporterStarted()` ⇒ 还原 4/4 绿） |

## 二、RAG 现状的 2 颗哑弹（A4）

> **这是本清单实测时发现的现存隐患，不是新问题。**

| 模块 | 现象 | 当前后果 | 引爆条件 |
|---|---|---|---|
| `article-rpc` | `application.yml` 配了 `grpc.client.security-rpc` 与 `grpc.client.message-rpc`，**两者都缺 `negotiation-type: plaintext`** | **无害** —— 全仓没有对应的 `@GrpcClient` bean，通道建了但没人用 | **任何人补上一行 `@GrpcClient("message-rpc")`** ⇒ devh 默认 TLS ⇒ 连不上明文 gRPC ⇒ **而所有测试都是绿的**（测试用 `@SpringBootTest(properties = "grpc.client.xxx-rpc.negotiation-type=plaintext")` **在测试里注入**了它） |

> ⚠️ **教训（比这个 bug 本身更重要）**：
> **测试注入会掩盖生产配置的缺失。** 测试自己把值设上了 ⇒ 断言永远成立 ⇒ 生产配置可以一直是错的 ⇒ **没有人会发现**。
> ⇒ 这就是"沉默不变量"最危险的形态：**它不仅会被漏掉，还会被测试主动掩护。**

## 四、例外必须显式声明

`hot-rpc` 没有 `@MapperScan` —— **因为它确实没有 mapper 包**。这不是违规，是例外。

| 规则 | 说明 |
|---|---|
| 例外必须**写进断言文件** | 不能靠"大家都懂" |
| 例外必须**写理由** | 否则例外会变成默认 |
| 没有写进文件的"例外" = 违规 | 断言不认口头豁免 |
