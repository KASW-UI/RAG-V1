# 架构符合性断言（A1–A12）

> **本文档回答一个具体问题**：*「文件树有没有漂移」怎么测？*
>
> **答案**：它**不是差分问题**（两个实现比行为），而是**符合性问题**（一个实现比规范）。差分需要真源，符合性只需要**可执行的规则**。

---

## 〇、为什么不是差分对拍

| | 差分对拍 (differential) | 符合性检查 (conformance) |
|---|---|---|
| 问什么 | A 和 B **行为一样**吗? | 这个实现**符合约定**吗? |
| 需要几个实现 | **2 个** | **1 个** + 一份可执行规则 |
| 证据形态 | 请求矩阵 + 双进程 + 字节 diff | 断言集（红的 = 漂移） |
| Go ↔ RAG | ✅ 就是这个 | — |
| 「像不像纯 Spring」 | ❌ **做不了**（都不是 Go 的东西，没有可比基线） | ✅ **这个能测** |

⇒ **"纯 Spring 的文件树"没有客观答案** —— Spring 官方从未规定过文件树，它规定的是 ① API 契约 ② auto-configuration 清单。
⇒ 所以真正可测的命题是：

> **这个能力 Spring 已经提供了 —— 你是自己手写了一遍，还是用了它？**

---

## 一、断言清单

### A1 · `*-rpc` 的 classpath 不得有 `spring-boot-starter-web`

| 项 | 内容 |
|---|---|
| **判据** | `mvn dependency:tree` ⇒ `*-rpc` 模块不得出现 `spring-boot-starter-web` |
| **理由** | `*-rpc` 是纯 gRPC 进程。引入 web starter 会被拉起 Servlet 容器，白占一个 HTTP 端口。 |
| **例外** | `task-rpc` / `message-rpc` 需 `spring-boot-web-server` 里的某个类 + 抽象接口 ⇒ 用**精确 artifact 坐标**引入 `spring-boot-web-server`，**不是** starter。 |
| **RAG 现状** | 🟢 10/10 通过 |

### A2 · `*-api` 必须有 `spring-boot-starter-web`

| 项 | 内容 |
|---|---|
| **判据** | `mvn dependency:tree` ⇒ `*-api` 必须出现 `spring-boot-starter-web` |
| **理由** | `*-api` 是 HTTP 进程。 |
| **RAG 现状** | 🟢 10/10 通过 |

### A3 · gRPC 拦截链必须**真挂到 server 上**（两个契约各一套判据）

| 项 | 契约 A（api/rpc 分离 · RAG 形态） | 契约 B（api+rpc 合并 · **RAG-V1**） |
|---|---|---|
| **判据** | 解析 `*Application.java` ⇒ 存在 `GrpcServerConfigurer` 实现，且其中调用了 `server.intercept(...)` | ① `common/` 必须**声明** `GrpcServerConfigurer` 且真调 `server.intercept(...)`；② **域内不得再声明** `GrpcServerConfigurer` |
| **理由** | `RpcServerInterceptorFactory` 只产出 `ServerInterceptor` **Bean**；**不挂到 server 上则整条拦截链静默失效**（超时 / 业务码分类 / `sea.slow` 标记全丢）。⚠️ 这是"注解存在 ≠ 机制生效"的活样本。 | ① 同左（devh starter 只注入 `List<GrpcServerConfigurer>` ⇒ 不产 Configurer ⇒ 链装不上）；② 重复声明 ⇒ **同一条链被挂 2 次** ⇒ span 重复、timeout 叠加 |
| **落点** | 每个 `*-rpc` 模块各写一遍 | **共享层 1 份**（D1 合并的收益：一域一进程 ⇒ 每进程 1 个 gRPC server ⇒ 1 个全局 Configurer 即覆盖 10 个域） |
| **RAG 现状** | 🟡 **10 个 rpc 模块只有 6 个真挂了**（like / comment / follow / favorite / task / hot）⇒ **message / user / admin 三个域的拦截链静默失效**；RAG 自己的 javadoc 承认「锁死用例 `LikeGrpcInterceptorWiringTest` **全仓不存在**」 | —— |
| **RAG-V1 现状** | —— | ⏳ **PENDING** —— 挂载点类 `ProtectionAutoConfiguration` 仍是空壳 ⇒ 判据未施加（落地实现后自动转 PASS/FAIL） |

> ⚠️ **这条断言**不是**「api/rpc 分离」的派生物** —— Go 侧范围内 **10 个服务逐条显式**调
> `s.AddUnaryInterceptors(observability.NewUnaryServerInterceptor(rpcTimeout, observability.SlowThreshold()))`
> （`service/{like,comment,follow,message,favorite,task,hot,article}/rpc/*.go` + `service/user/{user,admin}/rpc/*.go`；
> `security` / `points` **不在迁移范围**）⇒ 合并后仍要挂，只是**挂载点从「每 rpc 模块」变成「共享层 1 份」**。
> ⇒ 设计依据 ⇒ [`完全spring化的文件树.md`](完全spring化的文件树.md) §5.5.2。

> ⚠️ **源码扫描只是「形状守门」，不是「机制验证」** —— A3 判的是源码里**有没有** `server.intercept(...)`，
> 而**真的挂上了**要靠运行期证据（§3.3 的「真触发」测试）⇒ 落地实现时必须补一条
> 「起真 gRPC server ⇒ 断言拦截器真的进了调用链」的测试（RAG 缺的就是这条）。

### A4 · 每个 `@GrpcClient("X")` 必须在同模块 yml 有 `negotiation-type: plaintext`

| 项 | 内容 |
|---|---|
| **判据** | 交叉引用：`src/main/java` 里的 `@GrpcClient("X")` ⟷ 同模块 `application.yml` 的 `grpc.client.X.negotiation-type` |
| **理由** | devh `GrpcChannelProperties` 的默认值是 **TLS**；Go `zrpc.MustNewServer` 是明文 gRPC ⇒ **不写会静默变 TLS**。 |
| **RAG 现状** | 🟡 **2 处哑弹**（见下） |

### A5 · 每个模块的 `@Import` 清单为空（starter 化之后）

| 项 | 内容 |
|---|---|
| **判据** | 解析所有 `*Application.java` ⇒ `@Import({...})` 中的 Bean 数为 0 |
| **理由** | starter 化（D3）之后，共享 Bean 由 `AutoConfiguration.imports` 统一装配。**残留 `@Import` 会与 auto-config 争抢求值顺序**，改变 `@ConditionalOnMissingBean` 语义。 |
| **RAG 现状** | 🔴 10/10 不通过（4~10 个 Bean 不等） |
| **RAG-V1 现状** | 🟢 0 个 |

### A6 · `MybatisPlusOrderingBridgeAutoConfiguration` 全仓只有一份

| 项 | 内容 |
|---|---|
| **判据** | 文件名扫描 ⇒ 命中数 ≤ 1 |
| **理由** | Boot 4 把 `DataSourceAutoConfiguration` 挪了包，MP 的 `@AutoConfigureAfter` 引用**静默悬空** ⇒ MP 自动配置不生效 ⇒ mapper 报 `sqlSessionFactory required`。这个桥是**域无关**的，不该有 9 份。 |
| **RAG 现状** | 🔴 9 份重复 |
| **RAG-V1 现状** | 🟢 收进 `common/autoconfigure/MybatisPlusOrderingBridgeAutoConfiguration` |

### A7 · classpath 上有 resilience4j ⇒ 不存在手写熔断器

| 项 | 内容 |
|---|---|
| **判据** | classpath 扫描 + 类名扫描 ⇒ 若 `io.github.resilience4j` 在 classpath，则不得存在手写的 `*Breaker` / `*CircuitBreaker` 实现 |
| **理由** | 生态已有就不该手写。手写版拿不到 resilience4j 的修复、指标与 Spring Cloud 集成。 |
| **RAG 现状** | 🔴 不通过（`GoStyleBreaker` / `GoStyleCircuitOpenException` 等） |
| **RAG-V1 现状** | 🟢 `protection/` 只剩 `CpuThresholdHealthIndicator`（生态缺口）+ `MaxBytesFilter` |

### A8 · 手写 `Logger` 必须实现 `org.slf4j.Logger`

| 项 | 内容 |
|---|---|
| **判据** | 类型检查 ⇒ 自定义 Logger 类 `implements org.slf4j.Logger` |
| **理由** | 保留 Go 的日志格式（`call_chain` 等是行为契约）**且**接入 Spring 的日志生态（配置、采集、MDC、traceId 自动注入）。**格式与生态可以兼得**，不该二选一。 |
| **RAG 现状** | 🔴 不通过 |
| **RAG-V1 现状** | 🟢 `common/logger/GoStyleLogger` |

### A9 · DTO 必须是 immutable（无 setter）

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ `api.dto` 下的类型无 setter，且是 `record` 或 final 字段 |
| **理由** | Go 的可变 struct 直译到 Java 会让"谁改的、什么时候改的"不可追。 |
| **RAG 现状** | 🔴 不通过（可变 POJO） |
| **RAG-V1 现状** | 🟢 全部 `record` |

### A10 · 存在手写校验器 ⇒ 必须引入 Bean Validation

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ 若无 `jakarta.validation` 依赖，则不得存在手写必填校验类 |
| **理由** | 手写校验器是"Go 语义手写"的产物。保留它意味着**放弃整个 Bean Validation 生态**（消息插值、分组、自定义约束）。 |
| **RAG 现状** | 🔴 不通过（`GoStyleRequired*` / `GoStyleRequest`） |
| **RAG-V1 现状** | 🟢 已删除手写校验器，`spring-boot-starter-validation` 已引入 |

### A11 · Go 侧 `cmd/fact-*` 独立进程 ⇒ 域内必须有对应装配落点

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ `comment` / `favorite` / `like` 三域各须存在 `rpc/bootstrap/<域>FactDispatchScheduler` 与 `rpc/bootstrap/<域>AuthorityEndpointConfig`；三域各须存在 `rpc/bootstrap/<域>FactProcessLogging` |
| **理由** | Go 侧这三域各有 `cmd/fact-dispatch` + `cmd/fact-authority`（favorite 另有 `cmd/fact-legacy-preflight`）**独立进程**。RAG 的组件级对照判定它们**零对外服务** ⇒ 可并入域内组件（见 [`决策记录.md`](决策记录.md) D1 的例外判定撤销）。<br>⚠️ 但「可合并」≠「已合并」—— 树里没有落点 = **该能力在实现阶段会被整个漏掉**，而漏掉它不会有任何编译错误或测试红灯（正是 RAG `article-rpc` 2 颗哑弹的同款形态）。 |
| **RAG 现状** | 🟢 三域均有（`mq/` 与 `fact/` 包下各 2 个 + `bootstrap/LikeFactProcessLogging`）—— ⚠️ 但 RAG 把它们放三个不同的包（`mq/`·`fact/`·`bootstrap/`），本身就不一致 |
| **RAG-V1 现状** | 🟢 2026-10-25 补齐：三域统一放 `rpc/bootstrap/`（6 个装配类 + 3 个日志身份类）<br>✅ **2026-10-25 二次订正**：守门脚本首次实跑发现 **`comment` 域实际缺 `CommentFactProcessLogging`**（只有 like / favorite 域有）⇒ 三份 logger 身份在该域**没有落点** ⇒ 已补，三域各 3 个落点齐备。⚠️ 该缺口**零编译错误 + 零测试红灯**，只有机器能抓 ⇒ 见 [`Pitfalls/_cross/P-08-落地证据未经机器复算.md`](Pitfalls/_cross/P-08-落地证据未经机器复算.md) |

### A12 · 一个模块内不得有同名简单类

| 项 | 内容 |
|---|---|
| **判据** | 静态检查 ⇒ 同一 Maven 模块内，两个 `.java` 文件的**简单类名**不得相同（不同包也不行） |
| **理由** | 同名类 ⇒ 职责重复，且**按简单类名检索时必然二义**。RAG-V1 曾有 `com.rag.like.mq.metrics.LikeMqMetrics` 与 `com.rag.like.rpc.metrics.LikeMqMetrics` 并存，且其中一个是**无契约的空壳** ⇒ 后写实现的人会填错那一个。 |
| **RAG-V1 现状** | 🟢 2026-10-25 已消（`LikeMqMetrics` 归位 `rpc/metrics/`，like-only 的 `mq/` 包已移除） |

## 二、RAG 现状的 2 颗哑弹（A4）

> **这是本清单实测时发现的现存隐患，不是新问题。**

| 模块 | 现象 | 当前后果 | 引爆条件 |
|---|---|---|---|
| `article-rpc` | `application.yml` 配了 `grpc.client.security-rpc` 与 `grpc.client.message-rpc`，**两者都缺 `negotiation-type: plaintext`** | **无害** —— 全仓没有对应的 `@GrpcClient` bean，通道建了但没人用 | **任何人补上一行 `@GrpcClient("message-rpc")`** ⇒ devh 默认 TLS ⇒ 连不上明文 gRPC ⇒ **而所有测试都是绿的**（测试用 `@SpringBootTest(properties = "grpc.client.xxx-rpc.negotiation-type=plaintext")` **在测试里注入**了它） |

> ⚠️ **教训（比这个 bug 本身更重要）**：
> **测试注入会掩盖生产配置的缺失。** 测试自己把值设上了 ⇒ 断言永远成立 ⇒ 生产配置可以一直是错的 ⇒ **没有人会发现**。
> ⇒ 这就是"沉默不变量"最危险的形态：**它不仅会被漏掉，还会被测试主动掩护。**

## 三、断言绑定契约，不可跨契约复用

| 契约 | A1 | A2 | A3 | A4 | A5 | A6 | A7 | A8 | A9 | A10 |
|---|---|---|---|---|---|---|---|---|---|---|
| **A**（Go 部署等价 · RAG 现状） | ✅ | ✅ | ✅ | ✅ | 🔴 | 🔴 | 🔴 | 🔴 | 🔴 | 🔴 |
| **B**（Spring 惯用 · RAG-V1） | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

⇒ **A1 / A2 / A3 是 api/rpc 分离的派生物**，合并后自动消失。
⇒ **它们是"沉默不变量只会出现在错误形态上"的活证据**：RAG 形态下 10/10 通过，一旦合并就不适用。
⇒ **RAG 与 RAG-V1 必须是两份断言**，共享的只是底层解析器。

## 四、例外必须显式声明

`hot-rpc` 没有 `@MapperScan` —— **因为它确实没有 mapper 包**。这不是违规，是例外。

| 规则 | 说明 |
|---|---|
| 例外必须**写进断言文件** | 不能靠"大家都懂" |
| 例外必须**写理由** | 否则例外会变成默认 |
| 没有写进文件的"例外" = 违规 | 断言不认口头豁免 |

| 项 | 内容 |
|---|---|
| **脚本位置** | `tools/difftest/check-arch-invariants.py` |
| **当前状态** | ✅ **2026-10-25 已实现** —— A1–A12 全部可执行；`--contract A|B` 支持契约绑定；`--self-test` 造违规假树验证 **12/12 条判据均能红** |

| **已抓到的真实漂移** | **A11**：`comment` 域缺 `CommentFactProcessLogging`（2026-10-25 补齐）⇒ 证明「树里没有落点 = 零编译错误 + 零测试红灯」不是修辞 |

| **接入 CI** | 与 `check-flyway-ledger.py` / `check-jar-executable.py` 同级，作为合并前的守门 |

> ⚠️ **实施时的坑**：`mvn dependency:tree` 在多模块仓库里对每个模块都要跑，**慢**。
> ⇒ 建议**用 POM 文本解析替代**（直接读 `<artifactId>spring-boot-starter-web</artifactId>` 是否出现在 `*-rpc` 的 pom 里）—— 零依赖、毫秒级，且足够可靠（依赖传递引入 starter 的情况在断言 A1 下反而不该存在）。
