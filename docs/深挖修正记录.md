# 深挖修正记录 —— Go 正推后的 8 处修正

> **触发**：2026-10-25 复核时发现，第一轮推导**是从 RAG 的 Java 侧反推 Go 的职责**。
> **为什么这是方法缺陷**：RAG 本身在 `users` / `like` / `message` / `common` / `article` 域都已被判定 `NOT EQUIVALENT`
> （见 RAG 仓库 `AGENTS.md` §0）。**拿一个已知漂移的实现当 Go 的替身，会把漂移固化进新树。**
> **修正方式**：改为 Go 正推 —— 逐域读 Go 源码，得出职责，再映射到 Java。

## 一、M-1 · HTTP method 分布（原推导说"全部 POST"是错的）

### Go 侧实测（`rest.Route{Method: http.MethodX}` 计数）

| 域 | Go 的 method 分布 | RAG 实际 | 一致? |
|---|---|---|---|
| article | **Get×3 Post×2 Put×1 Delete×1** | Get×3 Post×2 Put×1 Delete×1 | ✅ |
| favorite | **Get×2 Post×3 Delete×2** | 同 | ✅ |
| hot | **Get×1** | Get×1 | ✅ |
| message | **Get×1 Post×12** | Get×1 + Post×7 + Post×5 | ✅ |
| comment | Post×7 | Post×7 | ✅ |
| follow | Post×8 | Post×8 | ✅ |
| like | Post×6 | Post×6 | ✅ |
| task | Post×1 | Post×1 | ✅ |
| **admin** | Get×3 Post×9 Delete×1 | **Post×13** | 🔴 **签字偏离** |
| **user** | Get×2 Post×6 Delete×1 | **Post×9** | 🔴 **签字偏离** |

### 结论

1. **只有 users 域偏离**，且**已签字**（RAG `docs/Intentional_Deviations/_cross/signed-deviations.md:15`）。
   依据是 HUMAN_ONLY.MD 决策"Method 统一用 POST —— 取消 method 区别带来的客户端 SDK 复杂度"。
2. **RAG 其余 8 个域与 Go 完全一致**。
3. ⇒ **原推导"RAG 全改 POST"是把 users 域的决策误推广到了全仓**。RAG-V1 的树必须按 Go 的真实分布建。

### 落地

每个 Controller 的 javadoc 写入 Go 侧端点清单（Method + Path）。例如 `article`：

```
GET     /v1/articles
GET     /v1/article
GET     /v1/user/articles
POST    /v1/article
PUT     /v1/article
DELETE  /v1/article
POST    /v1/upload
```

## 二、M-2 · 路由前缀（3 个域原推导猜错）

| 域 | Go `rest.WithPrefix` | RAG 实际 | RAG-V1 修正 |
|---|---|---|---|
| **article** | **`/v1`** | `/v1` ✅ | `/v1`（**不是** `/article/v1`） |
| **task** | **`/taskcenter/v1`** | `/taskcenter/v1` ✅ | `/taskcenter/v1`（**不是** `/task/v1`） |
| **message** | `/message/v1` + **`/message/v1/admin`** | 两个都有 ✅ | 两个 Controller |
| user | `/usercenter/v1/user/*` | `/user/v1/*` ⚠️签字 | 继承签字偏离 |
| admin | `/admincenter/v1/admin/*` | `/admin/v1/*` ⚠️签字 | 继承签字偏离 |

### 两个额外发现

- **message 是双路由组**：`/message/v1` 用 **UserAuth** 的 JWT，`/message/v1/admin` 用 **AdminAuth** 的 JWT

  **中间那个 `/admin` 段被去掉了** ⇒ 不只是改名。

## 四、M-4 · 错误码值 / 文案 / 语言是**逐域隔离**的（差点被我"统一"掉）

### 同一语义，跨域码值不同

| 语义 | favorite / follow / hot / message | comment / like / user | article |
|---|---|---|---|
| `ErrorServerCommon` | 5001 | 5001 | 5001 |
| `ErrorDbUpdate` | **5008** | **5002** | 5002 |
| `ErrorDbSelect` | **5007** | **5003** | 5003 |
| `ErrorNotFound` | **5002** | — | — |
| `ErrorInvalidParam` | **5003** | — | — |
| `ErrorUnauthorized` | **5004** | — | — |
| `ErrorForbidden` | **5005** | — | — |
| `ErrorAlreadyExist` | **5006** | — | — |
| 「用户不存在」段 | **5101+** | **1001+** | — |

### 同一语义，跨域**文案与语言**不同

| 域 | `CodeServerBusy` 文案 | 语言 |
|---|---|---|
| article / comment / favorite / like / user | `"服务繁忙"` | **中文** |
| **follow / hot / message** | `"service busy"` | **英文** |

### ⇒ 推翻了「提取共享通用错误基座」的想法

我一度打算把"通用码段 + 通用文案"提到 `common` 做基座。**这是错的**：
- 码值不一致 ⇒ 统一即改行为
- 文案与语言不一致 ⇒ 统一即改行为
- 各域的 `BizCodeFromError` 反查表**只在域内自洽**（按 message 反查）⇒ 跨域共用反查表会得到错误 code

⇒ **正确结论**：每个域一套**独立**的错误契约包，值逐字照抄 Go（含码值、含文案、含语言）。
⇒ 这条约束已写进每个错误契约类的 javadoc。

### 另一个细节：`CodeError` 同时是错误类型和响应体

```go
type CodeError struct {
    Code int    `json:"code"`
    Msg  string `json:"msg"`
}
```

⇒ **不能当普通异常丢字段** —— 它被直接 JSON 序列化进响应体。

### 还有：`BizCodeFromError` 的反查算法

**先按 message 反查 code，查不到才按 gRPC 标准码 fallback**：

```
InvalidArgument → 5003    Unauthenticated → 5004    PermissionDenied → 5005
AlreadyExists   → 5006    NotFound        → 5002    Internal         → 5001
default         → 1015
```

⇒ 原推导 §5.3 的「统一错误模型」假设是"从异常上直接拿 code"，**算法不同**。已更正。

## 五、M-5 · task 域**没有**错误码空间（原来凭空造了一个）

Go 的 `task/` 下**没有 `common` 包**（`api=7 / rpc=17 / common=0`）⇒ 没有 `errmsg.go` ⇒ **没有错误码空间**。
⇒ 原推导给 task 建了 `contract/ErrorCode.java` ⇒ **凭空造**，已删除。

> 同理 Go 的 `hot` 也没有 `internal/model`（`hot=12` 个文件里无 model）⇒ hot 无持久化实体。
> RAG 的 `hot/rpc/domain/HeavyKeeper.java` 对应的是 Go 的 **`service/hot/heavykeeper/heavykeeper.go`** ——
> **域级独立包**（不在 common、不在 rpc），RAG 放进了 `rpc/domain/`，位置略有偏差但性质对。

## 六、M-6 · DTO 清单（从 RAG 反推 → 漏 2 改 3）

### 逐域对照 Go 的 `types.go`

| 域 | Go struct 数 | RAG-V1 原 | 差异 |
|---|---|---|---|
| article | 13 | 12 | **缺 `UploadImageReq`** |
| favorite | 16 | 15 | **缺 `GetFavoriteFoldersReq`** |
| hot | 3 | 3 | `HotArticleItem` → 原写成 `HotArticleCard` |
| user/user | 19 | 19 | `CreateUserReq/CreateUserResp` → 原写成 `RegisterReq/RegisterResp` |
| user/admin | 28 | 28 | `CreateInviteReq/CreateInviteResp` → 原写成 `CreateInviteCodeReq/Resp` |
| comment / follow / like / message / task | 16/6/15/17/3 | 同 | ✅ |

### 两个缺失 DTO 的真实原因（**不是 bug，是 L4 idiomatization**）

- **article `UploadImageReq`**：Go 用 multipart，RAG 改用 `@RequestParam("image") MultipartFile`
  ⇒ **Spring 的 multipart 机制直接承担**，比 Go struct 更地道。**保留 RAG 的做法**，但 DTO 仍建出来（承载 multipart 之外的字段），
  javadoc 写明这是 L4 替代关系。
- **favorite `GetFavoriteFoldersReq`**：Go 侧是个**空 struct**，但 Go 仍会解析并校验 body
  ⇒ RAG 用 `assertGoEmptyStructBody(httpRequest)` **手工复刻**了这个行为
  ⇒ ⚠️ **这个端点是 GET**，Go 用 GET 却仍读 body —— 极反直觉，**必须保留**（否则非法 body 的请求会从 5003 放过成 200，是可观察的 L1 差异）。

### 改名（3 处）

`HotArticleItem` / `CreateUserReq` / `CreateInviteReq` —— **Java 内部命名，不是 L1**（JSON tag 才是契约）。
但 RAG-V1 既然从 Go 正推，就跟 Go 的语义名，**便于逐行对照**，且在 javadoc 标注 Go 原名。

## 八、M-8 · Go 侧还有跨服务消息契约

`service/comment/rpc/common/types/kqueue.go`：

```go
package kqtypes
type CommentKafkaMsg struct {
    CommentId, TargetType, TargetId, UserId, RootId, ParentId,
    Content, Meta, OwnerId, Attribute, CreateTime
}
```

⇒ **跨服务 Kafka 消息契约 = L1**（字段名与顺序即消费方解析依据）。
⇒ 原推导完全没识别出这类东西 ⇒ **RAG-V1 新增 `comment-contract/contract/CommentKafkaMsg.java`**
（**D7 后的当前位置**：`service/comment/src/main/java/com/rag/comment/contract/CommentKafkaMsg.java`
—— `comment-contract` 模块已删除，类并入 comment 域模块的 `contract/` 包）。

> ⚠️ **这条揭示了一个系统性缺口**：Go 的**每个**域都可能有自己的 MQ 消息类型包，
> 而第一轮推导**只做了 `internal/types`（HTTP DTO）与 `internal/model`（实体）两类**，
> **漏了"跨服务消息契约"这一整类**。
> ⇒ 待办：逐域核查 Go 侧是否有 `kqueue` / `mqtypes` / `kafka types` 类包。

## 九、方法论修正（这一节才是最重要的）

### 第一轮推导为什么系统性漏

| # | 症状 | 根因 |
|---|---|---|
| 1 | 用 RAG 的类名清单代替 Go 的职责清单 | **从下游反推上游** —— 而 RAG 是已知漂移的实现 |
| 2 | 把 8 个域的 4 种错误契约形态统一成 1 种 | 按**目录名**归类（都在 `errmsg.go` 里），没读**函数面** |
| 3 | 认定"method 统一 POST" | 采信了 users 域的 HUMAN_ONLY.MD 决策，**误推广到全仓** |
| 4 | 前缀按"域名"猜 | 没读 `rest.WithPrefix` 的实际参数 |
| 5 | 完全没识别 Kafka 消息契约 | **只盘点了 HTTP DTO 与实体两类**，没穷举 Go 的包类型 |

### 五条纪律（应写进任何"Go → 目标框架"推导的检查清单）

1. **正推，不反推** —— 先读 Go 源码得出职责，再映射到目标框架。**不得用任何已有实现当 Go 的替身。**
2. **按"函数面 / 导出符号"归类，不按文件名 / 目录名** —— `errmsg.go` 里可能有 6 种职责，`types.go` 里可能有 15 个 DTO。
3. **L1 契约逐条抄，包括"反直觉"的部分** —— GET 端点读 body、method 混合、路径段数变化。
4. **同类项跨域逐一比对** —— "各域都有的东西"恰恰是**最可能取值不同**的地方（码值、文案、语言）。
5. **盘点要穷举包类型** —— HTTP DTO / 实体 / **跨服务消息契约** / 错误契约 / 配置块 / 指标名，缺一类就漏一类。

### 已补进 RAG-V1 的落地

- 每条纪律 ⇒ `AGENTS.md` §1.1（正推不反推）与 §6 检查清单
- M-1 / M-2 ⇒ 每个 Controller 的 javadoc 写入 Go 端点清单（Method + Path）
- M-3 / M-4 ⇒ 每个错误契约类的 javadoc 写入「逐域照抄、含语言、码值不可统一」的硬约束
- M-5 ⇒ task 域 contract 包清空
- M-7 ⇒ 新增 `users-common` 公共库模块
- M-8 ⇒ 新增 `CommentKafkaMsg`

## 十一、这次修正对"完全 Spring 化"结论的影响

| 原结论 | 修正后 |
|---|---|
| 「RAG 的 api/rpc 分离是最大的 Go-ism」 | **仍然成立**，但**不是唯一的** —— 错误契约的逐域形态、method 混合、MQ 契约都是 Go 侧的**语义约束**，不是 Go-ism，**必须照抄** |
| 「完全 Spring 化 = 合并 + starter + 生态优先」 | **仍然成立**，但要加一条：**L1 契约的域内隔离性必须逐字保留**（码值、文案、语言、method、前缀、消息字段） |
| 「收益不在文件数」 | **更成立了** —— 本轮修正**一个文件都没多**（只改内容与少量增删），却纠正了 8 处 L1 风险 |
