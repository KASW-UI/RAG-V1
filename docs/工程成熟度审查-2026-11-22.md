### 🔴 全仓回归失败的**根因**（本轮最重要的一条实证）

并行与串行两轮回归都红，且**根因相同**：

1. **字节码实证**：Testcontainers `PostgreSQLContainer.waitUntilContainerStarted` 的等待策略为
   `Duration.of(60, SECONDS)`（`javap -c` 反编译：`56: iconst_2` → `60: ldc2_w // long 60l` → `66: invokestatic Duration.of(J, TemporalUnit)`）
   ⇒ **容器启动等待窗口硬编码 60 秒**，且**全部测试夹具都没有覆写 `withStartupTimeout`**。
2. **实测对照**：本机用**完全相同的配置**手工起容器
   （`postgres:16-alpine` + `POSTGRES_DB=admin_rpc_column_parity_it` / `POSTGRES_USER=rag` / `POSTGRES_PASSWORD=rag`）
   ⇒ **70 秒**才打出 `database system is ready to accept connections`（`initdb` 耗时占大头）。
3. **结论**：**70s > 60s ⇒ 超时必然发生** ⇒
   `ContainerLaunchException: Timed out waiting for log output matching '.*database system is ready to accept connections.*'`
   ⇒ 失败用例耗时 123.5s（并行）/ 150.2s（隔离单跑）—— **两次都是超时重试耗尽**，不是断言失败。

**这意味着什么**：
- **不是**产品缺陷、**不是**测试逻辑缺陷、**不是**「并行资源竞争」——而是**测试夹具对「容器冷启动耗时」做了未声明的隐式假设**（60 秒够用）。本机 Docker Desktop 冷启动 + 文件系统缓存未预热 ⇒ 实际 70 秒。
- **后果**：在冷缓存机器 / 慢 CI / 资源受限环境上，**默认回归必然红**。这直接说明 **RAG-V1 的测试套件不具备环境无关性（non-hermetic）**。
- **修复（一行级）**：所有 PG 容器夹具加 `.withStartupTimeout(Duration.ofMinutes(3))`。本报告 §交付物 4 的 **RAG-D9-02** 即此条。
- **对 AGENTS.md 记录的影响**：§0 记载的「串行全仓回归 BUILD SUCCESS · 16/16 模块 · 1615 例」**在本轮无法复现**（本轮 15/16 模块 SUCCESS、admin-service FAILURE）。最可能的原因是记录当时容器镜像已预热、启动落在 60s 窗口内。**该读数不应再作为「当前绿」的依据。**
