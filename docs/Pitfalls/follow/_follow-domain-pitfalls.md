## P-FOLLOW-01 · 🔴 下游被**外力 SIGKILL** ⇒ 探针照样绿灯 ⇒ **读数测的是另一个场景**

**形态**：对拍探针把下游 user-rpc **SIGSTOP**（连接可建、无响应）来构造「超时」场景。
⇒ 某轮跑着跑着，下游被宿主**内存压力**杀掉（macOS jetsam 挑最大的进程杀；本机 24GB 内存 ⇒ 默认堆 6GB/JVM ⇒ 探针的 4 个服务端 JVM ＋ 多个 wire 探针 JVM 就是最大的那几个）。
⇒ **探针不会察觉** ⇒ 它照样把剩下的轮次跑完 ⇒ 给出「3 轮分布 `[1015 5001 5001]` · 两侧同轮同码 · 逐字节一致」的**绿灯**。

**为什么特别危险**：那几轮测的是「**连接被拒**」，**不是**「**挂起超时**」⇒
⇒ **码值分布变了，但两侧仍然一致** ⇒ ⇒ **只读码值分布绝对发现不了** ⇒ ⇒
⇒ 差点把一个「环境事故」当成「两侧都稳定的新行为」写进台账。

**判定式**：**每条场景判据都要配一条「场景有效性断言」** ——
判据问「行为对不对」，有效性断言问「**我测的是这个场景吗**」。
本例的断言 = **下游进程还活着**（`kill -0 ${USER_RPC_PID}`）⇒ 死了就 `die`（exit 2 = 环境问题），
**绝不产出误导性读数**。

**修法（三件套）**：
1. **降峰值**：全部 JVM 封顶（服务端 `-Xmx512m` · wire 探针 `-Xmx256m` · 构建 `MAVEN_OPTS=-Xmx768m`）。
2. **加断言**：`downstream_alive()` ⇒ 阶段1 前后 + 每轮之间 + 阶段2b 每轮之前都查。
3. **配「断言时点」**：断言要落在**采样点附近**（每轮之间），不是只在开头查一次。

**⇒ 同族**：与 [`P-12`](../_cross/P-12-变异没变红等于那条断言没覆盖到.md)（「变异没变红」可能是变异没打到）、
「跑绿 ≠ 本来就绿」同源 —— 本条补的是「**读数的「分布好看」不等于「测的是那个场景」**」这一面。

## P-FOLLOW-02 · 🔴 等待「服务发现条目回来」的**嵌套重试** ⇒ 下游已死时**死等 7.5 分钟**

**形态**：探针里写的是
```bash
for _ in $(seq 1 15); do nacos_assert_instance ... && break; sleep 1; done
```
而 `nacos_assert_instance` **自己内部又重试 30 次 × 1s** ⇒ ⇒ **最坏 15 × 30 = 450 秒**。
⇒ 而「下游已被外力杀掉」这个场景下，**条目永远不会回来** ⇒ ⇒ 探针**卡死 7.5 分钟**，
后面所有阶段都跑在坏环境上。

**修法**：① 外层重试与内层重试**只留一层**（单次调用 ⇒ 最坏 30s）；
② **先断言「等的东西还可能回来」**（下游活着）⇒ 不可能就直接 `die`，**不做无谓等待**。

**⇒ 同族**：「重试」与「等待」都要算**最坏耗时**；两层重试相乘是很容易漏掉的。

## P-FOLLOW-03 · 🔴 生成器在 **worktree** 里跑 ⇒ 与 main 的差异是**假差异**（**git 不跟踪空目录**）

**形态**：仓内生成器 `tools/gen-file-tree.py` 的 `ROOT` **硬编码成主工作区绝对路径** ⇒
在 worktree 里直接跑 ⇒ 量的是**主工作区**那棵树（⇒ 假绿）；
按纪律把 `ROOT` 改指 worktree 后再跑 ⇒ ⇒ **又与 main 不一致了** ——
因为 **main 里有 `proto/src/test/java/`（空目录），而 git 不跟踪空目录 ⇒ worktree 里没有它**
⇒ ⇒ 生成物把这一行**删掉**了 ⇒ ⇒ **提交上去就会与 main 的真实目录结构不符**。

**判定式**：**「生成器在哪棵树上跑」不是唯一的问题** ⇒ 还要问「**那棵树和落地的那棵树是不是同一棵**」。
空目录是 git 看不见的 ⇒ **worktree 天然缺它们** ⇒ ⇒ **凡是用文件树/目录清单做判据的生成物，
差异必须人工判一次**（尤其是「少了一个目录」这种差异 ⇒ 大概率是空目录 ⇒ 撤回）。

**修法**：**生成物要在「最终落地的那棵树」上生成**（= main）⇒
本轮做法 = worktree 里生成后**逐项看差异** ⇒ 发现 `proto.md` 只是少一个**空目录** ⇒ ⇒ **撤回该文件**（`git checkout --`），
保留**真正反映代码变化**的差异。

**⇒ 同族**：与「生成器的 ROOT 与它 import 的模块的 ROOT 可能不是同一个」、
「『机器生成物』不能当落点」同源 —— 本条补的是「**worktree 与 main 的差异里，有一部分是 git 的盲区（空目录）造成的假差异**」这一面。

## P-FOLLOW-04 · 变异脚本的备份是**启动时一次性取的** ⇒ 运行期间改靶点文件会被**还原冲掉**

**形态**：`mutate-parity.sh` 的 `backup` 在**脚本启动时**把全部四个靶点各备份一份 ⇒
⇒ **运行期间**对任一靶点文件的任何修改，都会被该轮结束时的 `restore`（`cp` 备份回来）**覆盖**。
⇒ 本轮踩到：跑变异期间给 `FollowUserExistenceService` 补了一段 javadoc ⇒ M6 跑完 ⇒ **那段 javadoc 消失了**。

**修法/纪律**：
① **跑变异期间只改非靶点文件**（文档 / 其他源文件）；
② 改完靶点文件**必须核对**（`grep` 一下自己写的那段还在不在）⇒ 本轮已重新 apply 并复验编译 + 单测；
③ ⚠️ **不要为了修这个而改「备份时机」** —— 改了脚本就得**重跑一遍变异**才让证据与脚本对得上 ⇒ 代价远大于收益 ⇒ **只记录，不动脚本**。

**⇒ 同族**：与「`git checkout --` 会抹掉未暂存改动」同源 —— 本条补的是「**自建脚本的备份也有同样的盲区，而且更安静**」这一面。

## P-FOLLOW-05 · 🔴 探针的**两段都会改库** ⇒ 顺序排错 ⇒ **假红**（差点误判成真漂移）

**形态**：2026-11-10 加「wire 第三方锚」时，锚报「**5 条不一致**」⇒ 第一反应是「真漂移」⇒ 实际是**顺序错**：

| 轮次 | 顺序 | 现象 | 真因 |
|---|---|---|---|
| ① | wire 段在 HTTP 矩阵**之后** | `wire_follow_list` 读出 `[1004,1002]`，Go 锚是 `[1003,1002]` | HTTP 矩阵的**写路径**已改库（加 1001→1004 · 删 1001→1003 · 删 1001→1005） |
| ② | wire 段挪到 HTTP 矩阵**之前** | **HTTP 矩阵反而红了**（同样 `[1004,1002]`） | **wire 段自己也有 4 条写用例**（`wire_follow_new` / `wire_unfollow` / `wire_block` / `wire_unblock`）⇒ **它污染了 HTTP 矩阵** |

⇒ ⇒ **只调顺序救不了**（两段都改库）⇒ ⇒ 必须**用「重播」隔离**。

**修法**：wire 段之后、HTTP 矩阵之前，**先清后插**地重播初始播种
（`DELETE FROM follow_relation WHERE user_id IN (1001,1002) OR target_id IN (1003,1004,1005,1006)` ⇒ `INSERT` 四行 follow + `DELETE … block_relation` ⇒ `INSERT` 一行 block）⇒ ⇒ 两侧都回到 Go 锚录制时的状态。
⚠️ **不能用 `ON CONFLICT DO NOTHING`**（只能加不能删 ⇒ 上轮残留行会留下 ⇒ 仍假红）。
⚠️ **不能删 1008/1009**（场景轮的并发 target / 事务回滚 target）⇒ 只删 1001/1002 与 1003~1006。

**判定式（通用）**：**探针读数与冻结期望不符时，先查「谁改过库」，再下漂移结论。**
⇒ **两侧同时偏离同一个冻结值** ⇒ 几乎总是**状态/顺序问题**，不是「两侧一起错」；
⇒ 真正的「两侧一起错」要用**第三方锚**（独立于双方的实现）才抓得到。

**⇒ 同族**：与「跑绿 ≠ 本来就绿」「变异没变红 = 没覆盖到」同源 —— 本条补的是「**假红的第三种形态：不是判据错，是被测状态错**」这一面。

## P-FOLLOW-06 · 🔴 「Go 真源已删」不等于「第三方锚不可得」—— 仓里**冻结字节**就是锚

**形态**：§11.6 的 NOT_VERIFIED ① 写着「gRPC wire 层**无第三方锚**（Go 真源的 wire 字节未冻结）」⇒ 加上「B 仓的 Go 真源**已被删除**（只剩 `tools/**` 里的 123 个探针 `.go`）」⇒ 第一反应是「**永久不可闭合**」。

**证伪**：**冻结字节还在仓里** —— `tools/difftest/follow/expected.txt` 是 B 侧 **2026-10-29 从 Go 侧录下的 20 条 HTTP 用例** ⇒ 它**不依赖任何当前可运行的代码** ⇒ 就是**真源级**的第三方锚。
⇒ 再加**第二个互相独立的第三方**：`protoc` 35.0 生成 Python 绑定 ⇒ `google.protobuf` 7.36.2（**与两侧的 grpc-java 完全独立**）⇒ 用它**独立解码** wire 原始字节 ⇒ ⇒ 判据 = **wire 语义 ≡ Go 锚的 HTTP 语义**（`code` / `msg` / `user_ids` / `users[target_id+mutual_score]`）⇒ ⇒ **wire 层由「双边一致」升级为「三方一致」**（实测 9/9 挂锚）⇒ ⇒ **「两侧一起错」类缺陷也能被抓**（双边一致抓不到）。

⚠️ **错误态用例不能挂 Go 锚**：Go 锚是 **HTTP 层业务码**，wire 错误态给的是 **gRPC status** ⇒ **不是同一个码空间** ⇒ 不可直接比；且 B 侧**自己**这两者就映射不一致（`NOT_FOUND` → B 侧 5002 vs Go 侧 5101）⇒ ⇒ 那属 **B 侧自身的既有漂移**，不属本锚范围 ⇒ 只判「C == B 的 status 一致」。

**⇒ 同族**：与「零命中 ≠ 不存在」「官方机制必须从 jar 挖」同源 —— 本条补的是「**『来源被删』不等于『证据消失』：先翻仓里有没有冻结下来的产物**」这一面。

## P-FOLLOW-07 · 🔴 语义字典的**键类型**不一致 ⇒ 好数据也报红（自证时抓到）

**形态**：第三方锚把 Go 锚的 JSON 与 wire 的 protobuf 都压成「字段号 → 值」字典再比 ⇒ 形状看起来一样 ⇒ 但：
① Go 锚的 `users[].target_id` 是**字符串**（`"1004"`）⇒ 我手搓的 Go 侧字典用了 **str 键** `{'1': 1004}`；
② wire 侧 `summarize()` 出的是 **int 键** `{1: 1004}` ⇒ ⇒ 比不上 ⇒ **连「完全正确」的夹具都报红**。

**修法**：两侧语义字典**必须用同一种键类型**（统一 **int 字段号**）＋ nested message **递归**用同一形状。
⚠️ **protobuf 7.x 的 upb 实现没有 `FieldDescriptor.label`** ⇒ 判 repeated 要用 `is_repeated`（用 `label == LABEL_REPEATED` 会抛 `AttributeError`）。

**⇒ 同族**：与「断言自己给自己兜了底」「比较器本身有 bug」同源 —— 本条补的是「**差分对拍的『相等判定』本身也是被测代码的一部分**」这一面：⇒ **先用一个「已知应当通过」的夹具跑一遍**（本条就是这样抓到的）。

## P-FOLLOW-08 · 🔴 **前提不成立却做了契约比对** ⇒ 探针把**系统级现象**报成**漂移**

**形态**：场景轮跑出 3 项红（`scn_recover_after_stall` / `scn_downstream_down` / `scn_concurrent_follow`），形态固定：
`C=1015（挂到 2s 出向预算）` vs `B=5001（快速失败）` ⇒ 两侧字节不等 ⇒ 探针判为**漂移**。

**真根因（三条腿，同一根）**：
① `wait_both_recovered 60 3 \|\| true` ⇒ **把「没进稳定态」这个事实吞掉** ⇒ 紧接着的逐字节比对在**探针自己刚判定「没恢复」的状态**上做；
② 「等 Nacos 条目回池」的预算**写死 30s** 且**失败只告警就继续跑** ⇒ 宿主吃紧时（实测条目回来要 >30s）探针**在「下游解析不到」的状态上继续跑**；
③ 恢复预算 **60s** 不够（条目续期 + 通道退避 + 连续 3 轮 200 三项叠加）⇒ 恢复本身没达成；阶段3/阶段5 又是**单发** ⇒ 一路请求超预算就采到形态差。

**⇒ 关键判定**：这种不同步**不是漂移** —— 域台账 §8.6.7 早已定案「**码值随「失败形态」走，不随错误码映射走**」⇒ 两侧**同形态必然同码** ⇒ 过渡窗口里两侧不同码 ⇒ **系统级现象**。

**修法（三条）**：
① **判据模型改成三态**（✅ 判据成立 / 🔴 行为不一致 / ⚠️ **前提不成立 ⇒ 观察项**）⇒ `wait_both_recovered` 的**返回值必须被消费**（删掉 `\|\| true`）⇒ 当 `compare_recovered` 的**前提参数**；
② 「等条目」预算**按场景给**（恢复轮 120s）＋ 失败 ⇒ **`die`（exit 2）** ⇒ 绝不在坏前提上产读数；
③ 阶段3/5 用**收敛重试**（阶段3 = 连续 2 轮一致；阶段5 = 取第一个「两侧 {200} ＋ 各 1 行」的轮次）⇒ ⚠️ **真漂移永不收敛 ⇒ 仍判红**。

**⇒ 元教训（本条最值钱的一句）**：**对照实验只能证伪「是不是我的改动」，不能证成「是环境」** —— 上一轮把「与本轮改动无因果」直接写成「归因 = 宿主环境面」，那是**第二跳的未经证明推断**；真根因要靠**读探针自己的前提链**才找得到。
⇒ 另有一条同源：**探针自己写明的注释（「两侧对称 ⇒ 系统级现象」）如果只印在警告里、却照样置 FAILED ⇒ 代码与自己的注释不一致** ⇒ 注释必须落成判据。

**⇒ 同族**：与「跑绿 ≠ 验过」「读数失败 ≠ 行为差异」「静默空结果」「脚本自报成功 ≠ 真做了」同源 —— 本条补的是「**比对的『前提』本身也要被管理**」这一面：**前提不成立 ⇒ 比对结论无效 ⇒ 必须与「真不一致」分开报**。

## P-FOLLOW-09 · 🔴 探针自己的**「重置/清理」**动作，把**注入的差异**一起抹掉 ⇒ 判据的**牙齿被削掉**

**形态**：变异验证 M3（「**C 侧多灌一行** (1001,1009)」⇒ 两侧库应不同 ⇒ HTTP 矩阵必须转红）**没按预期转红**：探针 exit 1（确实有东西红了），但红的**不是** `follow_list_seeded` ⇒ 断言不成立 ⇒ **变异脚本判定「探针是假绿」**。

**真根因**：探针有一段「**重播**」—— 把库恢复到 Go 真源冻结字节录制时的状态（因为 wire 段有自己的写用例，会污染后面的 HTTP 矩阵）。它的删除条件当时是**宽条件**：
`DELETE … WHERE user_id IN (1001,1002) OR target_id IN (1003,1004,1005,1006)`
⇒ ⇒ **把 `user_id=1001` 的所有行都删了** ⇒ ⇒ M3 注入的 `(1001,1009)` **也被一起删掉** ⇒ ⇒ 两侧库又一致 ⇒ ⇒ **HTTP 矩阵看不见差异**。

**为什么基线永远是绿的**：重播多删几行，**基线读数一个字节都不会变** ⇒ ⇒ **人眼 / 常规回归永远发现不了** ⇒ ⇒ **只有「把差异注入进去」这个动作才能发现它** ⇒ ⇒ 这正是变异验证存在的理由（AGENTS.md §3.3.3）。

**修法**：重播的删除范围**必须「恰好覆盖被测流程改过的东西」，不能更宽** ⇒ 窄化到**逐对**（只列 wire 段那 4 条写用例**可能碰到的对**，含写路径「先删双向」带来的反向对）⇒ ⇒ **绝不碰 `(1001,1009)`** ⇒ ⇒ M3 的牙齿保住；回插用 `ON CONFLICT DO NOTHING`（幂等）。

**⇒ 元教训（跨项目可复用）**：**「恢复到基线状态」是探针里最容易被写宽的一步** —— 写宽了，它会**顺手把被注入的缺陷一起抹掉** ⇒ ⇒ 探针从「有牙齿」退化成「永远绿」⇒ ⇒ **而基线读数完全正常** ⇒ ⇒ **只能靠变异验证发现**。
⇒ **判定式**：凡探针里有「重置/清理/重播/回滚到初始状态」这类动作 ⇒ **逐条核它的删除范围** ⇒ **必须能被写成一个「恰好覆盖被测流程改过的东西」的枚举**；写不出这个枚举 ⇒ 说明它在**盲删**。

**⇒ 同族**：与「探针自己给自己兜了底」「假绿」「跑绿 ≠ 验过」同源 —— 本条补的是「**探针的辅助动作（重置/清理）也是判据的一部分**」这一面：**辅助动作越权 ⇒ 判据失效**。
