## P-FOLLOW-01 · 🔴 下游被**外力 SIGKILL** ⇒ 探针照样绿灯 ⇒ **读数测的是另一个场景**

**形态**：对拍探针把下游 user-rpc **SIGSTOP**（连接可建、无响应）来构造「超时」场景。
⇒ 某轮跑着跑着，下游被宿主**内存压力**杀掉（macOS jetsam 挑最大的进程杀；本机 24GB 内存 ⇒ 默认堆 6GB/JVM ⇒ 探针的 4 个服务端 JVM ＋ 多个 wire 探针 JVM 就是最大的那几个）。
⇒ **探针不会察觉** ⇒ 它照样把剩下的轮次跑完 ⇒ 给出「3 轮分布 `[1015 5001 5001]` · 两侧同轮同码 · 逐字节一致」的**绿灯**。

**为什么特别危险**：那几轮测的是「**连接被拒**」，**不是**「**挂起超时**」⇒
⇒ **码值分布变了，但两侧仍然一致** ⇒ ⇒ **只读码值分布绝对发现不了** ⇒ ⇒
⇒ 差点把一个「环境事故」当成「两侧都稳定的新行为」写进台账。

**判定式**：**每条场景判据都要配一条「场景有效性断言」** ——
判据问「行为对不对」，有效性断言问「**我测的是这个场景吗**」。
本例的断言 = **下游进程还活着**（`kill -0 ${USER_RPC_PID}`）⇒ 死了就 `die`（exit 2 = 环境问题），
**绝不产出误导性读数**。

**修法（三件套）**：
1. **降峰值**：全部 JVM 封顶（服务端 `-Xmx512m` · wire 探针 `-Xmx256m` · 构建 `MAVEN_OPTS=-Xmx768m`）。
2. **加断言**：`downstream_alive()` ⇒ 阶段1 前后 + 每轮之间 + 阶段2b 每轮之前都查。
3. **配「断言时点」**：断言要落在**采样点附近**（每轮之间），不是只在开头查一次。

**⇒ 同族**：与 [`P-12`](../_cross/P-12-变异没变红等于那条断言没覆盖到.md)（「变异没变红」可能是变异没打到）、
「跑绿 ≠ 本来就绿」同源 —— 本条补的是「**读数的「分布好看」不等于「测的是那个场景」**」这一面。

## P-FOLLOW-02 · 🔴 等待「服务发现条目回来」的**嵌套重试** ⇒ 下游已死时**死等 7.5 分钟**

**形态**：探针里写的是
```bash
for _ in $(seq 1 15); do nacos_assert_instance ... && break; sleep 1; done
```
而 `nacos_assert_instance` **自己内部又重试 30 次 × 1s** ⇒ ⇒ **最坏 15 × 30 = 450 秒**。
⇒ 而「下游已被外力杀掉」这个场景下，**条目永远不会回来** ⇒ ⇒ 探针**卡死 7.5 分钟**，
后面所有阶段都跑在坏环境上。

**修法**：① 外层重试与内层重试**只留一层**（单次调用 ⇒ 最坏 30s）；
② **先断言「等的东西还可能回来」**（下游活着）⇒ 不可能就直接 `die`，**不做无谓等待**。

**⇒ 同族**：「重试」与「等待」都要算**最坏耗时**；两层重试相乘是很容易漏掉的。

## P-FOLLOW-03 · 🔴 生成器在 **worktree** 里跑 ⇒ 与 main 的差异是**假差异**（**git 不跟踪空目录**）

**形态**：仓内生成器 `tools/gen-file-tree.py` 的 `ROOT` **硬编码成主工作区绝对路径** ⇒
在 worktree 里直接跑 ⇒ 量的是**主工作区**那棵树（⇒ 假绿）；
按纪律把 `ROOT` 改指 worktree 后再跑 ⇒ ⇒ **又与 main 不一致了** ——
因为 **main 里有 `proto/src/test/java/`（空目录），而 git 不跟踪空目录 ⇒ worktree 里没有它**
⇒ ⇒ 生成物把这一行**删掉**了 ⇒ ⇒ **提交上去就会与 main 的真实目录结构不符**。

**判定式**：**「生成器在哪棵树上跑」不是唯一的问题** ⇒ 还要问「**那棵树和落地的那棵树是不是同一棵**」。
空目录是 git 看不见的 ⇒ **worktree 天然缺它们** ⇒ ⇒ **凡是用文件树/目录清单做判据的生成物，
差异必须人工判一次**（尤其是「少了一个目录」这种差异 ⇒ 大概率是空目录 ⇒ 撤回）。

**修法**：**生成物要在「最终落地的那棵树」上生成**（= main）⇒
本轮做法 = worktree 里生成后**逐项看差异** ⇒ 发现 `proto.md` 只是少一个**空目录** ⇒ ⇒ **撤回该文件**（`git checkout --`），
保留**真正反映代码变化**的差异。

**⇒ 同族**：与「生成器的 ROOT 与它 import 的模块的 ROOT 可能不是同一个」、
「『机器生成物』不能当落点」同源 —— 本条补的是「**worktree 与 main 的差异里，有一部分是 git 的盲区（空目录）造成的假差异**」这一面。

## P-FOLLOW-04 · 变异脚本的备份是**启动时一次性取的** ⇒ 运行期间改靶点文件会被**还原冲掉**

**形态**：`mutate-parity.sh` 的 `backup` 在**脚本启动时**把全部四个靶点各备份一份 ⇒
⇒ **运行期间**对任一靶点文件的任何修改，都会被该轮结束时的 `restore`（`cp` 备份回来）**覆盖**。
⇒ 本轮踩到：跑变异期间给 `FollowUserExistenceService` 补了一段 javadoc ⇒ M6 跑完 ⇒ **那段 javadoc 消失了**。

**修法/纪律**：
① **跑变异期间只改非靶点文件**（文档 / 其他源文件）；
② 改完靶点文件**必须核对**（`grep` 一下自己写的那段还在不在）⇒ 本轮已重新 apply 并复验编译 + 单测；
③ ⚠️ **不要为了修这个而改「备份时机」** —— 改了脚本就得**重跑一遍变异**才让证据与脚本对得上 ⇒ 代价远大于收益 ⇒ **只记录，不动脚本**。

**⇒ 同族**：与「`git checkout --` 会抹掉未暂存改动」同源 —— 本条补的是「**自建脚本的备份也有同样的盲区，而且更安静**」这一面。
