# P-10 · 断言的「自动消失」≠ 问题不存在 —— 判形态相关要看**命题**，不看**实现形态**

> 档位：跨模块（`_cross/`）· 首次登记 **2026-10-26** · 触发场景：D1 合并 api/rpc 后 A3 断言被判为 N/A（2026-10-26 · D9 更正）

---

## 一、现象

D1 决定把 `api/` + `rpc/` 合并成单一 Spring Boot 应用后，
守门脚本 `tools/difftest/check-arch-invariants.py` 里写着：

```python
# 脚本第 27 行（原文）
⚠️ **A1 / A2 / A3 是 api/rpc 分离的派生物**，合并形态下它们**自动消失**。
```

于是 `check_a3` 在契约 B（合并形态）下直接：

```python
if contract != "A":
    return na("契约 B（api+rpc 合并）下不适用 —— D1 连带效应，不得改成红灯")
```

⇒ **A3 从此是 N/A**，不参与任何门禁。

## 二、为什么会踩（这才是本档要记的）

**A3 的实质命题是「gRPC 拦截链有没有**真挂到 server 上**」—— 这与进程形态无关。**

Go 侧范围内 **10 个服务逐条显式**：

```go
// service/{like,comment,follow,message,favorite,task,hot,article}/rpc/*.go
// service/user/{user,admin}/rpc/*.go
s.AddUnaryInterceptors(observability.NewUnaryServerInterceptor(rpcTimeout, observability.SlowThreshold()))
```

⇒ 合并成「一域一进程」后**照样要挂**，只是**挂载点从「每 rpc 模块各写一遍」变成「共享层 1 份」**。

⚠️ **而 RAG 侧的真实数据是：10 个 rpc 模块只有 6 个真声明了 `GrpcServerConfigurer`**
⇒ **message / user / admin 三个域的拦截链本来就是静默失效的**
⇒ 而 RAG-V1 的树里 `GrpcServerConfigurer` / `ServerInterceptor` **全树 0 落点**。

⇒ **A3 被判 N/A 的那一刻，这条真保证连同它本该抓出的缺陷，一起从门禁里消失了。**

### 根因

**判「断言是否形态相关」时，看的是断言的**实现形态**（它查 `*-rpc` 模块），
而不是它的**实质命题**（拦截链挂没挂上）。**

`if contract != "A": return na(...)` 这行字**看起来是保护措施**（"不得改成红灯"），
实际上它是**断言的死亡证明** —— 它把「这条保证在另一形态下不成立」这个**未经论证的假设**
写进了代码，而没人再去论证一次。

## 三、教训

1. **每写一行 `return na(...)`，必须回答：「这条断言的**命题**在另一契约下还成立吗？」**
   - 命题是「api 模块与 rpc 模块分开」⇒ 形态相关 ⇒ N/A 合理
   - 命题是「拦截链挂上了」⇒ **形态无关** ⇒ 必须**改写**而非 N/A

2. **「N/A」与「PASS」不是一回事，但「N/A」与「FAIL」在门禁里是同一件事：都不拦。**
   ⇒ 一条断言被降级为 N/A 时，**必须同时写下**「它在另一形态下由什么来保证」——
   写不出来 ⇒ 说明这条保证在另一形态下**真的没了**（本例：真的没了 ⇒ 必须补落点）。

3. ⚠️ **断言是「沉默不变量」的载体**（P-08）—— 本条是它的**升级版**：
   **沉默不变量不只是「没人复算的证据」，还包括「被形态判据顺手关掉的断言」。**
   ⇒ 每次改断言的**契约归属**，都要重新论证一次它守护的命题。
