# P-31 · 配置文件改名 ⇒ **三类「不跟随」的消费者**（Spring 上下文 / 直接读文件 / 向上搜索）

> 档位：跨模块（`_cross/`）· 首次登记 **2026-11-28** · 触发场景：**S1 · 10 份域 yml 改名**

---

## 一、现象

把 10 个域的 `application.yml` 改名为 `application-<域>.yml`（原因见 P-29）之后，
**域自己的测试大面积红**，而**编译全绿**、**域 jar 也能打出来**：

```
[ERROR] MessageServiceApplicationTests.configurationPropertiesBeansAreRegistered
  » IllegalState ApplicationContext failure threshold (1) exceeded
[ERROR] MessageServiceApplicationTests.mapperBeansAreRegistered
  » IllegalState Failed to load ApplicationContext
      ... caused by: java.lang.IllegalStateException:
      message-api.user-auth.access-secret 不能为空：请设置环境变量 USER_JWT_SECRET
```

---

## 二、三类「不跟随」的消费者（**这是本档的核心**）

配置改名/移动后，**只有走 Spring 配置体系的那一类会自动跟随**；另外三类**不会**：

| # | 消费者 | 会不会跟随 | 实测症状 |
|---|---|---|---|
| ① | **走 Spring 配置体系**的（`@SpringBootTest` + `spring.config.import`） | ✅ **会**（import 是显式声明） | — |
| ② | ★ **直接读 yml 文件**的（`YamlPropertySourceLoader` + `ClassPathResource("application.yml")`） | ❌ **不会**（它读的是**文件路径**，不经过任何配置体系） | `management.metrics.tags.application 应当存在 … expected: <favorite-service> but was: <null>` |
| ③ | ★ **靠 `@SpringBootTest` 向上搜索**找 `@SpringBootConfiguration` 的 | ❌ **不会**（它找的是**类**，不是配置） | `Unable to find a @SpringBootConfiguration by searching packages upwards from the test` |
| ④ | ★ **读 `target/classes/application.yml` 核对打包产物**的（`FileSystemResource`） | ❌ **不会** | 路径对不上 ⇒ 读到 null |

**本仓实测命中**：② **16 个测试文件** · ③ **2 个测试文件** · ④ 若干。

---

## 三、为什么没拦住（这才是本档要记的）

| 环节 | 为什么没拦住 |
|---|---|
| **编译时** | yml 是**资源文件**，改名**不影响编译** ⇒ 编译期**完全看不见** |
| **打包时** | 资源改名照样打进 jar ⇒ jar 结构**合法** |
| **守门脚本时** | 守门做的是源码文本扫描 ⇒ 判不了「测试读的路径还指不指得到真配置」 |
| ⚠️ **最典型的形态** | 「**域 jar 能打 + 域测试类能编译**」⇒ ⇒ **看起来一切正常**；⇒ ⇒ 但**一跑测试就红** ⇒ ⇒ 幸而它是**红的**（不是静默的） |

---

## 四、⚠️ 元教训（比坑本身更重要）

1. **「改名 / 移动配置」不是纯文本操作** ⇒ ⇒ 它有**四类消费者**，其中**三类不跟随**。
   ⇒ ⇒ 凡是动配置文件的位置，必须同时问一句：**谁在读这个路径？**
2. ★ **「直接读文件」的测试是最容易被忘的一类** ——
   它**看起来**像配置测试，实际是**文件内容断言** ⇒ ⇒ 配置文件一改，它的断言对象就变了
   （却**不是**它想断言的那份）⇒ ⇒ **这类测试要显式标注「我读的是哪份文件」**。
3. ★ **降级 `@SpringBootApplication` ⇒ 连带废掉「向上搜索」** ——
   `@SpringBootApplication` 带 `@SpringBootConfiguration`，而 Spring 的
   `SpringBootContextLoader` **靠这个注解做向上搜索** ⇒ ⇒ 降级它 ⇒ ⇒
   **所有无 `classes=` 的 `@SpringBootTest` 一起失效** ⇒ ⇒ 必须**同批**补 `classes=`。
   ⇒ ⇒ **本仓实测**：93 个 `@SpringBootTest` 里 **3 个**受影响（2 个带 properties 无 classes ＋ 1 个无参）。
4. ⇒ **可复用的自检**：`grep -rn 'ClassPathResource("application.yml")' --include="*.java" src/test`
   ⇒ 命中即「这类测试不跟随配置改名」。

## 五、⚠️ 追加（2026-11-28 晚 · 同轮 S1 的另一条同源坑）

降级 `@SpringBootApplication` 为裸 `@Configuration + @EnableAutoConfiguration + @ComponentScan` 时，
**丢了 `@ComponentScan` 隐含的 `excludeFilters`**：

- `@SpringBootApplication` 的 `@ComponentScan` **隐含**两个过滤器：
  ① `TypeExcludeFilter`（Boot 的测试类型排除）② `AutoConfigurationExcludeFilter`（排除 `@AutoConfiguration` 类）
- ⇒ 降级成裸 `@ComponentScan("...")` ⇒ **两个一起丢**
- ⇒ ⇒ **实测症状**：域内 `ContentAuditAutoConfiguration` 被**组件扫描**扫到
  ⇒ bean 名变成短名 `contentAuditAutoConfiguration`（而不是 `.imports` 机制给的 FQCN）
  ⇒ ⇒ **绕过了 `META-INF/spring/…AutoConfiguration.imports` 机制** ⇒ ⇒ **A5 断言红**
- ⇒ ⇒ **修法**：降级后的 `@ComponentScan` **逐字补回**：
  ```java
  @ComponentScan(basePackages = "com.rag.article",
          excludeFilters = {
                  @ComponentScan.Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
                  @ComponentScan.Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class)
          })
  ```

⇒ ⚠️ **元教训**：**降级一个「组合注解」时，它隐含的语义不止表面那几条注解**
⇒ ⇒ `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`
⇒ ⇒ 而那个 `@ComponentScan` **自带 excludeFilters** ⇒ ⇒ **逐条抄注解会漏配置**。
⇒ ⇒ **可复用的自检**：降级后跑「本域的 `.imports` 机制断言」（本仓 = A5）⇒ 它当场抓这条。

## 六、⚠️ 追加（2026-11-28 晚 · 同轮 S1 · 「直读」这一类实际有**三种读法**）

§二 的第 ② 类「直接读 yml 文件」在实测里**分裂成三种读法**，**每一种都要单独点名**：

| 读法 | 代码形态 | 本仓实测命中 |
|---|---|---|
| **① classpath 字节流** | `getClass().getResourceAsStream("/application.yml")` | `CommentOversizedBodyRealTomcatTest` · `CommentGrpcInterceptorWiringRealTest` |
| **② classpath 资源** | `new ClassPathResource("application.yml")` | `CommentRuntimeConfigContractTest` · `CommentApiPropertiesSecretGuardTest` · `CommentJwtTokenMatrixRealTomcatTest` · `FavoriteApiPropertiesSecretGuardTest` 等 |
| **③ 磁盘路径** | `new FileSystemResource("src/main/resources/application.yml")` | `HotOtelExporterWiringTest` |

⚠️ **只按关键字 `application.yml` 全局替换是不够的** —— ② 里的 `spring.config.location=classpath:/application.yml`
是**故意**指向**入口文件**的（入口文件再 import 真配置）⇒ ⇒ **机械替换会改错**。

⇒ ⇒ **收口做法**：**逐个打开文件确认它到底要哪一份**（真配置 or 入口文件）⇒ 再改。

## 七、⚠️⚠️ 元教训（本条最值钱的部分）：**并行回归会漏掉后段模块的失败**

S1 收尾时，本仓**先跑并行回归**（`mvn -o -B -T1C clean verify`）⇒ 只报了 **1 个失败**
（`DeadlineBudgetPersistencePgTest`，且**单模块跑 6/6 绿** ⇒ 属 **P-24** 并行假红）
⇒ 看起来「只差一个时间预算类用例」。

⇒ ⇒ **改跑串行**（`mvn -o -B clean verify`）⇒ 才暴露出 **7 个真实失败**：
- **6 个**在 `comment` 域 ⇒ 原因 = 并行时它排在后面，被前面模块的失败**短路跳过**（reactor 报 `SKIPPED`）
  ⇒ ⇒ **它根本没跑** ⇒ ⇒ 它的 6 个失败**一次都没执行过**；
- **1 个**在 `hot` 域 ⇒ 串行跑到它时才暴露。

⇒ ⇒ **根因**：`mvn` 的 reactor 是 **fail-fast** ⇒ 前序模块失败 ⇒ 后序模块 **`SKIPPED`**（不测）
⇒ ⇒ **`SKIPPED` 的模块 = 没验** ⇒ ⇒ **「跑完了」不等于「验过了」**。

⇒ ✅ **纪律**：
1. **全量回归的最终判据必须是串行** —— `-T1C` 只用来做「快筛」，**不能当验收信号**；
2. **看 reactor 汇总里的 `SKIPPED`** —— 出现就说明**有模块没被验**；
3. 若要「一遍跑完且不短路」⇒ 用 `-fae`（fail-at-end）⇒ 失败模块**继续跑**，后段模块也会跑
   ⇒ ⇒ **两遍都要**：`-fae` 拿「**失败面全貌**」，串行拿「**最终验收信号**」。

## 八、⚠️ 追加（2026-11-28 晚）：**「跑单模块」会捡到 `~/.m2` 里的陈旧 jar**

S1 修完 8 个 listener 的 `containerFactory=` 之后，单独跑 `mvn -o -B -pl service/boot/task test`：

```
[ERROR] Could not register Kafka listener endpoint on [kafkaListenerContainerFactory] for bean
        taskArticleCountConsumer, no 'KafkaListenerContainerFactory' with id
        'kafkaListenerContainerFactory' was found in the application context
```

⇒ 看着像「改完还是错」⇒ ⇒ **但全量 reactor 跑是绿的** ⇒ ⇒ 差在哪？

⇒ ⇒ **单模块 `-pl` 跑时装依赖走 `~/.m2`** ⇒ ⇒ 那里躺的是**改动前**装的
`task-domain-1.0-SNAPSHOT.jar`（实测文件时间戳 = 改动前 20 分钟）
⇒ ⇒ 它里面的 listener **仍指向旧 bean 名** ⇒ ⇒ 报错的是**旧字节码**。

🔴 **可复用的判据**（三步）：
1. 报错提到的类/常量**在源码里已经改了** ⇒ ⇒ **先怀疑「跑的不是新字节码」**；
2. `ls -la ~/.m2/repository/<artifact>/1.0-SNAPSHOT/*.jar` ⇒ **看时间戳是否早于你的改动**；
3. `unzip -p <那个 jar> <类路径> | strings | grep <旧名字>` ⇒ ⇒ **直接看 jar 里的字节码**。

⇒ ⇒ **修法**：**先 `mvn install` 再单模块跑**（`mvn -o -B clean install -DskipTests`）
⇒ ⇒ ⚠️ **本仓的 `P-30` 让这件事更容易踩**：域 jar 改名了（`task-service` ⇒ `task-domain`）
⇒ ⇒ ⇒ **旧坐标 `task-service` 的 jar 还躺在 `~/.m2` 里** ⇒ ⇒ 更容易「以为改了但跑的是旧的」。

⇒ ⇒ **元教训**：**「单模块跑失败」与「全量跑失败」不一致时，第一件事是确认「跑的是不是同一份字节码」**
⇒ ⇒ **不是**先怀疑代码改错了。
