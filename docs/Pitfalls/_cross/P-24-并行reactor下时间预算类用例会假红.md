# P-24 · **并行 reactor**（`-T1C`）下「时间预算类」用例会**假红** ⇒ 极易被误判成行为回归

> **登记时间**：2026-11-04（`global` 收口域 · 收口 **DRIFT-COMMON-V20 / D-15** 时暴露）
> **性质**：**验证方法学**的坑（**回归读数的运行环境**会污染「时间敏感」判据）
> **发现者**：D-15 落地后的第一次全量回归

---

## 一、形态

本仓 16 个模块各自带 **真 PG / Redis / Nacos 的 Testcontainers** ⇒ 单模块全量本来就不便宜
⇒ ⇒ 于是大家习惯用 **`mvn -o -T1C test`**（并行）跑全仓回归。

🔴 **问题出在「并行」这两个字上**：并行 ⇒ 多个模块的 **Testcontainers 起容器 + 建 schema + 起 Spring 上下文**
**同时抢 CPU / IO** ⇒ ⇒ **单个用例的墙钟耗时被拉长**。

⇒ ⇒ 而本仓有一类用例**把自己的业务预算当断言**：
- 「到点服务端必须断连」⇒ 断言 `DEADLINE_EXCEEDED`；
- 「预算耗尽 ⇒ 写命令不许下发」；
- 「客户端 deadline 到期 ⇒ 服务端提前放弃」。

**这类用例的通过与否，取决于「墙钟耗时有没有超过那笔预算」，而不只取决于语义对不对。**

⇒ ⇒ 并行争抢 ⇒ **墙钟变慢** ⇒ ⇒ **预算被自己的邻居挤掉** ⇒ ⇒ **假红**。

## 二、🔴 为什么这条特别危险（差点真的回滚了正确的修复）

本轮 D-15 改的**恰好就是「服务端在预算到点时掐断」这条语义**
⇒ ⇒ 并行回归红出来的两条（like / admin 各 1 条）**恰好都报 `DEADLINE_EXCEEDED`**
⇒ ⇒ **症状与「本次改动引入的行为回归」完全一致**
⇒ ⇒ 若不复核，就会：① 判「D-15 引入回归」⇒ ② 回滚共享层 ⇒ ③ 把一个**刚补上的真缺口**（出向载体从未绑上）又埋回去。

**差点**发生 —— 拦住它的是「跑一次同条件对照」这个动作。

## 三、判定式（三步 · 按序做，别跳）

1. **先问「这条红是不是时间敏感」** —— 断言里出现「到点 / 超时 / 预算 / deadline / 耗尽 / 必须在 N ms 内」
   ⇒ ⇒ **它就是时间敏感类** ⇒ ⇒ **不能在并行 reactor 下判红**。
2. **单独串行复跑那条用例**（`mvn -o -pl <模块> -am -Dtest='<那条用例类>' -Dsurefire.failIfNoSpecifiedTests=false test`）：
   - **单独跑绿** ⇒ ⇒ **并行读数不可用于行为判定** ⇒ ⇒ 接着跑**串行全量**拿权威读数；
   - **单独跑也红** ⇒ ⇒ 才进入「是我的错还是被测对象坏」的归因流程。
3. **再跑一次串行全量**（`mvn -o test`，**去掉 `-T1C`**）⇒ ⇒ 那才是可写进台账的读数。
   ⚠️ 串行全量**更慢**（本仓 ≈ 6 分钟）⇒ ⇒ **这是拿到可信读数的代价，不是浪费**。

## 四、实测代价（RAG-V1 · 2026-11-04 · D-15 收口）

- **第一次**（`mvn -o -T1C test`）⇒ **like-service 红 1 条**（`LikeGrpcServiceContractTest.allSixMethodsAreDispatched`
  ⇒ `StatusRuntimeException: DEADLINE_EXCEEDED: rpc deadline exceeded` · 耗时 **2.206s** ≈ 该域 `rpc-timeout: 2s`）
  ＋ **admin-service 红 1 条**（`AdminRpcLogoutClientVisibleGrpcStatusDefaultBehaviorTest.logoutClientSeesDeadlineExceededWhenCommandsAreQueued`
  ⇒ 同一个 `DEADLINE_EXCEEDED`）。
- **判定实验 ①**：**HEAD 版（无 D-15）单独**跑 like 那条 ⇒ **4/4 绿** ⇒ ⇒ 「本来红」不成立。
- **判定实验 ②**：**D-15 单独**跑同样两条 ⇒ like **4/4 绿** ＋ admin **1/1 绿**
  （机器读数 `code=DEADLINE_EXCEEDED description=rpc deadline exceeded elapsedMs=2022` ≈ 该域 2s 预算 ⇒ **正是设计行为**）
  ⇒ ⇒ **D-15 不是根因**。
- **根因**：admin 那条用例**本身要跑 30s**（`Time elapsed: 30.40 s`），而它断言的预算只有 **2s**
  ⇒ ⇒ 并行时稍有 CPU/IO 争抢就超时 ⇒ ⇒ like 那条同理。
- **串行全量**（`mvn -o test`）⇒ **16/16 模块 BUILD SUCCESS · 全绿**。

## 五、附带的一条：**别用「单点相等」替代「同条件对照」**

本轮第一步用的是「HEAD 版单独跑」⇒ 排除了「本来红」；
第二步用「D-15 单独跑」⇒ 排除了「D-15 引入」；
⇒ ⇒ **两步合起来才把「环境」与「代码」分开** ⇒ ⇒ **只做一步都会归因错**
（只做① ⇒ 会误以为「并行下才红 ⇒ 与代码无关」；只做② ⇒ 会直接判「D-15 引入回归」）。

## 六、同族

- 与 P-19「JWT 确定性 ⇒ 黑名单串味 ⇒ 与执行顺序强相关的不稳定失败」同源：**顺序 / 邻居会改写读数**
  —— P-19 改的是**数据**，本条改的是**墙钟**。
- 与 P-23「顺序注入把调用起点差混进读数」同源：**读数里混进了「与被测语义无关的差」**
  —— P-23 混进的是**时刻差**，本条混进的是**资源争抢造成的耗时差**。
- 与「跑绿 ≠ 本来就绿」同源，但**方向相反**：本条是「**跑红 ≠ 本来就红**」
  ⇒ ⇒ **同样必须带「跑法」标注**（AGENTS.md §五.8 规则 ① 的精神：读数要能复现）。
