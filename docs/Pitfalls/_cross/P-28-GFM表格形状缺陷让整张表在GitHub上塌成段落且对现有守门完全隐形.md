## 一、形态（**四个维度，每一个都能让表塌掉**）

GitHub Flavored Markdown 的表格**不是**「有几列就画几列」，而是**先切列、再渲染** ⇒ ⇒
**切列的规则错了 ⇒ 整块根本不被识别为表格**（退化成普通段落）。

| # | 缺陷 | GFM 后果 | 隐蔽度 |
|---|---|---|---|
| **①** | 表块**缺分隔行**（含：被空行切成几块后，续块没有分隔行） | 整块按**普通段落**渲染 | 中（看得出没表格） |
| **②** | **分隔行格数 ≠ 表头格数** | 整块按**普通段落**渲染（GFM §4.10 Ex.200） | 🔴 **高**（内容看着完整） |
| **③** | **数据行格数 ≠ 表头格数** | 多的格**静默丢弃**、少的**补空**（Ex.199） | 🔴 **高** |
| **④** | **inline code 内出现未转义的 `\|`** | 竖线被当**列分隔符** ⇒ 该行多切一列 ⇒ 落到 ③ | 🔴 **高** |

⇒ ⇒ **本仓实测（2026-11-11）**：**110 份 markdown 里 26 份命中、99 处** ⇒ 其中
**`docs/Mapping_Table/` 全套主表**（common / article / comment / favorite / hot / like / message / task）
**分隔行一律写成 3 格、表头却是 4 格** ⇒ ⇒ **「抄写路线图」在 GitHub 上整张表都塌成段落**。

## 三、🔴 检查器自己也会骗你：**代码围栏里的行不是 markdown**

写检查器时踩到的第二个坑（**自测里当场抓到**）：

| 行 | 真相 |
|---|---|
| `find … -name '*.java' \| xargs -n1 basename \| sort -u` | **shell 管道**（在 ```bash 围栏里）⇒ **不是表格行** |
| `\|  \- org.springframework.boot:spring-boot-starter-jackson:jar:4.0.8` | **依赖树输出**（在 ``` 围栏里）⇒ **不是表格行** |

⇒ ⇒ 不认围栏 ⇒ 这两行**以 `|` 开头** ⇒ ⇒ 被当成「一行表格块」⇒ ⇒ **假红**。
⇒ ⇒ 而**假红会淹没真缺陷**（本工具首跑就把 **6 处围栏内容**报成「① 缺分隔行」）。

⇒ ⇒ **判定式**：**检查器必须先标出「围栏内的行」**（``` 或 ~~~ 围起来的整块）⇒ 再判形状。

## 四、🔴 判定式（五条）

1. **分隔行的格数必须等于表头格数** —— 不等 ⇒ **整块不是表**（不是「某列错位」）。
2. **数据行的格数与表头不符** ⇒ 多出的格被**静默丢弃** ⇒ **内容会消失**。
3. **inline code 内的 `|` 也要转义**（写成 `\|`）⇒ GFM 会把它**还原成 `|`** ⇒ **显示不变、表不塌**。
4. **代码围栏内的行不是 markdown** ⇒ 检查器**必须认围栏** ⇒ 否则假红。
5. **判据要有牙齿** ⇒ 用**实测渲染**兜底：`pandoc -f gfm -t html` ⇒ 「渲成 `<table>`」还是「渲成 `<p>`」。

⇒ ⇒ **第 5 条的实测对照（本仓，2026-11-11）**：

```
| A | B | C | D |      | A | B | C | D |
|---|---|---|             |---|---|---|---|
| 1 | 2 | 3 | 4 |      | 1 | 2 | 3 | 4 |
⇒ <p>| A | B | C | D | |---|---|---| | 1 | 2 | 3 | 4 |</p>   ← 不是表
⇒ <table><thead><tr><th>A</th>…            ← 是表
```

## 六、⇒ 通用判据（跨项目可复用）

> **文档的「内容对」与「渲染对」是两个正交维度。**
> ⇒ 若你的检查器只解析内容 ⇒ 它**结构性地看不见**渲染层的问题（表格塌成段落、表格被空行切块、
> 列表缩进塌掉、代码围栏没闭合……）。
> ⇒ ⇒ **补维度的方法**：找一个**独立的渲染器**（`pandoc -f gfm -t html` / `cmark-gfm`），
> 让它**渲染改前与改后** ⇒ 比**文本层**是否等价（**不是**比 HTML）⇒ ⇒ 既能证明「零内容丢失」，又能当场看清「是不是表」。
