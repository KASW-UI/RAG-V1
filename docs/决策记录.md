## 一、已定决策（D1–D14）

> ⚙️ **全项目工具链口径 = Jackson 2 + Spring Boot 3.5（D14 · 2026-11-02 用户定）** —— 框架 · 驱动 · 中间件客户端 · 测试栈 · 第三方 SDK **全部**适配这条线；**任何**新代码 / 新依赖都必须落在这条线上。详见 **D14** + `../AGENTS.md` §1.0d。

### D1 · api 与 rpc 合并为单一 Spring Boot 应用 ✅ 已定

| 项 | 内容 |
|---|---|
| **决策** | 每个业务域**只有一个** `<domain>-service` 模块、一个进程、一个 `@SpringBootApplication` 入口。不再有 `*-api` / `*-rpc` 两个模块。 |
| **依据** | ① Spring Cloud 的部署单元是"可部署服务"，不是"api 层 / rpc 层"；② go-zero 的 api/rpc 分离源于 `.api` 文件与 `.proto` 两条 codegen 路径，是**语言产物**而非架构原则；③ 常规 Spring Boot 实践中，`@RestController` 与 `@GrpcService` 共处一个 app 是默认形态（见 `spring-petclinic` 与 devh `grpc-spring-boot-starter` 官方样例）。 |
| **代价** | ① Go / RAG 形态的 20 个进程 → 本仓库 10 个；② Nacos 注册项减少；③ **"rpc 进程不可用"这一故障模式消失**（属 L3 部署层，不属业务语义）；④ 域的独立扩容能力消失（改横向扩容策略而非加进程）。 |
| **可回退性** | **可回退，但代价高** —— 拆回两个模块要把 `api.service` 与 `rpc.service` 的依赖方向重新分开，并复制一整套样板。 |
| **落地证据** | `service/*/service/` 共 10 个模块（`users` 域为 `service/users/{user,admin}/service/`），各含 1 个 `*ServiceApplication.java`；**全仓 `api/client` 目录 0 个**。<br>⚠️ **物理目录 ≠ artifactId**：目录叫 `service` / `contract`，artifactId 仍是 `<域>-service` / `<域>-contract`（Maven reactor 内需全仓唯一）。 |

#### 🔴 D1 的例外判定已撤销（2026-10-25 · 据 RAG 的实测）

> **触发**：《第二轮深挖-契约盘点》U-2 记录「Go 侧有 8 个 `cmd/` 子命令 + 4 个 `Init/` 文件 ⇒ 独立进程入口
> ⇒ RAG-V1 的树完全没有对应物 ⇒ **D1 需要设例外**」。这是当时**唯一可能推翻 D1** 的一项。

**2026-10-25 实测 Go 侧全部 `cmd/` 目录**（`service/comment/rpc/cmd`、`favorite/rpc/cmd`、
`hot/test/cmd`、`knowledge/cmd`、`like/rpc/cmd`）：

| Go 入口 | 性质 | 结论 |
|---|---|---|
| `comment/rpc/cmd/fact-dispatch`<br>`favorite/rpc/cmd/fact-dispatch`<br>`like/rpc/cmd/fact-dispatch` | **零对外服务** —— `main.go:76` 只调 `communityfact.RunDispatcher` | ✅ **可合并** |

**判定依据（RAG 的组件级对照已先行做出，`docs/FileTree/like/rpc.md:84-97`）**：

> ① 两个 cmd **不注册任何 gRPC 服务** ⇒ 没有强类型契约需要独立进程承载；
> ② `Dispatcher` / `AuthorityHandler` **已经是纯库**（静态工厂 / 返回 Servlet）⇒ 本就是设计给「宿主进程」用的；
> ③ Go 注释 *"keeps retry cadence outside the business RPC process"*（`communityfact/process.go:18-19`）

⇒ **D1 不设例外。** 三域的 `fact-*` 能力作为**域内组件**承载。

### D2 · 域内调用直连，不再自我 gRPC 往返 ✅ 已定

| 项 | 内容 |
|---|---|
| **决策** | 同一进程内，HTTP 层直接注入领域服务 Bean。**跨域**调用仍走 gRPC（见 D6）。 |
| **依据** | 同进程内调 gRPC 是无意义的序列化开销与故障注入点；Go 侧的 `svcCtx.<Domain>Rpc.*`（同域）调用在合并后没有存在理由。 |
| **代价** | ① api 层的"gRPC code → 业务码"映射层消失；② **同一份业务逻辑要能同时产出 HTTP 与 gRPC 两种错误表达** ⇒ 引入统一错误模型（见 D5 的附属设计）；③ 原 `api/client/` 包整体清空。 |
| **可回退性** | 可回退（把直连改回 stub 注入即可），但会重新引入"自我往返"。 |
| **落地证据** | `rpc/client/` 目录 **7 个**（仅跨域：article→message、comment→article/message、favorite→article/user、follow→user、like→message、message→admin/user、hot→article）；`api/client/` **0 个**。 |

### D3 · `service/common` 升级为真 starter ✅ 已定

| 项 | 内容 |
|---|---|
| **决策** | 共享层由"普通 jar + 每个消费者手写 `@Import` 清单"改为**真 starter**：`AutoConfiguration.imports` + `@AutoConfiguration` + `@ConditionalOnMissingBean`。 |
| **依据** | ① Spring 生态里共享能力层的标准形态是 starter，不是手工清单；② RAG 形态实测：`service/common/src/main/resources` **为空** ⇒ 不是 starter ⇒ 10 个 rpc 模块各写一份 4~10 个 Bean 的 `@Import` 清单（10 种写法）；③ `MybatisPlusOrderingBridgeAutoConfiguration` 被复制 **9 遍**，正是"普通 jar 放不下 auto-config"的直接账单。 |
| **代价** | ⚠️ **`@Import` 与 auto-config 不能混用** —— `@Import` 的那一份按 user config 处理（更早求值），会改变 `@ConditionalOnMissingBean` 的语义。⇒ **要么全删 `@Import` 让 auto-config 接管，要么保持现状，不能并存。** |
| **可回退性** | 高 —— 纯结构改动。 |
| **落地证据** | `common/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（7 行）；**全仓 `@Import` 清单 0 个**；MP bridge 副本 **0 个**（收进 starter 的 1 份）。 |

### D5 · DTO 改 immutable record + Bean Validation ✅ 已定

| 项 | 内容 |
|---|---|

### D6 · 跨域调用仍走 gRPC ✅ 已定

| 项 | 内容 |
|---|---|
| **决策** | 跨域调用用 devh `grpc-client-spring-boot-starter` 的 `@GrpcClient`，**不改传输方式**。 |
| **依据** | proto 是 **L1 外部契约**（方法签名、字段号、错误码），改传输就是改契约；而 devh starter 本身已是 Spring 生态做法，不是 Go-ism。 |
| **代价** | ⚠️ **devh 的 `GrpcChannelProperties` 默认 TLS**，而 Go `zrpc.MustNewServer` 是明文 ⇒ **必须显式写 `negotiation-type: plaintext`**，否则静默变 TLS。 |
| **可回退性** | 低 —— 涉及 L1 契约。 |
| **落地证据** | 各域 `application.yml` 的 `grpc.client` 段已带该注释；对应断言 **A4**（见 [`架构符合性断言.md`](架构符合性断言.md)）。 |

### D7 · proto 集中 + 模块打平 + 包压平（2026-10-26 落地）✅ 已定

> **本条是一组耦合的三件事**，合写是因为**顺序不可拆**：包压平依赖模块打平的结果，模块打平依赖 proto 集中的结果。
> ⇒ 拆成 D7/D8/D9 会让「谁依赖谁」这段决策链断在编号里。
> ⚠️ **本条是 D1 的后续**：D1 合并了 api/rpc **两个进程**，D7 把它们留下的**协议层包名**也一并消掉。

| 项 | 内容 |
|---|---|
| **决策** | ① **proto 契约集中**：10 个域的 `.proto` 从各域 `*-contract` 子模块集中到**根级 `proto/` 模块**（Maven 坐标 `com.rag:proto`），pb 类包名 `com.rag.<域>.contract.proto.*` → **`com.rag.proto.<域>.*`。<br>② **模块打平**：删除 10 个 `*-contract` 子模块，每域从「聚合 pom + contract 子模块 + service 子模块」变成**一个 jar 模块**（`service/<域>/`，artifactId `<域>-service`）；各域的 `contract/` 包（错误码 + 事件 DTO）搬进域模块内。<br>③ **包压平**：`api/` + `rpc/` 两层包合并为**单层按技术角色划分的包树**（`controller` / `advice` / `interceptor` / `dto` / `config` / `metrics` / `service` / `grpc` / `domain` / `messaging` / `mapper` / `client` / `wiring` / `exception` / `contract`）。 |
| **依据** | ① **proto 是 L1 外部契约**、跨服务共享 ⇒ 放**一个**根级模块，域模块只依赖它，不再各自带一份（10 份 `.proto` 的副本是漂移源）。pb 类包名必须跟模块坐标走（`com.rag:proto` ⇒ 包根 `com.rag.proto`）—— 且 `admin` 与 `user` 两域有 **8 个同名 message**（`java_multiple_files = true` ⇒ 同名类）⇒ **必须按域分子包**，`com.rag.proto.<域>` 是唯一可行形态。<br>② **契约与实现分离**的诉求仍然成立，但分离粒度从「每域一个契约模块」变成「**全仓一个根级 proto 模块 + 域内 `contract/` 包**」—— 错误契约**逐域隔离**（AGENTS §五.2 R1），放进 `common/` 是错的；但为每域单开一个 Maven 模块只是把**目录**提升成**坐标**，收益不足以抵消 10 份 pom 的维护面。<br>③ **Spring 生态里 HTTP 与 gRPC 共存靠注解区分（`@RestController` vs `@GrpcService`），不靠包** —— `api/` + `rpc/` 这层「协议层」在 Spring 里**没有对应物**，是 go-zero codegen 产物的惯性投影（D1 合并进程后它只剩名字）。实测**压平后「同包 + 同名」真冲突 0 处**（两侧类名本就分层：api 侧带 `Api` 前缀，rpc 侧是 `*DomainService` / `*Mapper` / `*Entity`）。 |
| **代价** | ① **pb 类包名变更** ⇒ 域代码的 `import` 全部要跟着改（`com.rag.<域>.contract.proto.X` → `com.rag.proto.<域>.X`）；这是 **L4 表达层**，wire 契约零影响（proto `package` 才是 L1，见 `DEV-LIKE-PROTO-001` / `DEV-COMMENT-PROTO-001`）。<br>② 10 个 `*-contract` artifactId 消失 ⇒ 任何外部依赖 `com.rag:<域>-contract` 的坐标都要改（本仓内已全部改净）。<br>③ **包名变更面 100%**（503 个 `service/` 下的类的 `package` 声明）—— 越晚做代价越大，故在「按域填实现」之前做。<br>④ 10 个 gRPC 实现类**改名**（`LikeServiceGrpcImpl` → `LikeGrpcService` 等）：`Impl` 后缀在 Spring 生态里通常指「接口的默认实现」，而这些类是**唯一的 gRPC 服务实现** ⇒ `*GrpcService` 更准。 |
| **可回退性** | **中** —— 三件事都是结构改动，**行为层影响 0**；但回退要同步改回 10 份 pom 的 `<modules>` + `<dependency>`、503 个类的 `package` 声明与 `import`、10 个 proto 的 `java_package`，并重生成 13 份 `File_Tree` + 13 份 `Mapping_Table`。⚠️ **一旦「按域填实现」开始，回退成本成倍上升**（每填一个实现都要连带改测试与 import）。 |
| **落地证据** | **16 个 `pom.xml`**（1 根 + `common` + `proto` + `service` 聚合 + **8 个业务域**（article / comment / favorite / follow / hot / like / message / task）+ `users` 聚合 + `users-common` + `user-service` + `admin-service`）；**559 个 `.java`**（**549 主代码 + 10 测试骨架**；`service/` 503 + `common/` 56）；**10 个改名类**（`ArticleGrpcService` / `CommentGrpcService` / `FavoriteGrpcService` / `FollowGrpcService` / `HotGrpcService` / `LikeGrpcService` / `MessageGrpcService` / `TaskGrpcService` / `UserGrpcService` / `AdminGrpcService`，**全部落在 `grpc/` 包**；`PbCommentServiceAlias` **保留原名** —— 它是把同一实现再挂到 `/pb.CommentService/*` 的 Go 兼容别名，不是「实现」）；**10 个 `.proto`** 集中在 `proto/src/main/proto/`（pb 包名 `com.rag.proto.<域>`，`admin` → `com.rag.proto.admin`、`users.proto` → `com.rag.proto.user`）；全仓 `mvn -o clean test-compile` **16/16 BUILD SUCCESS**；`docs/File_Tree/` 重生成 = **13 份模块文档 + `_INDEX.md`**；`tools/check-mapping-coverage.py` ⇒ **EXIT=0，C 列 549/549、A 列 482/482**；`tools/difftest/check-arch-invariants.py` ⇒ **EXIT=0（A1–A12：PASS 8 · N/A 3 · PENDING 1，无 FAIL）**。 |

**四条落地规则**：

1. ✅ **允许** `com.fasterxml.jackson.annotation.*` —— 两代**同包名**，且是 Jackson 3 自己的依赖（`tools.jackson.core:jackson-databind:3.1.5` → `jackson-annotations`）⇒ **不是 Jackson 2 残留，别删**。
2. ❌ **禁止** `com.fasterxml.jackson.{databind,core,module}` —— 业务模块 grep 须归零（`jackson-annotations` 除外，见 ①）。
3. **第三方**：`io.minio:minio` 必排除 `jackson-databind` + `jackson-core`；`jjwt-jackson` **不用** ⇒ 换**自写基于 `tools.jackson.databind.ObjectMapper` 的 `io.jsonwebtoken.io.Serializer`**（⚠️ `jjwt-gson` / `jjwt-orgjson` 的 adapter jar **本地 m2 没有** ⇒ 离线构建下不可用 ⇒ 自写是唯一离线可编译路径）。
   ⇒ **Nacos 侧**：`nacos-client` **必须 ≥ 3.3.0**（根 pom `nacos.version` 单一真源）⇒ 其 JSON Adapter 层会自动选 Jackson 3；**排除** `jackson-core` + `jackson-databind`。
   ⇒ **Flyway 侧**：**不排除**（排除即 `NoClassDefFoundError`）⇒ **它是全仓唯一的 Jackson 2 残留**（第三方黑盒）。

| # | 结论 | 取证方式 | 影响 |
|---|---|---|---|
| 1 | **Jackson 2.19.4 的 coercion API 与 Jackson 3 逐项同构** ⇒ `Coercion` 的**回改量 = 0** | `javap` `jackson-databind-2.19.4.jar`：`MapperBuilder.withCoercionConfig(LogicalType, Consumer<MutableCoercionConfig>)` / `MutableCoercionConfig.setCoercion(shape, action)` / `CoercionInputShape.{Integer,Float,Boolean}` / `LogicalType.Textual` / `CoercionAction.Fail` **全部同名同参存在** | ⚠️ **订正批 1 的评估**：「Jackson 2 无此 API ⇒ `Coercion` 属**真重写**」是**错的** ⇒ 批 1 的批次划分表已改写 |
| 2 | **Jackson 2.19.4 的 `getText()` 对数字返回「原始字面量」** | 探针（`jackson-core-2.19.4.jar`）：`1.50 → "1.50"`、`1e3 → "1e3"`、`-2.5e-7 → "-2.5e-7"`、`1e400 → "1e400"` ⇒ **与 Jackson 3 同语义** | 3 个 Deserializer 的语义（`json.Number` 字面量保真）**原样保住** ⇒ 但这是**版本相关**事实 ⇒ 已由真触发测试钉住（换 Jackson 大版本必红） |
| 3 | **Jackson 2 里根本没有 `ValueDeserializer` 这个类** | `javap` 该包顶层类：只有 `JsonDeserializer` / `KeyDeserializer` | `MapStringValueDeserializer` 的**基类必须换** ⇒ 用 `com.fasterxml.jackson.databind.JsonDeserializer<String>`（语义等价：`NullValueProvider` 的 `getNullValue` 钩子仍在 ⇒ map 元素为 null 仍走同一机制） |
| 4 | **Spring 6.2 的 `AbstractJackson2HttpMessageConverter` 不是 `SmartHttpMessageConverter`** | `javap` 类声明：`extends AbstractGenericHttpMessageConverter<Object>`（只实现 `GenericHttpMessageConverter`）⇒ RAG 覆写的 `canWrite(ResolvableType, Class, MediaType)` / `canRead(ResolvableType, MediaType)` **在 Spring 6.2 下不存在**；`javap -c` 反编译 `AbstractMessageConverterMethodProcessor` / `AbstractMessageConverterMethodArgumentResolver` ⇒ 分支顺序实测为 **Generic → Smart → PLAIN** | `JsonBodyConverter` 的覆写点必须改成 **Type 版三参**（`canWrite(Type, Class<?>, MediaType)` / `canRead(Type, Class<?>, MediaType)`）⇒ **语义等价**（Generic 分支优先 ⇒ 改后的那一版就是被调用的那一版）。⚠️ 好消息：**照抄 RAG 的签名会编译期就红**（`方法不会覆盖或实现超类型的方法`）⇒ **不会静默失效** |

### P4 · `rpc.*` 包是否改名 ＋ 协议层是否压平 ✅ **选项 ③ 已实施（D7 · 2026-10-26）**

> **背景**：D1 合并后，`rpc.*` 承载的是「领域 / 服务端能力层」，不再是「RPC 进程」⇒ 名字已不准。
> **2026-10-25 追加**：更进一步 —— **`api/` + `rpc/` 这层协议层本身**是否该保留，也已成问题：
> Spring 里 HTTP 与 gRPC 共存靠**注解**区分（`@RestController` vs `@GrpcService`），**不靠包**。
>
> ✅ **2026-10-26 结论：选项 ③（压平协议层）已实施** ⇒ 记入 **D7**（proto 集中 + 模块打平 + 包压平）。
> ⇒ 本条**只剩 P4-④ 的剩余 6 个**（`common/logger/` 1 · `common/observability/` 1 · 域内 4，见下）—— 其余 23 个已改（D8）。

| 选项 | 说明 |
|---|---|
| ① 不改（记技术债） | 合并后 `rpc.*` 实际承载"领域 / 服务端能力层"，名字已不准。 |
| ② 改 `domain.*` 或 `service.*`（**保留协议层**） | 语义更准。 |
| ③ **压平协议层**（`api/` + `rpc/` → 顶层平铺） | 更接近 Spring 惯例树。⚠️ **实测 0 处「同包+同名」真冲突**（两侧类名本已分层：api 侧带 `Api` 前缀，rpc 侧是 `*DomainService`/`*Mapper`/`*Entity`）。代价 = **549 个类**的 package 声明 + **13 份** File_Tree + **13 份** Mapping_Table 重生成 + **A12** 复检；**行为层影响 0** |

> ✅ **结论（2026-10-26）**：**选 ③**，已实施 ⇒ 见 **D7**。当时的预算是「549 个类 + 23 份 File_Tree」，
> 实际落地时因**模块打平**（`*-contract` 子模块删除）变成了「**503 个类 + 13 份 File_Tree**」⇒ 比预估**更省**。

> **P4-④（剩余项）**：**6 个** `GoStyle*` / `GoCompatible*` 是否**批量改名**（RAG 仓侧 64 个 → 本仓原 22 个 → **已改 16 个**（D8）→ 余 6 个；**欠的是名字不是实现**）—— **仍未拍板**。
