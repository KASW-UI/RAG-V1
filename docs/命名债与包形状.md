## 〇之二、物理目录 ≠ artifactId（2026-10-25 `service/` 改造的产物 · 2026-10-26 D7 后仍成立）

> **`service/` 已改 Maven Aggregator 嵌套结构**：物理目录改**短名**，**artifactId 保持长名唯一**。
> ⇒ 这一条**不是命名债**（artifactId 本身没动），但**是新的认知负担** —— 写路径时极易把两者搞混。

| 层 | 值（2026-10-26 · D7 之后） | 说明 |
|---|---|---|
| **物理目录** | `service/<域>/`（**每域一个 jar 模块**）<br>`service/users/common/` · `service/users/user/` · `service/users/admin/`<br>`common/`（starter）· `proto/`（proto 契约根模块） | **短名**，按域分组 |
| **artifactId** | `<域>-service`（**8 个业务域** + `user-service` + `admin-service`）· `users-common` · `common` · `proto` | **长名**，全仓唯一 |

**为什么 artifactId 不跟着改短**：Maven reactor 内 **artifactId 必须唯一**。13 个叶子模块若都叫 `service` / `contract` 就无法解析依赖 ⇒ 改目录不改坐标 ⇒ **所有 `<dependency>` 声明零改动**。

**踩坑点（已发生一次）**：文档生成器原本用**目录名**渲染 artifactId（`base.name`），目录改短后 23 份 `File_Tree` 全报错 artifactId（写 `service`，实际 `article-service`）。
⇒ 已修为从 pom 读真值（`tools/gen-file-tree.py` 的 `pom_artifact_id()`，**跳过 `<parent>` 块**）。
⇒ **`docs/File_Tree/` 现在分两行**：`模块路径`（物理）+ `artifactId`（坐标）。
⚠️ **D7 之后又多了一个坑**：目录 `service/users/user/` 的 artifactId 是 `user-service`（**不是** `users-user-service`）⇒ 仍然必须读 pom，不能用目录名反推。

## 一、形状债：`api/` + `rpc/` 协议层包裹了技术层 ✅ **已清零（2026-10-26 · D7）**

> ✅ **本节已实施** —— 压平后的真实形态见 §一·五；本节保留为**实施记录**（含实测代价）。

### 1.1 现状 vs Spring 惯例

**Spring Boot 惯例（一个 app 内）**：

```
com.example.app
├── AppApplication.java
├── controller/     ← @RestController
├── service/        ← @Service
│   └── impl/
├── repository/     ← @Repository（MyBatis-Plus 项目写 mapper/）
├── entity/ 或 domain/
├── config/         ← @Configuration
├── dto/            ← request/response record
├── exception/      ← @RestControllerAdvice
└── metrics/
```

**RAG-V1 现状（每个 `*-service`）**：

```
com.rag.like
├── LikeServiceApplication.java
├── api/            ← 协议层（HTTP）
│   ├── controller/  dto/  advice/  config/  interceptor/  metrics/  service/
└── rpc/            ← 协议层（gRPC）
    ├── domain/  mapper/  service/{impl}  exception/  config/  bootstrap/  client/  metrics/
```

> ⚠️ **底下的技术分层全是标准 Spring 命名**（controller / service / domain / mapper / config / dto / exception / interceptor / advice / metrics），
> **唯独外面多包了一层 `api/` + `rpc/`** —— 而**协议层在 Spring 生态里没有对应物**：
> Spring 里 HTTP 与 gRPC 共存靠**注解**区分（`@RestController` vs `@GrpcService`），**不靠包**。

### 1.2 根因

**D1 决定 api + rpc 合并为同一进程后，go-zero 的 `api` / `rpc` 二分被原样保留成了包名。**
⇒ 合并前它们是两个**进程**，包名对应进程；合并后它们是同一进程内的**两个协议栈**，包名却还在。

> 📌 **与 [`决策记录.md`](决策记录.md) P4 的区别**：P4 问的是「包**叫** `rpc.*` 准不准」（选项 ② = 改名，但保留层）；
> **本文问的是「这层本身该不该存在」**（选项 ③ = 去掉协议层）—— **P4 原文没有这一项**。

### 1.3 选项 ③：压平协议层 —— 实测代价极低

**压平后每个 `*-service` 变成**：

```
com.rag.like
├── LikeServiceApplication.java
├── advice/         ← api 侧（@RestControllerAdvice / ResponseBodyAdvice）
├── bootstrap/      ← rpc 侧（NacosRegistration / *SchemaGate / *FactDispatchScheduler）
├── client/         ← rpc 侧（跨域 gRPC client）
├── config/         ← api + rpc 合并
├── controller/     ← api 侧
├── domain/         ← rpc 侧（实体）
├── dto/            ← api 侧
├── exception/      ← rpc 侧（业务异常）
├── interceptor/    ← api 侧
├── mapper/         ← rpc 侧（MyBatis-Plus BaseMapper）
├── metrics/        ← api + rpc 合并
└── service/        ← api + rpc 合并
    └── impl/       ← rpc 侧
```

**实测结论（`os.walk` 遍历全部 10 个 app / 549 个类）**：

| 指标 | 实测值 |
|---|---|
| **压平后「同包 + 同名」真冲突** | **0 处** ✅ |
| api / rpc 两侧共有的扁平包 | **26 个**（全部是 `config/` / `metrics/` / `service/`） |
| 只在 api 侧的扁平包 | `advice/` · `controller/` · `dto/` · `interceptor/` |
| 只在 rpc 侧的扁平包 | `bootstrap/` · `client/` · `domain/` · `exception/` · `mapper/` · `service/impl/` |

**为什么零冲突**：两侧类名**本来就分层了** —— api 侧一律带 `Api`/`Api*`（`LikeApiService` / `LikeApiSupport` / `LikeApiProperties` / `LikeApiMetrics`），
rpc 侧是 `*DomainService` / `*Mapper` / `*Entity` / `*RpcProperties` / `*RpcMetrics`。
⇒ **压平只改 `package` 声明，不改任何类名、不改任何 import 语义。**

**代价**（诚实版）：

| 项 | 量 |
|---|---|
| 需改 `package` 声明的类 | **549 个**（含 10 个 `*-contract`） |
| 需重跑的生成器 | `python3 tools/gen-file-tree.py`（**23 份**文件树） |
| 需重写的映射文档 | `docs/Mapping_Table/` **13 份**域文档（C 列路径全变） |
| 需复检的断言 | **A12**（一个模块内不得有同名简单类）—— 压平后同类同包概率上升，**必须重跑** |
| 需重跑的守门 | `tools/check-mapping-coverage.py`（C 列 549/549 必须仍绿） |
| **行为层影响** | **0** —— 全是包路径，不触 L1/L2 |

### 1.4 压平后仍不是 100% Spring 惯例（残余项）

| 残余 | Spring 生态的对应 | 判定 |
|---|---|---|
| `bootstrap/` | Spring 用 `config/` 或 `initializer/`；`@Component` / `ApplicationRunner` 也常见 | ⚠️ **可接受**（Spring 项目里 `bootstrap/` 并不罕见） |
| `domain/`（实体） | `entity/`（Spring Data）或 `domain/`（DDD） | 🟢 **两种都常见**，Spring Data 项目用 `domain/` 不违和 |
| `mapper/`（MP） | `repository/`（JPA）或 `mapper/`（MyBatis-Plus 主流） | 🟢 **MyBatis-Plus 生态主流写法** |
| `advice/` | `@RestControllerAdvice` 常放 `advice/` 或 `exception/` | 🟢 **两者都是惯例** |

⇒ **压平后 ≈ 90% 是标准 Spring 树**，残余项均可接受。

### 1.5 最终形态（2026-10-26 实测 · D7 落地后）

**打平后的模块坐标（16 个 `pom.xml`）**：

```
pom   RAG-V1         modules=3   .            ← common / service / proto
jar   common         modules=0   common
jar   proto          modules=0   proto         ← ★ 10 个 .proto 集中于此
pom   service        modules=9   service
jar   article-service / comment-service / favorite-service / follow-service
jar   hot-service / like-service / message-service / task-service
pom   users          modules=3   service/users
jar   users-common   modules=0   service/users/common
jar   user-service   modules=0   service/users/user
jar   admin-service  modules=0   service/users/admin
```

**打平后的域内包树**（以 `like` 域为例，10 域同构）：

```
service/like/src/main/java/com/rag/like/
├── LikeServiceApplication.java
├── advice/       bootstrap/    client/       config/
├── contract/     controller/   domain/{entity,model,service}/
├── dto/          exception/    grpc/         interceptor/
├── mapper/       messaging/    metrics/      service/
```

| 项 | 压平前（2026-10-25） | 压平后（2026-10-26 · D7） |
|---|---|---|
| 模块数 | **35** 个 `pom.xml` | **16** 个 `pom.xml` |
| 叶子模块 | 22 | **13**（`common` + `proto` + **8 个业务域 jar** + `users-common` + `user-service` + `admin-service`）|
| 域内包层 | `api/` + `rpc/` **两层** | **单层**（14 个技术角色包）|
| 契约落点 | 每域一个 `*-contract` 模块 | **根级 `proto/` 模块** + 域内 `contract/` 包 |
| gRPC 实现类 | `<域>ServiceGrpcImpl`（在 `rpc/service/impl/`） | `<域>GrpcService`（在 `grpc/`）—— 10 个类改名 |
| pb 类包名 | `com.rag.<域>.contract.proto.*` | **`com.rag.proto.<域>.*`** |
| 需改 `package` 声明的类 | 预估 **549** | **实测 503**（`service/` 下）—— 比预估**少 46**，因为 `*-contract` 模块的 10 个模块与 46 个类先被合并掉了 |
| 需重跑的生成器 | **23** 份 File_Tree | **13** 份 + `_INDEX.md` |
| **行为层影响** | **0** | **0** |

**残余的 Spring 非惯例项**（与上表 §1.4 一致，未变）：`bootstrap/` ⚠️ 可接受 · `domain/` 🟢 · `mapper/` 🟢 · `advice/` 🟢。

**逐域 B → C 包对照** ⇒ 见 [`Mapping_Table/`](Mapping_Table/_INDEX.md) 各域文档的 **§0.5「B → C 结构映射速查表」**（10 域 + users 3 份 + common，共 13 份）。

## 二、命名债：`GoStyle*` / `GoCompatible*` 共 22 个 ⏳ **仍在（P4-④）**

### 2.1 事实

| 位置 | 数量 | 说明 |
|---|---|---|
| `common/web/` | **16** | Go 的 JSON / 表单 / 错误形状兼容层（`GoStyleJsonBodyConverter` / `GoStyleCoercion` / `GoStylePlainTextErrors` / `GoStyleRouterErrorResponses` …） |
| `common/logger/` | **1** | `GoStyleLogger implements org.slf4j.Logger`（G-4：承载 `call_chain` 字段，SLF4J 无等价） |
| `common/observability/` | **1** | `GoStyleRequestDeadline` |
| 域内（4 个） | **4** | `service/follow/src/main/java/com/rag/follow/mapper/GoStyleLimitOffset.java` · `service/message/src/main/java/com/rag/message/mapper/GoStylePagination.java` · `service/like/src/main/java/com/rag/like/service/GoCompatibleJson.java` · `service/task/src/main/java/com/rag/task/config/GoStyleRawBodyArgumentProcessor.java` |
| **合计** | **22** | 对比：RAG 仓库侧有 **64** 个 ⇒ 已减 66%，但**未清零** |

> ⚠️ **D7 后的路径已更新** —— 4 个域内类的位置随包压平变了（`follow/rpc/mapper/` → `mapper/`；`message/rpc/mapper/` → `mapper/`；`like/rpc/service/` → `service/`；`task/api/config/` → `config/`）⇒ 数量仍是 22，**位置已变**。

> ✅ **这些类本身是必要的** —— 它们承载 Go 的**行为兼容**（JSON 读取判据、类型强转、400 错误形状、`call_chain` 日志字段），
> D5 只删掉了 `GoStyleRequired*` / `GoStyleRequest` 这一族（校验改 Bean Validation）。
> ⇒ **欠的是「名字」，不是「实现」。**

### 2.2 目标名（推导文档已给）

`完全spring化的文件树.md` 的映射表里已写明目标名，例如：

| 现名 | 目标名 | 依据 |
|---|---|---|
| `GoStyleJsonBodyConverter` | `JsonBodyConverter` | §5 映射表（保留 `withJson` 的字面判据） |
| `GoStyleCoercion` | （并入 `RagJacksonAutoConfiguration` 的 `CoercionConfig`） | 已是 Jackson 原生机制 |
| `GoStyleLogger` | （保留 SLF4J 实现，去 `GoStyle` 前缀） | G-4：`call_chain` 是行为契约，类名不是 |

> ⚠️ **改名的前置条件**：`common/` 是 starter，**被 10 个 app 直接依赖** ⇒ 每次改名要锁住全部 10 域构建（§五.3 · R1）。
> ⇒ 建议**一次性批量改** + 配一条**覆盖全部 22 处的守恒断言**（§3.3-2 的守恒断言纪律）。
