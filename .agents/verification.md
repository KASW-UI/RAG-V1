# RAG（Spring Boot 4）→ RAG-V1（Spring Boot 3.5）迁移审核 Prompt

## 0. 本次任务定义

本次任务是：

**Java → Java，Spring Boot 4 → Spring Boot 3.5，在目标文件树不同、存在多文件合并、拆分、职责上收和框架接管的情况下，审核迁移后的实现是否完整保留源项目的实际行为。**

本次迁移只有两个项目：

- **RAG**：迁移源项目，Java + Spring Boot 4。
- **RAG-V1**：迁移目标项目，Java + Spring Boot 3.5。

本次不是：

- 上游 → Java 代码翻译。
- 重新设计 Java 项目架构。
- 重新生成目标文件树。
- 重新制作文件映射表。
- 逐文件复制代码。
- 仅比较两个项目的代码差异。
- 仅检查 Maven 编译是否通过。
- 重新判断 RAG 的业务设计是否正确。

本次最终目标：

**确认 RAG-V1 是否完整承接了 RAG 的实际实现职责，并且在 Spring Boot 3.5 环境下没有发生未经批准的行为漂移。**

---

# 一、两个项目的角色必须严格区分

| 标识 | 项目 | 作用 |
|---|---|---|
| B | RAG | Java + Spring Boot 4，迁移源项目 |
| C | RAG-V1 | Java + Spring Boot 3.5，迁移目标项目 |

## 1.1 B：RAG（Spring Boot 4）

B 是本次迁移的直接源项目，也是行为对比基线。

必须以 B 的实际代码为依据，提取：

- 实际类和方法职责。
- 实际执行流程。
- 实际调用关系。
- 实际业务分支。
- 实际异常路径。
- 实际状态变化。
- 实际副作用。
- Spring 容器行为。
- 框架和第三方依赖提供的运行时行为。

注意：

B 是本次迁移的行为基线。

本次审核不需要重新判断 B 的实现是否符合其他项目的设计，也不需要回看其他语言的历史实现。

如果 B 本身存在已知问题，仍然以 B 的实际行为作为本次迁移对比基线，但必须记录该问题，避免将源项目原有问题误报为迁移引入的问题。

必须区分：

1. B 原有的已知问题。
2. C 新引入的问题。
3. C 对 B 原有行为的意外改变。
4. 已经获得明确批准的主动行为变更。

不能把 B 原有问题误报为 C 的迁移问题，也不能因为 B 原本存在问题，就忽略 C 新产生的问题。

## 1.2 C：RAG-V1（Spring Boot 3.5）

C 是实际审核对象。

必须检查 C 的真实源码、配置、POM、Bean 注册和测试。

不能因为 File_Tree 中规定了某个文件，就认为该文件已经实现。

不能因为 Mapping_Table 中存在映射关系，就认为对应职责已经落地。

目标代码当前是否正确，必须以实际实现和验证证据判断。

# 二、现有资料的使用规则

本次审核必须优先使用已经存在的两套资料。

## 2.1 Mapping_Table：迁移映射依据

Mapping_Table 已经建立项目文件及职责之间的映射关系。

**本次只使用 RAG → RAG-V1 对应关系。**

如果 Mapping_Table 保留了其他历史项目或历史映射列，这些内容不属于本次迁移审核范围，不得将其作为第三个项目引入审核。

Mapping_Table 已经包含：

- 文件路径对应。
- 文件职责对应。
- 1:1 映射。
- 1:N 映射。
- N:1 映射。
- C 新增。
- 模块合并。
- 包结构压平。
- 共享能力上收。
- 框架能力接管。
- 文件删除和职责迁移。
- 映射备注及特殊约束。

**禁止重新从零制作一份 Mapping_Table。**

**禁止为了获得一对一文件关系，破坏已经确定的目标结构。**

但必须注意：

Mapping_Table 主要回答文件名和职责落点的对应关系，不直接证明行为已经对齐。

因此：

- 映射关系只能作为定位依据。
- 映射类型不能作为实现完成证据。
- 映射备注不能代替源码核查。
- 映射表中的历史路径必须检查是否仍然有效。
- 映射表中的 GAP 必须检查当前是否已经解决。

如果映射表与当前仓库实际状态不一致，记录差异，不要擅自修改映射表。

## 2.2 File_Tree：目标架构约束

File_Tree 已经定义 RAG-V1 的目标结构。

它用于判断：

- C 的目标文件应该位于哪里。
- 各包和模块承担什么职责。
- 哪些职责被集中到 common starter。
- 哪些职责被合并到单一 Spring Boot 应用。
- 哪些职责被拆分到不同技术角色包。
- 哪些原有组件已经由 Spring 或第三方基础设施接管。

**禁止重新设计 File_Tree。**

**禁止要求 C 为了对应 B 而恢复 B 的文件结构。**

如果 C 的实际结构与 File_Tree 不一致，单独记录结构偏差，并判断是否为已批准的变更。

## 2.3 资料之间的优先关系

遇到冲突时，按以下原则处理：

1. B 的实际源码：本次迁移的直接行为基线。
2. C 的实际源码：本次被审核的实现。
3. Mapping_Table：RAG → RAG-V1 的责任定位依据。
4. File_Tree：C 的目标结构和职责约束。
5. 已有决策记录及已批准的变更：用于判断哪些差异是有意且允许的。

注意：

已批准的决策可以改变迁移要求，但不能仅凭某个文件中写了 TODO 或某个映射备注，就推定已经获得批准。

# 三、本次审核的核心原则

## 3.1 行为等价，不要求文件结构等价

B 和 C 不需要拥有相同的：

- 文件数量。
- 文件名称。
- 包路径。
- 模块数量。
- 类数量。
- 方法组织方式。

允许：

- 多个 B 文件合并到一个 C 文件。
- 一个 B 文件拆分成多个 C 文件。
- B 的多个模块合并为 C 的单一 Spring Boot 应用。
- B 的共享能力集中到 C 的 common starter。
- Spring Boot 3.5 接管原先由 Boot 4 提供的某项框架职责。
- 使用其他等价的第三方组件实现原有能力。

但是：

**文件结构可以变化，源项目需要保留的行为不能因为结构变化而消失。**

## 3.2 多文件合并不能降低审核覆盖率

例如：

B：

- A.java
- B.java
- C.java

C：

- D.java

不能只审核 D.java 的主要方法。

必须分别检查 A、B、C 原本承担的每项职责是否被 D 完整承接。

尤其检查：

- 原有执行顺序。
- 原有条件分支。
- 原有异常处理。
- 原有状态变化。
- 原有事务边界。
- 原有线程和异步行为。
- 原有资源生命周期。
- 原有外部副作用。

合并后如果多个职责被集中到同一类，还要检查是否产生新的共享状态、调用顺序或生命周期问题。

## 3.3 文件拆分不能造成职责断裂

如果 B 的一个文件拆成多个 C 文件：

必须把这些 C 文件作为一个整体审核。

检查：

- 调用链是否完整。
- 数据是否完整传递。
- 异常是否正确传播。
- 事务边界是否保持。
- 是否存在重复执行。
- 是否存在遗漏执行。
- 是否改变初始化或销毁时机。

## 3.4 Spring 接管必须有真实证据

如果 B 的某项职责在 C 中不再由手写代码承担，而是交给 Spring Boot 3.5 或其他基础设施：

必须证明：

1. B 原来承担什么职责？
2. C 使用什么组件接管？
3. 该组件在什么时候执行？
4. 由什么配置触发？
5. 是否真正注册到了运行链路？
6. 输入和输出是否一致？
7. 异常如何处理？
8. 生命周期是否一致？
9. 是否保留原有副作用？

仅仅存在一个 Bean、Configuration 或 Starter，不代表职责已经接管。

必须检查它是否真正进入运行链路。

# 四、第一阶段：确认迁移范围和现状

开始前先读取：

1. Mapping_Table 对应模块的文档。
2. File_Tree 对应模块的文档。
3. B 对应模块的实际源码。
4. C 对应模块的实际源码。
5. 本模块相关的决策记录和已有 DRIFT 记录。

先确认：

- B 的实际 Spring Boot 版本。
- C 的实际 Spring Boot 版本。
- Spring Framework 版本。
- 关键依赖版本。
- 当前模块路径。
- B 和 C 的实际文件数量。
- 是否存在尚未实现的目标文件。
- Mapping_Table 是否与实际路径一致。
- File_Tree 是否与当前目标结构一致。

不要相信旧报告中的文件数量就是当前数量。

如果存在时间较早的统计数据，以当前仓库实测为准。

本阶段只确认当前审核范围，不要顺手扫描无关模块。

# 五、第二阶段：建立 B → C 职责承接清单

这是本次审核的核心。

不要重新设计映射表，而是将已有 Mapping_Table 转换为本次审核所需的行为承接清单。

## 5.1 按 B 的源文件逐项提取职责

对于每个 B 源文件，识别：

- 类的实际职责。
- 所有实际执行的方法。
- 方法之间的调用关系。
- 对外提供的能力。
- 输入和输出。
- 状态变化。
- 数据库操作。
- 外部调用。
- 异常路径。
- 线程和异步行为。
- Spring 生命周期行为。
- 资源创建和释放。

不要只看 JavaDoc 或 Mapping_Table 的职责描述。

必须核对实际源码。

## 5.2 根据 Mapping_Table 找到 C 的承接位置

每项职责都要找到 C 中实际承接它的位置。

允许：

- 一对一。
- 一对多。
- 多对一。
- 多对多。
- Spring 接管。
- 第三方组件接管。
- 有依据的删除或取消。

使用以下审核表：

| ID | B 源文件/方法 | B 原始职责 | C 承接文件/方法 | 映射类型 | 当前实现状态 | 证据 |
|---|---|---|---|---|---|---|

每项 B 职责都必须有明确的承接结果。

如果找不到：

- 不允许直接忽略。
- 不允许根据文件名称推测。
- 不允许认为 Spring 自动处理了。
- 标记为 NOT_IMPLEMENTED 或 NOT_VERIFIED。

## 5.3 检查映射遗漏

重点检查：

- B 有实现，Mapping_Table 没有记录。
- Mapping_Table 有记录，C 没有实现。
- Mapping_Table 指向的文件已经改名或移动。
- 多文件合并后遗漏了某个源文件的次要方法。
- 共享能力上收后遗漏了原有消费方。
- 原有独立进程合并后遗漏了定时任务或消息监听。
- 原有 API / RPC 合并后遗漏了入口行为。
- C 新增文件是否有明确职责和依据。

映射表没有覆盖到的实际源职责，也必须登记。

# 六、第三阶段：完整行为审核

建立职责映射后，开始逐项审核实际行为。

## 6.1 外部契约

检查：

- HTTP 路径和方法。
- 请求参数。
- 请求体。
- 响应体。
- 状态码。
- Header。
- Content-Type。
- 错误码和错误消息。
- RPC 方法及字段。
- Protobuf 字段号。
- Kafka Topic。
- Kafka 消息结构。
- JWT claims。
- 数据库表和字段契约。

如果 B 和 C 在某个外部契约上存在差异，必须查找批准依据。

不能将 Boot 版本变化作为修改外部契约的理由。

## 6.2 业务执行流程

逐条检查：

- 正常执行流程。
- 所有条件分支。
- 状态转换。
- 数据读取和写入。
- 调用其他服务。
- 消息发布和消费。
- 幂等处理。
- 并发控制。
- 缓存读写。
- 重试。
- 补偿。
- 资源清理。

不能只审核入口方法。

必须沿实际调用链追踪到产生最终行为的位置。

## 6.3 异常语义

检查：

- 异常类型。
- 异常捕获位置。
- 异常转换。
- 异常传播。
- HTTP 错误映射。
- RPC 错误映射。
- 消息失败处理。
- 数据库异常。
- 事务回滚。
- 重试和死信。
- 资源释放。

特别注意：

C 不能因为使用了不同的 Spring 异常处理机制，就意外改变 B 原本的错误码、状态码或回滚行为。

## 6.4 状态和副作用

检查：

- 数据库最终状态。
- Redis 最终状态。
- Kafka 消息。
- Outbox / Inbox 记录。
- 外部服务调用。
- 文件和对象存储。
- 指标和日志。
- 定时任务执行。
- 线程和连接资源。

同样的返回值，不代表副作用相同。

# 七、第四阶段：Spring Boot 4 → 3.5 专项审核

必须建立独立的框架差异清单。

不能因为业务代码看起来相同，就认为框架运行行为一致。

也不能因为框架 API 不同，就直接判定业务行为不同。

每项差异都必须经过行为影响判断。

## 7.1 依赖体系

检查：

- Spring Boot。
- Spring Framework。
- Spring Cloud。
- Spring Cloud Alibaba。
- Nacos Client / Server。
- Servlet API。
- Tomcat。
- Jackson。
- Spring Security。
- Spring Data Redis。
- Kafka。
- MyBatis / MyBatis-Plus。
- 数据库驱动。
- MinIO SDK。
- 其他影响运行行为的第三方依赖。

检查实际解析版本，而不是只看 POM 中声明的版本。

检查：

- 编译依赖。
- 运行时依赖。
- 传递依赖。
- 自动配置模块。
- 最终打包依赖。
- 是否存在版本冲突。

## 7.2 Spring 自动配置

检查：

- 自动配置类名称及包位置。
- 自动配置条件。
- `@AutoConfiguration`。
- `@Import`。
- `AutoConfiguration.imports`。
- Bean 注册。
- Bean 覆盖。
- Bean 条件。
- 配置属性。
- 默认值。
- 自动配置顺序。

特别检查 Boot 4 → 3.5 之后，原先的自动配置是否仍然真正生效。

不能只证明 Bean 存在，还要证明对应功能已经进入执行链。

## 7.3 Web 和 Servlet 行为

检查：

- Filter。
- Interceptor。
- ArgumentResolver。
- HttpMessageConverter。
- ControllerAdvice。
- 异常解析。
- 请求体读取。
- 响应序列化。
- Header。
- Content-Type。
- HTTP 状态码。
- 请求路径匹配。
- CORS。
- 请求参数绑定。
- 文件上传。
- 请求大小限制。

特别检查 Tomcat 11 → Tomcat 10.1 以及 Servlet API 变化是否影响真实 HTTP 行为。

不能只用 MockMvc 结果代替真实 HTTP 验证。

对于重要 HTTP 契约，优先使用真实容器验证。

## 7.4 Jackson 和 JSON

如果 B、C 使用不同 Jackson 主版本，必须检查：

- ObjectMapper / JsonMapper 创建。
- 默认配置。
- Coercion。
- Serializer / Deserializer。
- JsonNode。
- 类型转换。
- 空值。
- 缺省值。
- 数字精度。
- 尾随 Token。
- 未知字段。
- 异常类型。
- HTTP Converter。
- Kafka 和 Outbox JSON 解析。

必须对相同输入进行对拍。

注意独立创建的 ObjectMapper，不能只检查 Spring 管理的 ObjectMapper。

还要检查第三方组件是否使用自己的 Jackson 运行时。

## 7.5 事务和数据库

检查：

- `@Transactional`。
- 事务传播。
- 回滚规则。
- 自调用。
- 代理行为。
- 事务管理器。
- 数据源。
- MyBatis 执行。
- 批量写入。
- 数据库异常转换。
- 多数据源。
- 连接池。

重点判断框架版本变化是否改变了事务覆盖范围和提交时机。

## 7.6 安全

检查：

- Spring Security Filter Chain。
- JWT 解析。
- JWT 签名和过期验证。
- SecurityContext。
- 密码编码。
- 权限检查。
- 无认证响应。
- 权限不足响应。
- CORS / CSRF。
- 认证信息清理。

## 7.7 生命周期和异步执行

检查：

- Bean 初始化顺序。
- `@PostConstruct`。
- `InitializingBean`。
- `SmartLifecycle`。
- `@PreDestroy`。
- 线程池。
- `@Async`。
- 定时任务。
- Kafka Listener。
- 消费确认。
- 重试。
- 应用关闭时的资源释放。

## 7.8 Spring Cloud Alibaba / Nacos

重点检查：

- Nacos 配置加载。
- 服务注册。
- 服务发现。
- 实例心跳。
- 注销。
- Naming Client。
- 配置中心。
- 自动配置。
- 启动和关闭。
- 连接失败和恢复。

必须区分 Spring Cloud Alibaba 与 Nacos Client 的版本兼容性。

不能只凭版本号推断兼容，也不能只凭编译通过判断兼容。

# 八、第五阶段：重点审核文件合并、拆分和架构调整

这部分必须单独形成审核结果。

## 8.1 多文件合并

对每个 N:1 映射：

- 列出所有 B 源文件。
- 列出每个文件的全部实际职责。
- 找出 C 的承接位置。
- 逐项核对执行流程。
- 检查异常边界。
- 检查事务边界。
- 检查副作用。
- 检查生命周期。

禁止只比较合并后的主类。

## 8.2 一对多拆分

对每个 1:N 映射：

- 找出所有 C 承接文件。
- 检查各文件之间的调用关系。
- 检查数据传递。
- 检查异常传播。
- 检查事务范围。
- 检查是否存在职责断裂。

## 8.3 API + RPC 合并

如果 B 原来存在独立 API 和 RPC 模块，而 C 合并为单一 Spring Boot 应用：

必须检查：

- HTTP 入口是否完整保留。
- gRPC 入口是否完整保留。
- RPC Server 是否正确启动。
- RPC Client 是否正确注册。
- 原有域内 RPC 往返是否按照既定设计调整。
- API 和 RPC 共用的 Bean 是否正确装配。
- HTTP 与 RPC 的安全上下文是否受到影响。
- 两类入口是否出现不必要的共享状态。
- 应用启动和关闭时，两类服务是否都正确工作。

## 8.4 Common Starter 共享能力上收

如果 B 的多个模块各自拥有某项配置或基础设施能力，而 C 将其合并到 common starter：

必须检查：

- 原有各消费方是否都被覆盖。
- 原有配置是否全部保留。
- 原有 Bean 是否仍然存在。
- 是否出现重复 Bean。
- 是否改变自动配置条件。
- 是否改变装配顺序。
- 是否改变线程和资源生命周期。
- 是否出现某些域能够使用、某些域无法使用的情况。

共享代码减少不等于迁移完整。

尤其要检查原先各模块独立注册的能力，是否因为统一自动配置而出现覆盖遗漏。

## 8.5 独立进程合并

如果 B 中原有独立可执行进程或独立任务被 C 合并进 Spring Boot 应用：

检查：

- 原有任务入口。
- 执行频率。
- 启动条件。
- 关闭条件。
- 并发控制。
- 重复执行保护。
- 任务失败处理。
- 资源隔离。

不能因为任务类已经存在，就认为原有独立进程行为已经被保留。

# 九、第六阶段：行为对拍和验证

对关键行为使用相同输入比较 B 与 C。

优先验证：

1. HTTP 请求和响应。
2. RPC 请求和响应。
3. JSON 解析和序列化。
4. 错误码和异常映射。
5. 数据库最终状态。
6. 事务提交和回滚。
7. Kafka 消息内容。
8. 消息发送时机。
9. 幂等和重复请求。
10. JWT。
11. Redis 状态。
12. 定时任务和生命周期。

对拍必须覆盖：

- 正常路径。
- 边界输入。
- 空值和缺省值。
- 非法输入。
- 类型不匹配。
- 重复请求。
- 并发请求。
- 外部依赖失败。
- 超时。
- 部分成功。
- 恢复和清理。

如果某项行为无法运行验证：

- 明确说明缺少什么环境。
- 保留静态代码证据。
- 标记为 NOT_VERIFIED 或 BLOCKED。
- 不得用静态代码相似度替代运行验证。

# 十、第七阶段：审核结果状态

每项审核必须使用以下状态：

| 状态 | 含义 |
|---|---|
| PASS | 职责已完整承接，行为一致且有充分证据 |
| FAIL | 明确存在职责遗漏或行为漂移 |
| NOT_IMPLEMENTED | C 尚未实现对应职责 |
| NOT_VERIFIED | 实现存在，但没有充分证据证明一致 |
| FRAMEWORK_DIFFERENCE | 存在框架差异，尚未确认是否影响行为 |
| BLOCKED | 缺少环境或依赖，无法完成验证 |
| INTENTIONALLY_CHANGED | 有明确批准依据的主动行为变更 |

注意：

- FRAMEWORK_DIFFERENCE 不能计入 PASS。
- NOT_VERIFIED 不能计入 PASS。
- NOT_IMPLEMENTED 不能计入 PASS。
- BLOCKED 不能计入 PASS。
- INTENTIONALLY_CHANGED 不能伪装成语义等价。

如果某项差异已经通过测试证明不影响业务可观察行为，可以将最终行为结论判为 PASS，同时在框架差异清单中保留该差异。

# 十二、执行约束和 Token 预算

我的 Token 额度有限。

本次审核必须优先保证覆盖质量，而不是通过无限扩大扫描范围来追求报告长度。

必须遵守：

1. 优先使用现有 Mapping_Table 和 File_Tree。
2. 不重新生成整个文件树。
3. 不重新生成整个 Mapping_Table。
4. 不重复读取已经有充分证据的历史报告。
5. 不对整个仓库进行无差别逐行扫描。
6. 不逐个打开与当前审核范围无关的文件。
7. 先根据映射关系确定需要读取的源文件和目标文件。
8. 对合并文件，必须检查所有来源文件的实际职责。
9. 对拆分文件，必须检查全部承接文件。
10. 对框架差异，优先检查真正影响运行行为的组件。
11. 只有在证据不足时才扩大检查范围。
12. 避免重复执行已经完成的测试。
13. 每次测试必须对应明确的待验证行为。
14. 不要生成大段 Spring Boot 或 Java 基础知识说明。
15. 不要为了报告显得完整而复制大量源代码。

**Token 节省不能以减少职责覆盖、遗漏分支或跳过异常路径为代价。**

如果当前 Token 预算不足以完成整个模块：

- 按业务流程分阶段审核。
- 记录已经完成的范围。
- 记录尚未完成的源文件和职责。
- 记录未完成的框架差异。
- 保存明确的续审位置。
- 不得把未完成部分标记为 PASS。

# 十三、禁止事项

禁止：

- 将其他项目或其他语言的实现引入本次迁移审核。

# 十四、最终必须回答的问题

1. C 是否完整承接 B 的全部实际职责？
2. Mapping_Table 中 RAG → RAG-V1 的映射是否与当前真实代码一致？
3. File_Tree 规定的目标结构是否正确落地？
4. 多文件合并是否造成职责、分支或异常路径遗漏？
5. 文件拆分是否造成调用链、数据传递或事务边界断裂？
6. API + RPC 合并是否改变原有入口和执行行为？
7. Common Starter 上收是否遗漏原有消费方？
8. Spring Boot 4 → 3.5 是否引入业务可观察行为变化？
9. Tomcat、Jackson、Spring Framework 等底层版本变化是否产生实际漂移？
10. 哪些差异已经通过证据证明安全？
11. 哪些差异仍然无法确认？
12. 当前 C 是否具备可靠的行为对拍条件？

**最终审核标准：C 不需要在代码结构上复制 B，但必须完整承接 B 的全部实际职责和需要保留的行为；框架实现可以不同，但不能以框架差异为理由放任未经批准的行为漂移。**
