# 任务：为现有源码流程教学文档增量增加「从需求到实现」的开发能力教学内容

## 一、任务背景

当前 ‘/Users/pr/Documents/GitHub/RAG-V1/Book/users’目录中已经存在一批基于真实 Java 项目源码编写的教学文档。

这些文档已经完成了大量工作，包括：

- 真实业务流程的执行顺序追踪；

- HTTP 请求、Spring MVC、Controller、Service、Mapper、数据库等环节的具体执行过程；

- Java 本地方法调用、Spring 框架触发、MyBatis 代理、gRPC 网络调用之间的区分；

- 各文件、类、方法的职责和实际执行时机；

- 数据在各环节之间的传递与变化；

- 正常路径、失败路径、异常传播和外部副作用；

- 项目启动、Bean 初始化、服务注册等生命周期机制。


**本次任务不是重新编写这些文档，而是在现有文档的基础上增加新的教学内容。**

现有文档主要解决：

> 已经有这套代码时，一次请求或事件在运行过程中究竟发生了什么？

本次需要进一步解决：

> 如果开发者面对的是一个需求，而不是一套已经写好的代码，他应该如何一步步推导出这些组件、文件、类、方法、数据结构和执行流程，最终把系统实现出来？实现之后又如何验证、排查和修改？

最终目标是让我不仅能够阅读、解释现有 Java 项目的运行过程，还能够在面对类似需求时，独立完成需求分析、组件设计、代码编写、行为验证、问题定位和系统修改。

## 三、需要新增的六项开发能力

这六项能力必须落实到真实项目的业务流程、源码和设计决定中，不能只给定义。

### 1. 独立分析需求

教学目标：

面对一个业务需求，不依赖现成实现，能够判断系统应该表现出什么行为。

以当前文档对应的真实业务为基础，讲解：

- 需求描述中有哪些明确要求？

- 谁发起这项操作？

- 操作需要什么输入？

- 系统需要执行哪些业务动作？

- 什么条件下算成功？

- 什么条件下必须拒绝？

- 有哪些边界情况？

- 有哪些失败情况？

- 哪些数据必须保持一致？

- 哪些行为是已有系统必须继续保持的？

- 哪些要求涉及事务、幂等、并发、安全性或外部依赖？


不能直接从现有代码倒推出一套看似合理的需求，然后声称这就是原始需求。

必须区分：

- **源码事实**：可以从当前源码直接确认的行为。

- **已有契约依据**：可以从接口定义、数据库约束、协议、原 Go 项目等确认的要求。

- **设计推导**：根据已确认的行为和约束推导出的合理实现要求。

- **无法确认**：当前资料不足以确定的内容。


如果没有原始需求文档，必须明确说明这是根据现有行为还原出的需求模型，而不是原开发者真实的需求记录。

最终需要让我能够回答：

> 如果现在让我从零实现这个业务，我首先应该确定哪些行为？为什么？

### 2. 设计组件

教学目标：

从已经明确的业务行为，推导出系统需要哪些组件，以及每个组件为什么存在。

不能直接给出当前文件树，然后解释每个文件的职责。

需要反过来讲解：

1. 某项业务行为要求系统完成什么工作？

2. 这项工作为什么需要独立的组件或方法？

3. 应该由哪个层次承担？

4. 为什么不应该由其他组件承担？

5. 组件需要什么输入？

6. 组件产生什么输出？

7. 它依赖什么？

8. 它通过什么方式被调用？

9. 它需要维护什么状态？

10. 它是否需要处理异常、事务、资源生命周期或并发？


必须结合当前项目中的真实组件进行分析，例如：

- Controller

- API Service

- Domain Service

- Mapper

- Entity

- DTO

- Proto

- Config

- Interceptor

- Filter

- Exception Handler

- Response Advice

- 各种基础设施组件


重点解释组件的产生过程，而不是重复介绍它们的定义。

例如，不能只说：

> LoginReq 是一个 DTO，用于接收登录请求。

而应当讲清楚：

- 客户端发送什么数据？

- Spring MVC 如何将 JSON 转成 Java 对象？

- 为什么需要这个 Java 对象？

- 为什么不直接使用 Proto 中的 LoginReq？

- 哪些字段来自外部请求？

- 哪些字段需要校验？

- DTO 的字段如何根据接口契约确定？

- 如果从空文件开始，如何确定这个 record 的结构？

- 如果字段发生变化，哪些下游组件会受到影响？


**对于 DTO、Entity、Proto、配置类、接口、枚举等代码量很少但不可缺少的文件，必须给予足够的推导说明。不能因为它们简单，就只写一句职责介绍。**

同时必须考虑 Spring 框架实际提供的能力。

不能为了模仿原来的 Go 项目而机械地拆分 Java 文件，也不能因为 Spring 提供了某项机制就随意合并组件。

需要解释：

- 哪些职责由 Spring 实际承担；

- 哪些职责仍然需要自己编写代码；

- 框架提供的机制替代了什么工作；

- 哪些业务行为不能因为框架存在而被省略。


### 3. 编写代码

教学目标：

让我理解从空文件开始，如何根据需求和设计真正写出当前代码。

对于当前流程涉及的关键文件，讲解：

1. 在开始写这个文件之前，已经明确了哪些需求？

2. 为什么需要这个文件？

3. 应该先确定什么类型、类、接口或 record？

4. 应该有哪些字段？

5. 每个字段来自哪里？

6. 应该有哪些方法？

7. 每个方法的输入、输出和异常如何确定？

8. 方法内部应该按照什么顺序执行？

9. 应该调用哪些已有组件？

10. 应该使用哪些 Spring、MyBatis 或其他框架机制？

11. 哪些代码是框架自动完成的，哪些必须自己实现？

12. 如何从当前文件的上下游关系反推它的代码结构？


不能只把现有代码重新解释一遍。

必须增加从零编写时的推导过程。

例如，分析 `LoginReq` 时，不能直接把现有 record 展示出来就结束，而应当从 HTTP 接口的输入契约开始，推导出：

- 为什么需要一个请求类型；

- 为什么使用 record；

- 为什么需要 username 和 password；

- 为什么字段类型是 String；

- 为什么使用 `@NotNull`；

- 为什么这里没有使用 `@NotBlank`；

- 为什么 Controller 接收它；

- 后续哪个组件使用它；

- 它如何转换为 Proto 类型；

- 如果自己从空文件创建，应当如何逐步写出来。


对于简单文件，也必须说明它的存在理由和产生过程。

对于复杂文件，则需要讲解关键方法的编写顺序、依赖关系、控制流程和异常路径。

不要要求我背诵现有类名、注解或文件结构。重点是让我知道：**当需求和上下游约束确定后，应该如何推导出这些代码。**

### 4. 验证行为

教学目标：

让我能够根据需求判断代码是否正确，而不是仅仅判断代码能否编译。

针对当前业务流程，讲解：

- 如何从需求中推导测试用例？

- 哪些是正常路径？

- 哪些是失败路径？

- 哪些是边界条件？

- 哪些输入应该被拒绝？

- 哪些操作会改变数据库状态？

- 哪些操作会改变 Redis、消息或其他外部状态？

- 如何验证事务是否生效？

- 如何验证幂等性？

- 如何验证并发行为？

- 如何验证异常是否被正确转换？

- 如何确认接口返回值与实际副作用一致？

- 修改后需要回归哪些原有行为？


必须区分：

1. 当前项目已经存在的测试；

2. 当前测试实际覆盖的行为；

3. 根据需求推导出来但尚未覆盖的测试；

4. 仅凭源码分析得出的预期，尚未实际运行验证的结论。


不能把“代码看起来没问题”“能够编译”“已有测试通过”直接等同于行为正确。

如果项目中存在测试类、测试脚本或 Apifox 测试资料，应当结合实际内容说明它们如何验证当前流程。

不能虚构已经执行过的测试。

### 5. 定位问题

教学目标：

让我面对实际故障时，能够从现象出发定位问题，而不是只会阅读正常执行流程。

针对当前业务流程，设计具有实际意义的问题定位案例。

每个案例必须包含：

1. **故障现象**：用户、接口或系统实际观察到了什么？

2. **预期行为**：正常情况下应该发生什么？

3. **实际行为**：现在发生了什么？

4. **排查入口**：应该从哪个接口、文件、方法或运行结果开始？

5. **检查顺序**：应该按照什么顺序检查？

6. **可能原因**：有哪些合理的故障假设？

7. **排除过程**：通过什么证据排除某个假设？

8. **根因确认**：如何证明真正的问题在哪里？

9. **影响范围**：问题还可能影响哪些组件和业务流程？

10. **修复与验证**：修改后应该重新验证什么？


案例应当来自当前流程的真实实现和依赖关系。

例如：

- DTO 字段定义与实际 JSON 输入不一致；

- Jackson 反序列化失败；

- Bean Validation 与业务要求不一致；

- API 层与 Domain Service 的状态映射错误；

- Mapper 查询条件错误；

- 数据库返回结果与预期不一致；

- Redis 黑名单读写不一致；

- JWT claim 或身份传递出现问题；

- 事务边界不正确；

- gRPC 状态码映射错误；

- Spring Bean 未注册或配置没有生效。


这些只是案例方向，必须根据当前流程选择真正相关的情况，不能为了凑数量而机械套用。

特别要求：不能把问题定位简化为“查看日志”“检查数据库”“使用 Debug”。

必须解释为什么先检查这里、这个检查能够排除什么、下一步应该根据什么结果决定。

### 6. 修改系统

教学目标：

让我面对一个已经运行的系统时，能够在理解原有行为的基础上完成修改，而不是只会从零写一个新功能。

针对当前流程设计合理的需求变更场景。

每个场景必须讲解：

1. 原有业务行为是什么？

2. 新需求改变了什么？

3. 哪些原有行为必须保持不变？

4. 哪些组件需要修改？

5. 为什么这些组件需要修改？

6. 哪些组件不应该修改？

7. 是否需要新增 DTO、Entity、字段、方法、配置或数据库约束？

8. 是否影响接口契约、Proto、数据库结构或其他服务？

9. 是否影响事务、幂等、并发、安全性和异常处理？

10. 修改的合理顺序是什么？

11. 修改后需要验证哪些新行为？

12. 需要回归哪些旧行为？


不能只给出修改后的代码。

必须解释为什么修改位置是这里，以及如何判断修改范围。

尤其要区分：

- 需求确实要求修改的部分；

- 为保持原有行为而必须同步修改的部分；

- 看似相关但不应该修改的部分；

- 当前项目没有实现、仅作为教学演示的变更建议。


如果是教学演示，必须明确标记为假设场景，不能将其描述成当前源码已经存在的功能。

## 四、六项能力必须与原有流程文档建立对应关系

- 如果调整认证规则，如何判断 Filter、Interceptor、业务层和配置之间的修改范围。


其他流程也必须采用相同原则，针对各自实际业务展开。

不能把所有文档的新增部分都写成同一套泛化内容，只替换业务名称。

## 七、内容质量要求

### 1. 不要只解释结果，要解释推导过程

不合格：

> 这里需要一个 DTO，用于接收客户端数据。

合格的讲解应当回答：

- 为什么需要承接客户端数据？

- 数据从哪里来？

- 下游谁使用它？

- 为什么不直接复用其他类型？

- 字段和类型如何确定？

- 校验规则从哪里来？

- 如果从空文件开始，如何写出这个 DTO？


### 2. 不要把现有实现误认为唯一可能的实现

如果某个设计有多种合理实现，需要说明：

- 当前项目选择了哪一种；

- 选择它满足了什么要求；

- 其他实现为什么可能不适合当前约束；

- 哪些属于必要条件，哪些属于实现选择。


不能把当前代码的每个写法都包装成唯一正确答案。

### 3. 不要编造开发者的主观意图

可以根据代码和契约推导设计理由，但必须区分事实和推断。

### 4. 不要省略失败路径

设计、编码、验证、排错都必须考虑失败路径。

### 5. 不要用抽象词代替具体教学

禁止仅写：

- 提高可维护性；

- 保证高内聚低耦合；

- 遵循单一职责原则；

- 提升系统健壮性；

- 做好异常处理；

- 加强测试覆盖。


如果使用这些概念，必须紧接着解释当前项目中具体是哪项职责、哪条依赖、哪个异常、哪种测试或哪处修改体现了它。

### 6. 不要把教学变成背诵

我不需要背下 30 篇文档中的所有类名、注解和文件路径。

我需要知道：

- 这些代码为什么会存在；

- 这些代码是从什么要求推导出来的；

- 如果没有这些代码，我应该如何确定需要写什么；

- 如何知道自己写对了；

- 出现问题如何定位；

- 修改需求时如何控制影响范围。


## 八、执行顺序

必须按以下顺序开展工作：

### 第一步：盘点现有文档

读取 `Book/` 目录中的全部 Markdown 文件。

建立清单，记录：

- 文件路径；

- 文档类型；

- 对应业务或机制；

- 原有章节结构；

- 涉及的主要源码组件；

- 适合增加的六项能力内容；

- 是否存在可以直接复用的原有解释。


不要在没有盘点的情况下直接批量生成。

### 第二步：确定新增内容与原文的对应关系

先建立一份补充计划，说明每篇文档将增加什么。

注意不同业务之间的差异。

例如，登录与注册都涉及 DTO，但字段来源、业务约束、失败条件和验证方法并不相同。

### 第三步：读取必要的真实源码

新增内容必须继续以真实项目源码为依据。

如果当前工作环境中没有原始源码，必须明确指出缺少哪些文件，不得凭原教学文档臆造源码细节。

涉及跨文件推导时，必须检查实际上下游代码。

### 第四步：逐篇增量补充

每次修改前读取原文件。

在原文末尾增加新章节。

不得用新生成的内容覆盖原有文档。

如果需要修改 README，只做必要的索引更新。

### 第五步：检查修改结果

逐篇检查：

- 原文是否完整保留；

- 原有代码片段、表格和 Mermaid 图是否保留；

- 原有章节编号和链接是否被破坏；

- 新增内容是否真正对应当前业务；

- 六项能力是否有具体的教学内容；

- 是否存在编造源码事实的情况；

- 是否只是重复原有运行流程；

- 是否对 DTO 等简单文件进行了充分的推导；

- 是否区分源码事实、设计推导和演示假设。


### 第六步：汇报完成情况

最终提供：

1. 修改的文件清单；

2. 每篇文档新增的章节；

3. 六项能力在各篇文档中的覆盖情况；

4. 仍然缺少源码依据、无法准确展开的部分；

5. 原文保留情况；

6. 尚未完成的任务。


不能仅报告“全部完成”，必须提供可检查的具体结果。

## 九、最终验收标准

这次工作是否合格，不以新增了多少文字、多少章节为标准。

而是看我读完现有流程讲解和新增内容后，能否做到：

1. 面对类似业务需求，独立列出需要实现的行为和约束；

2. 从这些行为推导出需要的组件、类、方法、DTO、Entity、Proto 等；

3. 解释为什么需要这些文件，以及每个字段、方法和依赖从哪里来；

4. 从空文件开始，按照合理顺序实现关键代码；

5. 根据业务要求设计验证方法，并判断哪些行为已经得到验证；

6. 面对实际故障，能够从现象出发定位根因；

7. 面对需求变更，能够判断修改范围、实施修改并完成回归。


**最重要的验收问题：**

如果暂时不让我参考当前实现，只给我一份类似的业务需求，我能否根据学到的推导过程，自己决定应该写哪些文件、每个文件应该有什么内容、组件之间如何协作、如何验证以及出现问题如何处理？

如果新增内容仍然只是把当前源码换一种说法重新解释一遍，就没有完成本次任务。
